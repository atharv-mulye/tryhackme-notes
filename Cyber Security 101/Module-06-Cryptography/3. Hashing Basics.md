# Hashing Basics

## Introduction

- Hashing is used to verify that data has not been modified.
- It allows us to compare large files quickly without checking every byte manually.
- If two files have the same hash value, they are very likely identical.
- A hash value is generated using a hash function.

---

## Hash Functions

### What is a Hash Function ?

- A hash function takes data of any size as input.
- It produces a fixed-size output called a hash value or digest.
- Hashing is a one-way process.
- Unlike encryption, there is no key used in hashing.
- It should be computationally impractical to recover the original input from the hash.

### Characteristics of a Good Hash Function

- Fast to calculate
- Produces a fixed-length output
- Difficult to reverse
- Small input changes create completely different outputs
- Minimizes the chance of collisions

---

## Avalanche Effect

A tiny change in the input should produce a significantly different hash output.

### Example

Files containing:

```text
T
```

and

```text
U
```

differ by only one bit, yet their hashes are completely different.

### Generate Hashes

```bash
md5sum file.txt
sha1sum file.txt
sha256sum file.txt
sha512sum file.txt
```

This behavior helps detect even the smallest modifications in data.

---

## Common Hashing Algorithms

### MD5

- Produces a 128-bit hash
- Fast but considered insecure
- Vulnerable to collision attacks

### SHA1

- Produces a 160-bit hash
- More secure than MD5 but no longer recommended
- Vulnerable to practical collision attacks

### SHA-256

- Part of the SHA-2 family
- Produces a 256-bit hash
- Widely used and currently considered secure

### SHA-512

- Produces a 512-bit hash
- Stronger security and larger output size

---

## Why Hashing is Important ?

### Data Integrity

- Verifies that files have not been altered.
- Commonly used when downloading software and operating system images.
- Matching hashes indicate that files are likely identical.

### Password Security

- Systems should store password hashes instead of plain-text passwords.
- During login:
  1. User enters password.
  2. System hashes the password.
  3. Generated hash is compared with the stored hash.
  4. Access is granted if both hashes match.

### Benefits

- Passwords are not stored directly.
- Reduces damage if a database is compromised.
- Adds an extra layer of protection.

---

## Hash Collisions

### What is a Collision ?

A collision occurs when two different inputs produce the same hash value.

```text
Input A → Hash X
Input B → Hash X
```

Even though the inputs are different, the output is identical.

### Why Collisions Happen ? 

- Input possibilities are practically unlimited.
- Hash outputs have a fixed size.
- Eventually, different inputs must share the same output.

This concept is explained by the **Pigeonhole Principle**.

### Simple Example

If a hash function generates:

```text
4-bit output
```

Possible hash values:

```text
2^4 = 16
```

Only 16 unique outputs exist.

Since there are far more than 16 possible inputs, some inputs must produce the same hash.

---

## Collision Attacks

### MD5

- Collision attacks have been demonstrated.
- Considered insecure for security-sensitive purposes.

### SHA1

- Practical collision attacks exist.
- No longer recommended for modern security applications.

Because of these weaknesses:

❌ Do not use MD5 for password storage.

❌ Do not use SHA1 for password storage.

✅ Use modern algorithms such as:

- SHA-256
- SHA-512
- bcrypt
- scrypt
- Argon2

---

## Key Takeaways

- Hashing is a one-way mathematical process.
- A hash function converts data of any size into a fixed-size output.
- Small input changes create drastically different hashes.
- Hashing is commonly used for:
  - Data integrity verification
  - Password storage
  - Digital signatures
- Hash collisions are unavoidable but should be extremely rare.
- MD5 and SHA1 are considered insecure due to collision attacks.
- Modern applications should use stronger hashing algorithms.

 > Hashing is a fundamental cybersecurity concept used to verify data integrity and securely store passwords. A hash function generates a fixed-length fingerprint of data, making it easy to detect modifications. While collisions are mathematically unavoidable, modern hashing algorithms are designed to make them extremely difficult to exploit, ensuring reliable security in real-world applications.

## Password Storage and Hashing

### Why Password Storage Matters ? 

- Websites and applications need to verify user passwords.
- Storing passwords insecurely can lead to major data breaches.
- If attackers obtain passwords, users who reuse passwords on multiple sites become vulnerable.
- Secure password storage is essential for protecting user accounts.

---

## Insecure Password Storage Methods

### 1. Storing Passwords in Plaintext

#### What It Means

- Passwords are stored exactly as users enter them.
- No encryption or hashing is applied.

#### Why It Is Dangerous ? 

- Anyone with database access can read all passwords.
- A data breach immediately exposes every user's password.

#### Example : RockYou Breach

- RockYou stored passwords in plaintext.
- Their database was leaked.
- More than 14 million passwords became public.
- The famous `rockyou.txt` wordlist originated from this breach.

Common passwords found:

```text
123456
password
iloveyou
princess
abc123
```

#### Takeaway

❌ Never store passwords in plaintext.

---

### 2. Using Weak Encryption

#### What Happened

- Some organizations encrypted passwords instead of hashing them.
- Older or deprecated encryption methods were used.

#### Example : Adobe Breach

Issues included:

- Passwords stored using weak encryption.
- Password hints stored in plaintext.
- Some hints directly revealed passwords.

#### Problem

- If attackers obtain the encryption key, every password can be decrypted.

#### Takeaway

❌ Encryption is not the preferred method for password authentication.

---

### 3. Using Weak Hashing Algorithms

#### Example : LinkedIn Breach

LinkedIn stored passwords using:

```text
SHA-1
```

Problems:

- SHA-1 is outdated.
- No password salting was used.
- Attackers cracked millions of passwords.

#### Takeaway

❌ MD5 and SHA-1 should not be used for password storage.

---

## Secure Password Storage Using Hashing

### Why Hash Passwords ?

Instead of storing passwords directly:

```text
Password → Hash Function → Stored Hash
```

Benefits:

- Original password is not stored.
- Database leaks reveal hashes instead of passwords.
- Attackers must crack each hash individually.

---

## Problem : Duplicate Passwords

Consider two users:

```text
User A: password123
User B: password123
```

Without salting:

```text
password123 → Same Hash
```

Issues:

- Attackers can identify users with the same password.
- One cracked hash may compromise multiple accounts.
- Rainbow table attacks become effective.

---

## Rainbow Tables

### What Are Rainbow Tables ?

A rainbow table is a precomputed database containing:

```text
Hash → Password
```

Example :

| Hash | Password |
|--------|----------|
| e10adc3949ba59abbe56e057f20f883e | 123456 |
| e99a18c428cb38d5f260853678922e03 | abc123 |
| d0199f51d2728db6011945145a1b607a | basketball |

### Purpose

- Speeds up password cracking.
- Avoids hashing passwords repeatedly.
- Uses storage space to save computation time.

### Takeaway

❌ Unsalted hashes are vulnerable to rainbow table attacks.

---

## Password Salting

### What Is a Salt ?

A salt is a random value added to a password before hashing.

Example:

```text
Password: AL4RMc10k
Salt: Y4UV*^(=go_!
```

Combined value:

```text
AL4RMc10kY4UV*^(=go_!
```

The combined value is then hashed.

---

## Benefits of Salting

### Prevents Duplicate Hashes

Even if two users have the same password:

```text
Password + Salt A → Hash A
Password + Salt B → Hash B
```

Result:

- Different hashes
- No visible password reuse

### Defends Against Rainbow Tables

- Attackers must generate new tables for every salt.
- Precomputed rainbow tables become ineffective.

### Important Note

- Salts do not need to be secret.
- Salts should be unique for every user.

---

## Secure Password Storage Process

### Recommended Steps

#### Step 1: Choose a Strong Password Hashing Algorithm

Recommended algorithms:

- Argon2
- bcrypt
- scrypt
- PBKDF2

#### Step 2: Generate a Unique Salt

Example:

```text
Y4UV*^(=go_!
```

#### Step 3: Combine Password and Salt

```text
AL4RMc10k + Y4UV*^(=go_!
```

Result:

```text
AL4RMc10kY4UV*^(=go_!
```

#### Step 4: Hash the Combined Value

```text
Hash(AL4RMc10kY4UV*^(=go_!)
```

#### Step 5: Store

Store:

- Hashed password
- Salt

Do NOT store:

- Original password

---

## Why Not Encrypt Passwords ?

At first glance, encryption seems like a good solution.

Example:

```text
Password → Encryption → Database
```

However:

- Encryption requires a key.
- The key must be stored somewhere.
- If attackers obtain the key, they can decrypt every password.

Hashing avoids this problem because:

- No decryption key exists.
- Hashes are designed to be one-way.

### Takeaway

✅ Hash passwords instead of encrypting them for authentication purposes.

---

## Best Practices

- Never store passwords in plaintext.
- Avoid MD5 and SHA-1.
- Use strong password hashing algorithms.
- Generate a unique salt for every user.
- Store only hashes and salts.
- Never store the original password.
- Regularly review password storage practices.

---

## Key Points

- Plaintext password storage is extremely insecure.
- Weak encryption can expose all passwords if the key is compromised.
- Modern systems use hashing instead of storing passwords directly.
- Salting prevents duplicate hashes and rainbow table attacks.
- Recommended password hashing algorithms include Argon2, bcrypt, scrypt, and PBKDF2.
- Secure password storage relies on strong hashing algorithms, unique salts, and proper implementation.

- In offensive security, password hashes are often discovered during assessments or CTFs.
- Before attempting to crack a hash, it is important to identify its type.
- Knowing the hash type helps determine which tools and techniques should be used.

---

### Automated Tools

## Linux Password Hashes

### Password Storage Location

Linux stores password hashes in:

```text
/etc/shadow
```

### Why ?

- Only privileged users can read it.
- Provides better security than the older `/etc/passwd` method.

### Structure of /etc/shadow

Each entry contains multiple fields separated by colons:

```text
username:password_hash:other_fields
```

Example:

```text
strategos:$y$j9T$76UzfgEM5PnymhQ7TlJey1$/OOSg64dhfF.TigVPdzqiFang6uZA4QA1pzzegKdVm4
```

---

## Linux Hash Format

Linux password hashes usually follow :

```text
$prefix$options$salt$hash
```

Components :

| Component | Purpose |
|-----------|----------|
| Prefix | Identifies algorithm |
| Options | Algorithm parameters |
| Salt | Random value added before hashing |
| Hash | Final hashed password |

---

## Common Linux Password Prefixes

| Prefix | Algorithm |
|----------|------------|
| `$y$` | yescrypt |
| `$gy$` | gost-yescrypt |
| `$7$` | scrypt |
| `$2a$`, `$2b$`, `$2x$`, `$2y$` | bcrypt |
| `$6$` | sha512crypt |
| `$md5` | SunMD5 |
| `$1$` | md5crypt |

## Common Unix/Linux Password Hash Prefixes

| Prefix | Algorithm | Notes |
|----------|------------|---------|
| `$y$` | yescrypt | Modern scalable password hashing scheme. Recommended default on newer Linux systems. |
| `$gy$` | gost-yescrypt | Combines the GOST R 34.11-2012 hash function with yescrypt. |
| `$7$` | scrypt | Memory-hard password-based key derivation function designed to resist brute-force attacks. |
| `$2b$`, `$2y$`, `$2a$`, `$2x$` | bcrypt | Based on the Blowfish cipher. Widely used and considered secure for password storage. |
| `$6$` | sha512crypt | Uses SHA-512. Commonly found on older Linux distributions. |
| `$md5` | SunMD5 | MD5-based hashing method originally developed for Solaris systems. |
| `$1$` | md5crypt | MD5-based password hashing algorithm originally developed for FreeBSD. Considered outdated. |

> **Strength Order (Strongest → Weakest):**
>
> `yescrypt → gost-yescrypt → scrypt → bcrypt → sha512crypt → SunMD5 → md5crypt`

## Password Cracking

## Key Points

- Password hashes cannot be decrypted because hashing is a one-way process.
- To recover a password, attackers attempt to crack the hash by hashing many candidate passwords and comparing the results.
- Common password cracking tools:
  - Hashcat
  - John the Ripper (JtR)

---

## How Password Cracking Works

1. Obtain the target hash.
2. Select a wordlist (e.g., rockyou.txt).
3. Hash each word using the same algorithm.
4. Compare generated hashes with the target hash.
5. If a match is found, the original password is identified.

---

## Popular Password Cracking Tools

| Tool | Description |
|--------|-------------|
| Hashcat | GPU-accelerated password cracking tool |
| John the Ripper | Popular CPU-based password cracker |
| CrackStation | Online hash lookup service |
| Hashes.com | Online hash cracking database |

---

## Cracking Passwords with GPUs

### Why GPUs Are Fast

- Modern GPUs contain thousands of processing cores.
- They perform mathematical operations much faster than CPUs.
- Ideal for cracking large numbers of hashes.

### Limitation

Some algorithms are intentionally designed to resist GPU acceleration:

- bcrypt
- scrypt
- Argon2

These algorithms make password cracking slower and more expensive.

---

## Running Cracking Tools in Virtual Machines

### Hashcat

❌ Not ideal inside a VM because:

- GPU access is limited.
- Performance is reduced.
- Cracking speed is significantly slower.

### John the Ripper

✅ Works well inside VMs because:

- Uses CPU by default.
- Requires less GPU support.

### Recommendation

- Run Hashcat on the host machine whenever possible.
- Use John the Ripper in VMs if needed.

---

## Basic Hashcat Syntax

```bash
hashcat -m <hash_type> -a <attack_mode> hashfile wordlist
```

### Parameters

| Option | Purpose |
|----------|----------|
| `-m` | Specifies hash type |
| `-a` | Specifies attack mode |
| `hashfile` | File containing target hash |
| `wordlist` | Password list used for cracking |

### Example

```bash
hashcat -m 3200 -a 0 hash.txt /usr/share/wordlists/rockyou.txt
```

This command:

- Uses bcrypt mode
- Performs a dictionary attack
- Uses rockyou.txt as the wordlist

## HMAC (Hash-based Message Authentication Code)

## What is HMAC ?

HMAC combines:

- A secret key
- A hashing algorithm

to verify:

- Integrity
- Authenticity

---

## Why Use HMAC ?

Normal hashing only proves data integrity.

HMAC proves:

### Integrity

- Data has not been modified.

### Authenticity

- Data originated from someone possessing the secret key.

---

## HMAC Process

<img width="450" height="400" alt="image" src="https://github.com/user-attachments/assets/239eccfc-221e-4030-9da2-bec70f3a26d5" />

1. The secret key is padded to the block size of the hash function.
2. The padded key is XORed with a constant (usually a block of zeros or ones).
3. The message is hashed using the hash function with the XORed key.
4. The result from Step 3 is then hashed again with the same hash function but using the padded key XORed with another constant.
5. The final output is the HMAC value, typically a fixed-size string.


---

## HMAC Formula

```text
HMAC(K,M) = H((K ⊕ opad) || H((K ⊕ ipad) || M))
```

Where :

| Symbol | Meaning |
|----------|---------|
| K | Secret Key |
| M | Message |
| H | Hash Function |
| opad | Outer Padding |
| ipad | Inner Padding |

## Hashing vs Encoding vs Encryption

## Hashing

### Purpose

- Verify integrity
- Store passwords securely

### Characteristics

- One-way process
- Cannot be reversed

Example:

```text
Password → Hash
```

---

## Encoding

### Purpose

- Convert data into a different format
- Improve compatibility between systems

### Examples

- ASCII
- UTF-8
- UTF-16
- Base32
- Base64

### Example

```bash
echo "TryHackMe" | base64
```

Output:

```text
VHJ5SGFja01lCg==
```

### Characteristics

- Easily reversible
- Does not provide security

---

## Encryption

### Purpose

- Protect confidentiality

### Characteristics

- Uses a cryptographic key
- Reversible if the key is known

Example:

```text
Plaintext → Encryption → Ciphertext
```

```text
Ciphertext → Decryption → Plaintext
```

---

## Quick Comparison

| Feature | Hashing | Encoding | Encryption |
|----------|----------|-----------|------------|
| Reversible | ❌ No | ✅ Yes | ✅ Yes |
| Uses Key | ❌ No | ❌ No | ✅ Yes |
| Protects Confidentiality | ❌ No | ❌ No | ✅ Yes |
| Verifies Integrity | ✅ Yes | ❌ No | ❌ No |
| Password Storage | ✅ Yes | ❌ No | ❌ No |

## Extra Info : Salt & Pepper

## What is a Salt ?

A **salt** is a random value added to a password before hashing.

### Example

```text
Password: password123
Salt: X7#9mK
```

Combined value:

```text
password123X7#9mK
```

The combined value is then hashed.

<img width="1297" height="504" alt="image" src="https://github.com/user-attachments/assets/51530102-3471-4ee3-9a2d-abf651172776" />

### Key Points

- Unique for each user
- Stored alongside the hash
- Does not need to be secret
- Prevents rainbow table attacks
- Ensures identical passwords generate different hashes

### Where is the Salt Stored ?

The salt is typically stored:

- In the authentication database
- Alongside the user's password hash
- Inside Linux password hash formats (e.g., `/etc/shadow`)
- Within application authentication tables

Example:

```text
Username: alice
Salt: X7#9mK
Hash: abc123xyz...
```

Since salts are not secret, storing them with the hash is considered safe.

---

## What is a Pepper ?

A **pepper** is an additional secret value added to the password before hashing.

### Example

```text
Password + Salt + Pepper
```

```text
password123 + X7#9mK + SuperSecretPepper
```

The resulting value is then hashed.

<img width="946" height="312" alt="image" src="https://github.com/user-attachments/assets/6700cdec-a799-4348-81cd-8cc13ead023e" />

### Key Points

- Secret value
- Usually shared across all users
- Not stored with password hashes
- Adds an extra layer of protection
- Helps defend against database breaches

---

## Where is the Pepper Stored ?

Unlike salts, peppers should **never be stored in the database**.

Common storage locations include :

### Environment Variables

```text
PEPPER=SuperSecretPepper
```

Stored on the application server and loaded at runtime.

### Application Configuration Files

```text
config.json
settings.conf
.env
```

Access should be restricted to administrators and the application itself.

### Secrets Management Systems

Examples:

- HashiCorp Vault
- AWS Secrets Manager
- Azure Key Vault
- Google Secret Manager

These are preferred in enterprise environments.

### Hardware Security Modules (HSMs)

- Dedicated hardware devices for storing secrets
- Extremely secure
- Common in high-security environments

---

## Salt vs Pepper

| Feature | Salt | Pepper |
|----------|--------|---------|
| Unique per user | ✅ Yes | ❌ Usually No |
| Stored in database | ✅ Yes | ❌ No |
| Secret value | ❌ No | ✅ Yes |
| Protects against rainbow tables | ✅ Yes | ❌ No |
| Protects against database leaks | ❌ Limited | ✅ Yes |

---

## Why Use a Pepper ?

If an attacker steals the database, they may obtain:

```text
Username
Salt
Hash
```

However, they still need the secret pepper to reproduce the correct hash.

Without the pepper:

```text
Password + Salt ≠ Stored Hash
```

The attacker must first compromise the application server or secret storage system before launching an effective cracking attack.

---

## Recommended Password Storage Process

```text
Password
    ↓
Add Unique Salt
    ↓
Add Secret Pepper
    ↓
Hash using Argon2 / bcrypt / scrypt
    ↓
Store Hash + Salt
```

### Database Stores

```text
Username
Salt
Hash
```

### Separate Secret Storage Stores

```text
Pepper
```

---

## Best Practice

For maximum security:

- Use Argon2, bcrypt, or scrypt
- Generate a unique salt for every user
- Store salts with the hash
- Store peppers separately from the database
- Use a secrets manager or HSM when possible

This approach significantly increases the difficulty of password-cracking attacks, even if the authentication database is compromised.
