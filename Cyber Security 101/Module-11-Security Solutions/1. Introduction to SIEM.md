# Introduction to SIEM

## What is SIEM ?

**SIEM (Security Information and Event Management)** is the central security solution used by SOC analysts to collect, analyze, correlate, and monitor logs from different devices across an organization.

Instead of checking logs on every device individually, SIEM gathers everything into one place and automatically detects suspicious activities.

---

## Logs Everywhere, Answers Nowhere

### Logs Everywhere

Every device in a network continuously generates logs.

These devices are called Log Sources.

### Types of Log Sources

#### 1. Host-Centric Log Sources

Generate logs related to activities happening **inside a device**.

**Examples of devices**
- Windows
- Linux
- Servers
- Workstations

**Examples of logs**
- User accessing files
- User login attempts
- Process execution
- Registry modifications
- PowerShell execution

#### 2. Network-Centric Log Sources

Generate logs related to **network communication**.

**Examples of devices**
- Firewall
- Router
- IDS/IPS
- VPN Gateway

**Examples of logs**
- SSH connections
- FTP transfers
- Web traffic
- VPN access
- File sharing activity

---

## Problems Without SIEM

### 1. Numerous Log Sources

- Hundreds of devices
- Thousands of logs every second
- Difficult to check each device manually

### 2. No Centralization

Logs stay on their own devices.

Analysts must use:

- SSH
- RDP
- Remote Login

to access every machine separately.

This wastes investigation time.

### 3. Limited Context

A single log rarely tells the whole story.

Example:

- User logs in
- Opens a document
- Runs PowerShell
- Connects to external IP

Individually these seem normal.

When correlated together → Possible Data Exfiltration.

### 4. Limited Manual Analysis

Humans cannot manually analyze millions of logs.

Important attacks may be missed.

### 5. Different Log Formats

Windows, Linux, Firewalls, Web Servers all generate logs differently.

Analysts would have to understand every format.

---

## Why SIEM ?

**SIEM solves all these problems by:**

- Collecting logs
- Normalizing logs
- Correlating logs
- Detecting attacks
- Alerting analysts

## Features of SIEM

### 1. Centralized Log Collection

Collects logs from:

- Endpoints
- Servers
- Firewalls
- Routers
- Applications

Stores everything in one place.

No need to investigate every device separately.

### 2. Normalization of Logs

#### Parsing

Breaking raw logs into meaningful fields.

Example

Raw Log

```
User=John IP=192.168.1.5 Event=Login
```

Parsed Fields

- User → John
- IP → 192.168.1.5
- Event → Login

#### Normalization

Converts logs from different devices into one standard format.

Example

Windows Log

```
AccountName = John
```

Linux Log

```
user = John
```

Normalized

```
Username = John
```

This makes searching much easier.

### 3. Correlation of Logs

Combines multiple logs from different sources to identify attacks.

Example

Within 5 minutes:

- VPN login from unknown IP
- Access shared files
- PowerShell executed
- Outbound connection established

Each event alone is normal.

Together → Possible Compromised Account + Data Exfiltration

### 4. Real-Time Alerting

SIEM continuously compares logs against **Detection Rules**.

When a rule matches,

➡ Alert is generated.

SOC Analysts investigate the alert.

### 5. Dashboards & Reporting

SIEM displays summarized information through dashboards.

Examples:

- Alert Highlights
- Failed Login Attempts
- Events Ingested
- Triggered Rules
- Health Alerts
- Top Visited Domains
- System Notifications

Managers and analysts use dashboards for quick monitoring.

## Log Ingestion Methods

Log ingestion refers to the process of collecting, importing, and processing log data from various sources into a centralized system, such as a Security Information and Event Management (SIEM) solution. This allows organizations to analyze, monitor, and respond to security events and incidents effectively. Ingested logs can come from servers, applications, network devices, and more, providing a comprehensive view of the system's activity and security posture.
All these logs provide a wealth of information and can help identify security issues. Each SIEM solution has its own way of ingesting the logs. Some common methods used by these SIEM solutions are :

### 1. Agent / Forwarder

A lightweight software installed on endpoints.

> These SIEM solutions provide a lightweight tool called an agent (forwarder by Splunk) that gets installed on the Endpoint. It is configured to capture and send all the important logs to the SIEM server.

Examples

- Splunk Universal Forwarder
- Elastic Agent

Collects logs and sends them to SIEM.

### 2. Syslog

A standard protocol used mainly by Linux devices, routers, firewalls, switches.

Sends logs in real time to SIEM.

> Syslog is a widely used protocol to collect data from various systems like web servers, databases, etc., and send real-time data to the centralized destination.

### 3. Manual Upload

Analyst uploads offline log files directly into SIEM.

Useful for forensic investigations.

> Some SIEM solutions, like Splunk, ELK, etc., allow users to ingest offline data for quick analysis. Once the data is ingested, it is normalized and made available for analysis.

### 4. Port Forwarding

SIEM listens on a configured port.

Devices forward logs to that listening port.

> SIEM solutions can also be configured to listen on a certain port, and then the endpoints forward the data to the SIEM instance on the listening port.

## Detection Rules

SIEM detects attacks using Detection Rules.

A rule is simply a logical condition.

Example Rules

- 5 failed logins within 10 seconds
- Successful login after multiple failed attempts
- USB inserted
- Outbound traffic > 25 MB

When conditions are met,

➡ Alert is generated.

---

## Detection Rule Examples

### Example 1

Windows Event ID **104**

Meaning:

Event Logs Cleared

Rule

```
IF
Log Source = WinEventLog

AND

Event ID = 104

THEN

Generate Alert
```

Alert

```
Event Log Cleared
```

### Example 2

Attackers often execute

```
whoami
```

Windows Process Creation Event

```
Event ID = 4688
```

Rule

```
IF

Log Source = WinEventLog

AND

Event ID = 4688

AND

NewProcessName contains "whoami"

THEN

Generate Alert
```

Alert

```
WHOAMI Command Executed
```

## Alert Investigation Process

Once an alert is triggered, SOC Analysts investigate it.

### Step 1

Check events associated with the alert.

### Step 2

Review the detection rule.

### Step 3

Decide whether it is

- False Positive
- True Positive

### If False Positive

- Tune the rule
- Reduce future false alerts

### If True Positive

- Continue investigation
- Contact asset owner
- Confirm suspicious activity
- Isolate infected machine
- Block malicious IP
- Begin Incident Response
