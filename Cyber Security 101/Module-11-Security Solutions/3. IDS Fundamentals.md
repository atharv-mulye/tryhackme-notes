# IDS Fundamentals

## What is an IDS ?

IDS (Intrusion Detection System) is a security solution that monitors network or system activities to detect malicious or suspicious behavior.

Unlike a firewall :

- **Firewall** → Prevents unauthorized traffic.
- **IDS** → Detects malicious activity that has already entered the network.

> IDS only **detects and alerts**. It does **not block** the traffic.

## Firewall vs IDS

| Firewall | IDS |
|----------|-----|
| Prevents attacks | Detects attacks |
| Filters incoming/outgoing traffic | Monitors network/system activity |
| Blocks unauthorized traffic | Generates alerts |
| First line of defense | Detects threats after they bypass the firewall |

---

## Types of IDS

IDS can be classified based on:

1. Deployment Mode
2. Detection Mode

---

## 1. Deployment Modes

### Host Intrusion Detection System (HIDS)

Installed on an individual host (computer/server).

#### Monitors

- Files
- Processes
- Registry
- System Logs
- User Activity

#### Advantages

- Detailed host visibility
- Detects attacks on a specific machine

#### Disadvantages

- Must be installed on every host
- Difficult to manage in large networks
- Uses host resources

---

### Network Intrusion Detection System (NIDS)

Installed at strategic points in the network.

Monitors traffic for the **entire network**.

#### Monitors

- Network packets
- Connections
- Traffic patterns

#### Advantages

- Centralized monitoring
- Covers multiple devices
- Easier management

#### Disadvantages

- Cannot inspect activities occurring only inside a host

---

## HIDS vs NIDS

| HIDS | NIDS |
|------|------|
| Installed on individual hosts | Installed in the network |
| Monitors host activities | Monitors network traffic |
| Detailed host visibility | Centralized network visibility |
| Resource-intensive | Easier to manage |

---

## 2. Detection Modes

### Signature-Based IDS

Detects attacks using **known attack signatures (patterns)**.

#### How it Works

- Compares traffic with stored attack signatures.
- If a match is found → Alert generated.

#### Advantages

- Fast detection
- Low false positives
- Excellent for known attacks

#### Disadvantages

- Cannot detect Zero-Day attacks
- Requires frequent signature updates

> Signature-Based IDS: Many attacks occur every day. Each attack has its unique pattern, which is known as a signature. These signatures are preserved by the IDS in their databases so that if the same attack happens in the future, it gets detected by its signature and reported to the security administrators for action. The stronger the signature database of the IDS is, the more efficiently it will detect known threats. However, the signature-based IDS is unable to detect zero-day attacks. Zero-day attacks have no prior signatures (patterns) and are not saved inside the IDS databases. Therefore, the signature-based IDS can only detect the attacks that happened previously, and its signatures (patterns) are saved inside the database.

---

### Anomaly-Based IDS

Learns the **normal behavior (baseline)** of the network or system.

Detects anything that deviates from normal behavior.

#### Advantages

- Detects unknown attacks
- Detects Zero-Day attacks

#### Disadvantages

- High false positives
- Requires tuning

> This type of IDS first learns the normal behavior (baseline) of the network or system and performs detections if there is any deviation from the normal behavior. Anomaly-based IDS can also detect zero-day attacks because they don’t rely on available signatures for detection. They detect abnormalities inside the network or system by comparing the current state with the normal behavior (baseline). However, this type of IDS may generate a lot of false positives (marking benign activities as malicious) because the nature of most legitimate programs matches the malicious ones. Anomaly-based IDS would mark them malicious and believe anything behaving unusually is malicious. We can also reduce the false positives generated by anomaly-based IDS by fine-tuning it (manually defining the normal behavior in the IDS).

---

### Hybrid IDS

Combines:

- Signature-Based Detection
- Anomaly-Based Detection

#### Advantages

- Detects both known and unknown attacks
- Better overall detection capability

#### Disadvantages

- More complex
- Higher processing overhead

>  A hybrid IDS combines the detection methods of signature-based IDS and anomaly-based IDS to leverage the strengths of each approach. Some known threats may already have some signatures in the IDS database; in this case, the hybrid IDS would use the detection technique of the signature-based IDS. If it encounters a new threat, it can leverage the detection method of anomaly-based IDS.

---

## Comparison of Detection Modes

| Detection Mode | Detects Known Attacks | Detects Zero-Day Attacks | False Positives |
|---------------|----------------------|--------------------------|-----------------|
| Signature-Based | ✅ Yes | ❌ No | Low |
| Anomaly-Based | ✅ Yes | ✅ Yes | High |
| Hybrid | ✅ Yes | ✅ Yes | Medium |

> Signature-based IDS can detect threats quickly, while other IDS can have a high processing overhead. However, it is also essential to consider the IDS based on several different factors. Signature-based IDS can be a good option for covering a small threat surface. Anomaly-based IDS and hybrid IDS can help detect modern zero-day attacks, which are increasing daily and can cause massive damage to organizations.

## IDS Example: Snort

**Snort** is one of the most popular open-source IDS tools.

Developed in **1998**.

Uses:

- Signature-Based Detection
- Anomaly-Based Detection

---

## Snort Rules

Snort detects attacks using **rule files**.

These rule files contain:

- Known attack signatures
- Detection logic

Snort also allows:

- Custom rules
- Enable/Disable rules
- Modify detection behavior

---

## Modes of Snort

### 1. Packet Sniffer Mode

Captures and displays network packets.

No analysis is performed.

#### Use Case

- Network troubleshooting
- Traffic monitoring

---

### 2. Packet Logging Mode

Captures network traffic and saves it as **PCAP** files.

#### Use Case

- Digital Forensics
- Root Cause Analysis
- Incident Investigation

---

### 3. NIDS Mode (Network Intrusion Detection System)

The primary operating mode of Snort.

#### How it Works

- Monitors network traffic
- Applies detection rules
- Matches attack signatures
- Generates alerts

#### Use Case

- Real-time threat detection
- SOC monitoring
- Enterprise security

---

## Snort Modes Comparison

| Mode | Description | Use Case |
|------|-------------|----------|
| **Packet Sniffer Mode** | This mode reads and displays network packets without performing any analysis on them. The packet sniffer mode of Snort does not directly relate to IDS capabilities, but it can be helpful in network monitoring and troubleshooting. In some cases, system administrators might need to read the traffic flow without performing any detection to diagnose specific issues. In this case, they can utilize the packet sniffer mode of Snort. This mode allows you to display the network traffic on the console or even output it in a file. | The network team observes some network performance issues. To diagnose the issue, they need detailed insights into the network traffic. For this purpose, they can utilize Snort’s packet sniffer mode. |
| **Packet Logging Mode** | Snort performs detection on the network traffic in real-time and displays the detections as alerts on the console for the security administrators to take action. However, in some cases, the network traffic needs to be logged for later analysis. The packet logging mode of Snort allows you to log the network traffic as a PCAP (standard packet capture format) file. This includes all the network traffic and any detections from it. Forensic investigators can use these Snort log files to perform the root cause analysis of previous attacks. | The security team needs to initiate a forensic investigation of a network attack. They would need the traffic logs to perform the root cause analysis. The network traffic logged through Snort’s packet logging mode can help them. |
| **NIDS Mode** | Snort’s NIDS mode is the primary mode that monitors network traffic in real-time and applies its rule files to identify any match to the known attack patterns stored as signatures. If there is a match, it generates an alert. This mode provides the main functionality of an IDS solution. | The security team must proactively monitor their network or systems to detect potential threats. They can leverage Snort’s NIDS mode to achieve this. |

## Snort Usage

### Prerequisites

During Snort installation, you must specify:

- **Network Interface** (e.g., `eth0`, `ens33`, `lo`)
- **Network Range** (HOME_NET)

### Promiscuous Mode

Normally, Snort captures only traffic destined for the local host.

To monitor **all network traffic**, enable the network interface in **Promiscuous Mode**.

> **Promiscuous Mode:** Allows the network interface to capture **all packets** on the network segment, not just packets addressed to the host.


### Note : Where is Snort Installed?

Snort can be deployed in two ways.

#### 1. Host IDS (HIDS-like)

Snort is installed on the **same machine** that needs protection.

```text
Internet
    │
    ▼
+----------------+
|    PC (Snort)  |
+----------------+
```

It monitors only:

- Incoming traffic to that host
- Outgoing traffic from that host

Since Snort only needs to inspect traffic related to its own machine, **Promiscuous Mode is not required**.

#### 2. Network IDS (NIDS)

Snort is installed on a **dedicated monitoring machine (sensor)**.

```text
              Switch
        ┌──────┼──────┐
        │      │      │
      PC-1   PC-2   Server
               │
               ▼
        Snort Sensor
```

The Snort sensor is **not part of the communication**. Its job is to observe the traffic flowing between all devices on the network.

### Why is Promiscuous Mode Required?

Normally, a network interface accepts **only packets addressed to itself**.

Example:

```text
PC-1 ─────► Server

Snort Sensor
```

Without Promiscuous Mode, Snort **cannot see** the communication between PC-1 and the Server because those packets are not addressed to the Snort sensor.

With **Promiscuous Mode**, the network interface captures **all packets** that reach it, even if they are meant for other devices.

This allows Snort to inspect the entire network's traffic and detect malicious activities happening between other hosts.

The purpose of a **Network IDS (NIDS)** is to detect attacks happening **between devices on the network**, not just attacks targeting the Snort sensor.

#### Example

```text
Internet
    │
Firewall
    │
Switch
 ├── PC-A (Employee)
 ├── PC-B (Employee)
 ├── Server
 └── Snort Sensor
```

Suppose an attacker compromises **PC-A** and then:

1. Connects from **PC-A → Server** using SSH.
2. Copies confidential files from the Server.
3. Sends the stolen data to the Internet.

Notice that:

- The communication is between **PC-A and the Server**.
- The **Snort Sensor is not part of this communication**.

If Snort captured only packets addressed to itself, it would **see nothing** and completely miss the attack.

#### What Does Promiscuous Mode Do ?

Without Promiscuous Mode, Snort only sees traffic such as:

```text
Internet → Snort
Snort → Internet
```

With Promiscuous Mode enabled, Snort can also observe:

```text
PC-A → Server
PC-B → Server
Server → Internet
PC-A → PC-B
```

This allows Snort to detect attacks occurring anywhere on the monitored network, such as:

- Port Scanning
- SSH Brute Force Attacks
- Malware communicating with a Command & Control (C2) server
- Data Exfiltration
- Lateral Movement (one compromised host attacking another)
- Suspicious DNS Requests

Snort stores its configuration files, rule files, and supporting files in:

```text

```

>
> - `/etc/snort`
> - `/usr/local/etc/snort`

### Important Files

| File/Folder | Purpose |
|-------------|----------|
| `snort.lua` | Main configuration file (Snort 3) /  The key file for Snort is its configuration file snort.lua |
| `rules/` | Contains all detection rule files. |
| `local.rules` | Stores custom rules created by the analyst. |
| `snort.conf` | Main configuration file (older Snort versions). |

## Snort Rule Format

 There is a specific way of writing the rules. A sample rule would detect ICMP packets (usually used when you ping a host) coming from any IP address and port and reaching the home network (the network range is defined in Snort’s configuration file) to any port. Once such traffic is detected, it generates “Ping Detected” alerts.

## Rule Components

| Component | Description |
|-----------|-------------|
| **Action** | Action taken when the rule matches (e.g., `alert`, `log`, `drop`). |
| **Protocol** | Network protocol to inspect (ICMP, TCP, UDP, etc.). |
| **Source IP** | IP address where traffic originates (`any` means any IP). |
| **Source Port** | Source port (`any` means any port). |
| **->** | Direction operator (traffic flow from source to destination). |
| **Destination IP** | Target IP (`$HOME_NET` refers to the monitored network). |
| **Destination Port** | Destination port (`any` means any port). |
| **msg** | Alert message displayed when the rule triggers. |
| **sid** | Signature ID (unique identifier for every rule). |
| **rev** | Rule revision number. Incremented whenever the rule is modified. |

In short : 

- **Action:** This specifies which action to take when the rule triggers. In this case, we have the action to "alert" when the traffic matches this rule.
- **Protocol:** This refers to the protocol that matches this rule. In this case, we use the protocol "ICMP" when pinging a host.
- **Source IP:** This determines the IP originating from the traffic. Since we want to detect traffic from any source IP, we set this as "any".
- **Source port:** This determines the port from which the traffic originates. Since we want to detect traffic from any source port, we set this as "any".
- **Destination IP:** This specifies the destination IP to which the matching traffic comes; it generates the alert. In this case, we used "$HOME_NET". This is a variable, and we defined its value as our whole network’s range in Snort’s configuration file.
- **Destination port:** This specifies the port the traffic would reach. Since we want to detect traffic coming to any port, we set it to "any."
- **Rule metadata:** Every rule has some metadata. That is defined at the end of the rule in parentheses. The following are its components:
    - **Message (msg):** This describes the message displayed when the subject rule triggers. The message should indicate the type of activity detected. In this case, we used "Ping Detected".
    - **Signature ID (sid):** Every rule has a unique identifier that differentiates it from others. This identifier is called the signature ID (sid). In this case, we set the sid to "10001".
    - **Rule revision (rev):** This sets the rule's revision number. Every time the rule is modified, its revision number is incremented, which helps in tracking changes to any rule.

## Creating a Custom Rule

Open the custom rule file:

```bash
sudo nano /etc/snort/rules/local.rules
```

Add the following rule:

```snort
alert icmp any any -> 127.0.0.1 any (msg:"Loopback Ping Detected"; sid:10003; rev:1;)
```

## Testing the Rule

Start Snort:

```bash
sudo snort -q -l /var/log/snort -i lo -A alert_fast -c /etc/snort/snort.lua
```

### Parameters

| Option | Meaning |
|---------|---------|
| `-q` | Quiet mode (less console output). |
| `-l` | Log directory. |
| `-i` | Network interface to monitor. |
| `-A alert_fast` | Display alerts in fast format. |
| `-c` | Configuration file to use. |

## Running Snort on PCAP Files

Snort can analyze **historical network traffic** stored in **PCAP (Packet Capture)** files.

Useful for:

- Digital Forensics
- Incident Response
- Offline Packet Analysis

Run Snort on a PCAP file:

```bash
sudo snort -q -l /var/log/snort -r Task.pcap -A alert_fast -c /etc/snort/snort.lua
```

### Parameters

| Option | Meaning |
|---------|---------|
| `-r` | Read packets from a PCAP file instead of live traffic. |
| `Task.pcap` | Packet capture file to analyze. |
