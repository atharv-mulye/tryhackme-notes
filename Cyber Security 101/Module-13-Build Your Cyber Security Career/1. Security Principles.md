# Security Principles

## Introduction

Security means protecting systems, data, and services from unauthorized access, modification, or disruption.

- Perfect security does **not** exist.
- Every system has some level of risk.
- Security aims to make attacks more difficult, expensive, and time-consuming.
- The level of security depends on the type of attacker and the value of the asset being protected.

---

## CIA Triad

The **CIA Triad** is the foundation of information security.

### Confidentiality

Confidentiality ensures that only authorized users can access information.

#### Goal
- Prevent unauthorized access to sensitive data.

#### Examples
- Password protection
- Encryption
- Access control
- Multi-Factor Authentication (MFA)

---

### Integrity

Integrity ensures that data remains accurate and is not modified without permission.

#### Goal
- Prevent unauthorized changes.
- Detect if data has been altered.

#### Examples
- Hashing
- Digital signatures
- Checksums
- File integrity monitoring

---

### Availability

Availability ensures that systems and data are accessible whenever authorized users need them.

#### Goal
- Keep services running without interruption.

#### Examples
- Backups
- Redundant servers
- Load balancing
- Disaster recovery plans

---

### CIA Summary

| Principle | Purpose |
|-----------|---------|
| Confidentiality | Prevent unauthorized access |
| Integrity | Prevent unauthorized modification |
| Availability | Ensure systems remain accessible |

---

## Beyond CIA

### Authenticity

Authenticity verifies that data or a user is genuine and comes from the claimed source.

#### Examples
- Digital certificates
- Digital signatures
- User authentication

---

### Nonrepudiation

Nonrepudiation prevents someone from denying that they performed an action.

#### Examples
- Digital signatures
- Audit logs
- Signed transactions

---

## Parkerian Hexad

The Parkerian Hexad expands the CIA Triad into six security principles.

| Principle | Purpose |
|-----------|---------|
| Confidentiality | Protect secret information |
| Integrity | Keep data accurate |
| Availability | Keep systems accessible |
| Authenticity | Verify identity and source |
| Utility | Ensure data is usable |
| Possession | Maintain control over information |

### Utility

Data should be usable.

Example:
- Encrypted data without the decryption key is available but not useful.

---

### Possession

Possession means maintaining control over data.

Examples:
- Backup drive stolen
- Data encrypted by ransomware

---

## DAD Triad

The **DAD Triad** represents attacks against the CIA Triad.

| DAD | Opposite CIA Principle |
|-----|------------------------|
| Disclosure | Confidentiality |
| Alteration | Integrity |
| Destruction / Denial | Availability |

### Disclosure

Unauthorized exposure of confidential information.

Example:
- Data breach

> Disclosure is the opposite of confidentiality. In other words, disclosure of confidential data would be an attack on confidentiality.

---

### Alteration

Unauthorized modification of data.

Example:
- Changing medical records
- Editing bank transactions

> Alteration is the opposite of Integrity. For example, the integrity of a cheque is indispensable.

---

### Destruction / Denial

Making data or services unavailable.

Example:
- DDoS attack
- Deleting important files

> Destruction/Denial is the opposite of Availability.

## Security Models

Security models define rules for protecting information.

## Bell-LaPadula Model

**Focus:** Confidentiality

### Rules

- **1. Simple Security Property :** This property is referred to as “no read up”, it states that a subject at a lower security level cannot read an object at a higher security level. This rule prevents access to sensitive information above the authorized level.
- **2. Star Security Property :** This property is referred to as “no write down”, it states that a subject at a higher security level cannot write to an object at a lower security level. This rule prevents the disclosure of sensitive information to a subject of lower security level.
- **3. Discretionary-Security Property :** This property uses an access matrix to allow read and write operations. An example access matrix is shown in the table below and used in conjunction with the first two properties.

| Subjects	| Object A | Object B | 
|------|--------|---------|
| Subject 1	| Write	| No access |
| Subject 2	| Read/Write | Read |

The first two properties can be summarized as “write up, read down.” You can share confidential information with people of higher security clearance (write up), and you can receive confidential information from people with lower security clearance (read down).

There are certain limitations to the Bell-LaPadula model. For example, it was not designed to handle file-sharing.

> In Short
> #### No Read Up
> - Lower security levels cannot read higher classified data.
> - #### No Write Down
- Higher security levels cannot write to lower classified data.
- #### Easy to Remember
- > **Read Down, Write Up**
Purpose:
  - Prevent sensitive information from leaking to lower security levels.
---

## Biba Model

**Focus:** Integrity

### Rules

- **1. Simple Integrity Property :** This property is referred to as “no read down”, a higher integrity subject should not read from a lower integrity object.
- **2. Star Integrity Property :** This property is referred to as “no write up”, a lower integrity subject should not write to a higher integrity object.

> In Short
> ### No Read Down
> - High integrity users should not read low integrity data.

> ### No Write Up
> - Low integrity users cannot modify high integrity data.

> ### Easy to Remember

> **Read Up, Write Down**

Purpose:
- Prevent untrusted data from affecting trusted data.

---

## Clark-Wilson Model

**Focus:** Integrity

Uses controlled processes instead of allowing direct data modification.

### Components

#### CDI (Constrained Data Item)
Critical data whose integrity must be protected.

#### UDI (Unconstrained Data Item)
Input from users or external sources.

#### TP (Transformation Procedure)
Approved operations that modify data safely.

#### IVP (Integrity Verification Procedure)
Checks whether protected data remains valid.

## Defence in Depth

Defence in Depth means protecting a system using **multiple layers of security**.

If one layer fails, other layers continue protecting the system.

### Examples

- Firewall
- Antivirus
- MFA
- IDS/IPS
- Encryption
- Physical security
- Access control

## ISO/IEC 19249

This international standard describes secure system design principles.

## Architectural Principles

### 1. Domain Separation

Separate different components into independent security domains.

> Every set of related components is grouped as a single entity, components can be applications, data, or other resources. Each entity will have its own domain and be assigned a common set of security attributes. For example, consider the x86 processor privilege levels: the operating system kernel can run in ring 0 (the most privileged level). In contrast, user-mode applications can run in ring 3 (the least privileged level). Domain separation is included in the Goguen-Meseguer Model.

Example:
- Operating system kernel vs user applications

---

### 2. Layering

Build systems using multiple layers.

Each layer performs a specific function and adds security.

> When a system is structured into many abstract levels or layers, it becomes possible to impose security policies at different levels, moreover, it would be feasible to validate the operation. Let’s consider the OSI (Open Systems Interconnection) model with its seven layers in networking. Each layer in the OSI model provides specific services to the layer above it. This layering makes it possible to impose security policies and easily validate that the system is working as intended. Another example from the programming world is disk operations, a programmer usually uses the disk read and write functions provided by the chosen high-level programming language. The programming language hides the low-level system calls and presents them as more user-friendly methods. Layering relates to Defence in Depth.

---

### 3. Encapsulation

Hide internal implementation details and allow access only through approved methods.

> In object-oriented programming (OOP), we hide low-level implementations and prevent direct manipulation of the data in an object by providing specific methods for that purpose. For example, if you have a clock object, you would provide a method increment() instead of giving the user direct access to the seconds variable. The aim is to prevent invalid values for your variables. Similarly, in larger systems, you would use (or even design) a proper Application Programming Interface (API) that your application would use to access the database.

Example:
- APIs
- Object-oriented programming

---

### 4. Redundancy

Duplicate important components to improve availability and reliability.

> This principle ensures availability and integrity. There are many examples related to redundancy. Consider the case of a hardware server with two built-in power supplies: if one power supply fails, the system continues to function. Consider a RAID 5 configuration with three drives: if one drive fails, data remains available using the remaining two drives. Moreover, if data is improperly changed on one of the disks, it would be detected via the parity, ensuring the data’s integrity.

Examples:
- RAID
- Backup power supplies
- Multiple servers

---

### 5. Virtualization

Run multiple virtual systems on one physical machine.

> With the advent of cloud services, virtualization has become more common and popular. The concept of virtualization is sharing a single set of hardware among multiple operating systems. Virtualization provides sandboxing capabilities that improve security boundaries, secure detonation, and observance of malicious programs.

Benefits:
- Isolation
- Sandboxing
- Better security

## Design Principles

### 1. Least Privilege

Give users only the permissions needed to perform their tasks.

> You can also phrase it informally as “need-to basis” or “need-to-know basis” as you answer the question, “who can access what?” The principle of least privilege teaches that you should provide the least amount of permissions for someone to carry out their task and nothing more. For example, if a user needs to be able to view a document, you should give them read rights without write rights.

---

### 2. Attack Surface Minimization

Reduce the number of services, applications, and features that attackers can target.

> Every system has vulnerabilities that an attacker might use to compromise a system. Some vulnerabilities are known, while others are yet to be discovered. These vulnerabilities represent risks that we should aim to minimize. For example, in one of the steps to harden a Linux system, we would disable any service we don’t need.

Example:
- Disable unused services.

---

### 3. Centralized Parameter Validation

Validate all user input from one trusted location.

> Many threats are due to the system receiving input, especially from users. Invalid inputs can be used to exploit vulnerabilities in the system, such as denial of service and remote code execution. Therefore, parameter validation is a necessary step to ensure the correct system state. Considering the number of parameters a system handles, the validation of the parameters should be centralized within one library or system.

Purpose:
- Prevent invalid or malicious input.

---

### 4. Centralized General Security Services

Keep authentication, authorization, and other security services centralized.

> As a security principle, we should aim to centralize all security services. For example, we would create a centralized server for authentication. Of course, you might take proper measures to ensure availability and prevent creating a single point of failure.

---

### 5. Error and Exception Handling

Systems should fail securely without exposing sensitive information.

> Whenever we build a system, we should take into account that errors and exceptions do and will occur. For instance, in a shopping application, a customer might try to place an order for an out-of-stock item. A database might get overloaded and stop responding to a web application. This principle teaches that the systems should be designed to fail safe, for example, if a firewall crashes, it should block all traffic instead of allowing all traffic. Moreover, we should be careful that error messages don’t leak information that we consider confidential, such as dumping memory content that contains information related to other customers.

Example:
- Firewall blocks traffic if it crashes instead of allowing everything.

## Trust Models

### Trust but Verify

Trust the user or system, but continuously monitor and verify their actions.

> This principle teaches that we should always verify even when we trust an entity and its behaviour. An entity might be a user or a system. Verifying usually requires setting up proper logging mechanisms, verifying indicates going through the logs to ensure everything is normal. In reality, it is not feasible to verify everything, just think of the work it takes to review all the actions taken by a single entity, such as Internet pages browsed by a single user. This requires automated security mechanisms, such as proxy, intrusion detection, and intrusion prevention systems.

Examples:
- Logging
- Monitoring
- Intrusion Detection Systems (IDS)

---

### Zero Trust

Zero Trust assumes **no user or device is trusted by default**.

> This principle treats trust as a vulnerability, and consequently, it caters to insider-related threats. After considering trust as a vulnerability, zero trust tries to eliminate it. It is teaching indirectly, “never trust, always verify.” In other words, every entity is considered adversarial until proven otherwise. Zero trust does not grant trust to a device based on its location or ownership. This approach contrasts with older models that would trust internal networks or enterprise-owned devices. Authentication and authorization are required before accessing any resource. As a result, if any breach occurs, the damage would be more contained if a zero trust architecture had been implemented.

#### Principles

- Never trust
- Always verify
- Authenticate every request
- Authorize every access
- Continuously monitor activity

#### Benefits

- Reduces insider threats
- Limits damage after a compromise

#### Microsegmentation

Split a network into very small segments.

Every connection between segments requires authentication and authorization.

> Microsegmentation is one of the implementations used for Zero Trust. It refers to the design where a network segment can be as small as a single host. Moreover, communication between segments requires authentication, access control list checks, and other security requirements.

## Vulnerability, Threat and Risk

### Vulnerability

A weakness that could be exploited.

Example:
- Weak password
- Unpatched software

---

### Threat

Anything that could exploit a vulnerability.

Examples:
- Hacker
- Malware
- Insider attack

---

### Risk

The likelihood that a threat will successfully exploit a vulnerability and the impact it would cause.

Risk depends on:

- Probability of attack
- Business impact

---

### Difference

| Term | Meaning |
|------|---------|
| Vulnerability | Weakness |
| Threat | Potential danger |
| Risk | Chance and impact of exploitation |

---

## Shared Responsibility Model

Cloud security responsibilities are shared between the cloud provider and the customer.

### Cloud Provider

Responsible for:
- Physical security
- Hardware
- Networking
- Data center

### Customer

Responsible for:
- Accounts
- Passwords
- Permissions
- Data
- Application security

The exact responsibility depends on the cloud service model (IaaS, PaaS, SaaS).

## Key Takeaways

- CIA is the foundation of information security.
- DAD represents attacks against CIA.
- Authenticity verifies identity.
- Nonrepudiation prevents denial of actions.
- Bell-LaPadula protects confidentiality.
- Biba protects integrity.
- Clark-Wilson protects integrity using controlled processes.
- Defence in Depth uses multiple security layers.
- Least Privilege gives only necessary permissions.
- Zero Trust follows **"Never Trust, Always Verify."**
- A vulnerability is a weakness, a threat is a possible attack, and risk is the likelihood and impact of that attack.
