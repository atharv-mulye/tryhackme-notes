
## Introduction

Active Directory (AD) is a Microsoft service used to manage users, computers, and permissions in a Windows network from a central location.

Instead of setting up each computer separately, AD allows administrators to control everything from one place.

### Key Functions :
- Authentication : Verifies user identity 
- Authorization : Controls access to resources

> In simple terms : Active Directory knows who you are and what you can access.

---

## Why Active Directory is Needed ?

### Small Network Scenario

In a small setup (e.g, few users and computers) :
- User accounts are created on each machine
- Settings are configured manually
- Issues are handled individually

Easy to manage due to small size

### Large Network Scenario

In a large organization :
- Many users and computers exist
- Systems may be in different locations
- Managing each device manually becomes difficult

Problems :
- Time-consuming management  
- Inconsistent configurations  
- Difficult security enforcement

## Active Directory

### Overview

Active Directory Domain Services (AD DS) is the core part of Active Directory.

It acts like a central database that stores information about all objects in a network.

### Common Objects in AD :
- Users  
- Groups  
- Computers (Machines)  
- Printers  
- Shared resources
- many others

> In simple terms : AD DS keeps track of everything inside the network.

---

## Users

Users are one of the most important objects in Active Directory.

They are known as security principals, which means :
- They can log in (authenticate)
- They can be given permissions to access resources

### Types of Users

#### 1. Human Users
- Represent real people (employees, students, etc.)
- Used to log into systems and access resources  

#### 2. Service Accounts
- Used by applications or services (e.g., web servers, databases)
- Not meant for human login  
- Have limited permissions only for their task  

---

## Machines (Computer Objects)

Every computer that joins a domain gets a machine account in Active Directory.

Machines are also security principals.

### Key Points :
- Each machine has its own account  
- Accounts have limited permissions  
- Used mainly by the system itself  

### Important Features :
- Passwords are automatically changed  
- Passwords are very long and complex (~120 characters)  
- Not meant for manual login  

### Naming Rule :
- Machine accounts end with `$`

**Example :**
- Computer Name : `DC01`  
- Machine Account : `DC01$`  

---

## Security Groups

Security Groups are used to manage permissions efficiently.

Instead of assigning permissions to each user, you assign them to a group.

### Benefits :
- Easier management  
- Saves time  
- Consistent access control  

### Features :
- Can contain users  
- Can contain machines  
- Can contain other groups  

> Security Groups are also security principals

---

## Default Security Groups

Some important built-in groups in a domain :

| Group Name          | Description |
|--------------------|------------|
| Domain Admins      | Full control over the domain / Users of this group have administrative privileges over the entire domain. By default, they can administer any computer on the domain, including the DCs. |
| Server Operators   | Manage Domain Controllers (limited) / Users in this group can administer Domain Controllers. They cannot change any administrative group memberships.|
| Backup Operators   | Can access all files for backup / Users in this group are allowed to access any file, ignoring their permissions. They are used to perform backups of data on computers. |
| Account Operators  | Can create/modify user accounts / Users in this group can create or modify other accounts in the domain.|
| Domain Users       | All users in the domain / Includes all existing user accounts in the domain.|
| Domain Computers   | All computers in the domain / Includes all existing computers in the domain. |
| Domain Controllers | All domain controllers / Includes all existing DCs on the domain. |

## Group Policies 

### What are Group Policies ?
- Group Policy Objects (GPOs) are collections of settings used to control user and computer behavior.
- They help administrators enforce rules across a network.
- GPOs are applied to Organizational Units (OUs) in Active Directory.

---

### Why use GPOs ?
- To apply different rules to different departments.
- Improves security and standardization.
- Example :
  - IT → full control
  - Other departments → restricted access

### How GPOs Work
1. Create a GPO
2. Link it to an OU or domain
3. It applies to :
   - That OU
   - All sub-OUs (inheritance)

### Default GPOs
- Default Domain Policy : applies to entire domain
- Default Domain Controllers Policy : applies only to domain controllers
- These contain important baseline settings like passwords and security rules

## GPO distribution

GPOs are distributed to the network via a network share called SYSVOL, which is stored in the DC. All users in a domain should typically have access to this share over the network to sync their GPOs periodically. The SYSVOL share points by default to the C:\Windows\SYSVOL\sysvol\ directory on each of the DCs in our network.

Once a change has been made to any GPOs, it might take up to 2 hours for computers to catch up. If you want to force any particular computer to sync its GPOs immediately, you can always run the following command on the desired computer :

```
gpupdate /force
```

## Authentication Methods 

### Overview
- In a Windows domain, all user credentials are stored in the Domain Controller (DC).
- When a user logs into a service, the service contacts the DC to verify credentials.

---

## Authentication Protocols in Windows
There are two main protocols :

### 1. Kerberos (Default)
- Modern and secure authentication protocol
- Used in newer Windows domains
- Based on tickets

### 2. NetNTLM (Legacy)
- Older protocol kept for compatibility
- Uses challenge-response mechanism
- Less secure compared to Kerberos

---

## Kerberos Authentication

### What is Kerberos ?
- Kerberos is the default authentication protocol in modern Windows domains.
- It uses a ticket-based system instead of sending passwords repeatedly.
- A ticket acts like proof that the user is already verified.

### Key Idea
- User logs in once → gets a ticket 
- Users don’t send passwords repeatedly
- Instead, they use tickets as proof of identity 
- Uses that ticket to access multiple services  

### Key Component
- KDC (Key Distribution Center)
  - Runs on Domain Controller
  - Issues and manages tickets

---

## Kerberos Process

When Kerberos is used for authentication, the following process happens :

1. The user sends their username and a timestamp encrypted using a key derived from their password to the Key Distribution Center (KDC), a service usually installed on the Domain Controller in charge of creating Kerberos tickets on the network.

The KDC will create and send back a Ticket Granting Ticket (TGT), which will allow the user to request additional tickets to access specific services. The need for a ticket to get more tickets may sound a bit weird, but it allows users to request service tickets without passing their credentials every time they want to connect to a service. Along with the TGT, a Session Key is given to the user, which they will need to generate the following requests.

Notice the TGT is encrypted using the krbtgt account's password hash, and therefore the user can't access its contents. It is essential to know that the encrypted TGT includes a copy of the Session Key as part of its contents, and the KDC has no need to store the Session Key as it can recover a copy by decrypting the TGT if needed.

<img width="750" height="350" alt="image" src="https://github.com/user-attachments/assets/04471f21-7f44-43bd-924a-11dff61daef3" />

2. When a user wants to connect to a service on the network like a share, website or database, they will use their TGT to ask the KDC for a Ticket Granting Service (TGS). TGS are tickets that allow connection only to the specific service they were created for. To request a TGS, the user will send their username and a timestamp encrypted using the Session Key, along with the TGT and a Service Principal Name (SPN), which indicates the service and server name we intend to access.

As a result, the KDC will send us a TGS along with a Service Session Key, which we will need to authenticate to the service we want to access. The TGS is encrypted using a key derived from the Service Owner Hash. The Service Owner is the user or machine account that the service runs under. The TGS contains a copy of the Service Session Key on its encrypted contents so that the Service Owner can access it by decrypting the TGS.

<img width="750" height="350" alt="image" src="https://github.com/user-attachments/assets/920342cc-ef0d-42c5-91f4-bba57528e8c2" />

3. The TGS can then be sent to the desired service to authenticate and establish a connection. The service will use its configured account's password hash to decrypt the TGS and validate the Service Session Key.

<img width="750" height="350" alt="image" src="https://github.com/user-attachments/assets/5e9ce57d-18fa-49f2-b5f3-337d8788beb9" />

## Kerberos Authentication – Step by Step 

## Step 1 : User Login
- User enters credentials
- Client sends :
  - Username
  - Timestamp (encrypted with password-derived key)
- Sent to KDC (Domain Controller)

## Step 2 : KDC Issues TGT
- KDC verifies user
- Sends back :
  - TGT (Ticket Granting Ticket)**
  - Session Key

### Note :
- TGT is encrypted using krbtgt account
- User cannot read it

## Step 3 : Request Service Ticket (TGS)
- User wants to access a service
- Client sends to KDC :
  - TGT
  - Authenticator (timestamp encrypted with session key)
  - SPN (service name)

## Step 4 : KDC Issues TGS
- KDC validates request
- Sends back :
  - TGS (Service Ticket)
  - Service Session Key

### Note :
- TGS is encrypted with service account hash

## Step 5 : Access Service
- Client sends to service:
  - TGS
  - Authenticator

## Step 6 : Service Grants Access
- Service decrypts TGS
- Verifies session key
- If valid → access granted

## Final Flow
1. Login → get TGT  
2. Use TGT → get TGS  
3. Use TGS → access service  

---

## Advantages of Kerberos Authentication

### 1. No Password Transmission
- Password is never sent over the network
- Reduces risk of interception and theft

### 2. Ticket-Based Authentication
- Users authenticate once and reuse tickets
- Avoids repeated login requests

### 3. Efficient Authentication
- After getting TGT, no need to re-enter credentials
- Faster access to multiple services

### 4. Mutual Authentication
- Both user and service verify each other
- Prevents fake servers or impersonation

### 5. Strong Encryption
- Uses secure encryption methods
- Protects tickets and communication

### 6. Centralized Control
- Managed by Domain Controller (KDC)
- Easier to enforce security policies

### 7. Reduces Credential Exposure
- Credentials are not repeatedly used
- Minimizes attack surface

## NetNTLM Authentication Process :

<img width="600" height="450" alt="image" src="https://github.com/user-attachments/assets/033c5dfc-c03b-4a56-8c2f-91dc4269e120" />

1. The client sends an authentication request to the server they want to access.
2. The server generates a random number and sends it as a challenge to the client.
3. The client combines their NTLM password hash with the challenge (and other known data) to generate a response to the challenge and sends it back to the server for verification.
4. The server forwards the challenge and the response to the Domain Controller for verification.
5. The domain controller uses the challenge to recalculate the response and compares it to the original response sent by the client. If they both match, the client is authenticated; otherwise, access is denied. The authentication result is sent back to the server.
6. The server forwards the authentication result to the client.

> Note that the user's password (or hash) is never transmitted through the network for security.

> Note : The described process applies when using a domain account. If a local account is used, the server can verify the response to the challenge itself without requiring interaction with the domain controller since it has the password hash stored locally on its SAM.

---

## Important Note
- Password is never sent over network
- Only hash-based response is used

---

## Local vs Domain Authentication
- Domain Account
  - Server contacts Domain Controller
- Local Account
  - Server verifies locally using SAM database

---

## Limitations of NetNTLM
- Older and less secure
- Vulnerable to attacks (e.g., relay attacks)
- Should be avoided if possible

---

## Kerberos vs NetNTLM

| Feature            | Kerberos              | NetNTLM              |
|-------------------|----------------------|----------------------|
| Type              | Ticket-based         | Challenge-response   |
| Security          | High                 | Lower                |
| Default Usage     | Modern systems       | Legacy support       |
| Password Sharing  | Never sent           | Never sent           |
| Efficiency        | High (reusable tickets) | Lower (repeat auth) |

---

## Key Points
- Kerberos = secure, ticket-based authentication
- NetNTLM = older, challenge-response method
- Modern environments prefer Kerberos
- Both may exist in real-world networks

## Trees, Forests, and Trusts

### Why Multiple Domains ?
- A single domain works for small organizations
- As companies grow :
  - Different locations (countries)
  - Different rules/laws
  - Separate IT teams
- Managing everything in one domain becomes complex

---

## Trees in Active Directory

### What is a Tree ?
- A tree is a group of domains sharing the same namespace
- Structured in a parent-child hierarchy

## Benefits of Trees
- Each domain is managed independently
- Separate :
  - Users
  - Computers
  - Policies (GPOs)
- IT teams only control their own domain

## Admin Roles
- Domain Admins
  - Control only their domain
- Enterprise Admins
  - Control all domains in the tree

## Forests in Active Directory

### What is a Forest ?
- A forest is a collection of multiple trees
- Trees can have different namespaces

---

> The domains you manage can also be configured in different namespaces. Suppose your company continues growing and eventually acquires another company called MHT Inc. When both companies merge, you will probably have different domain trees for each company, each managed by its own IT department. The union of several trees with different namespaces into the same network is known as a forest.

## Benefits of Forests
- Allows merging of different organizations
- Maintains separation between domains
- Supports large-scale environments

## Trust Relationships

### What is a Trust ?
A trust allows users from one domain to access resources in another domain

Having multiple domains organised in trees and forest allows you to have a nice compartmentalised network in terms of management and resources. But at a certain point, a user at THM UK might need to access a shared file in one of MHT ASIA servers. For this to happen, domains arranged in trees and forests are joined together by trust relationships.

In simple terms, having a trust relationship between domains allows you to authorise a user from domain THM UK to access resources from domain MHT EU.

The simplest trust relationship that can be established is a one-way trust relationship. In a one-way trust, if Domain AAA trusts Domain BBB, this means that a user on BBB can be authorised to access resources on AAA :

<img width="600" height="300" alt="image" src="https://github.com/user-attachments/assets/89c0c3f3-6617-4dda-b03d-72fa23619f0b" />

The direction of the one-way trust relationship is contrary to that of the access direction.

Two-way trust relationships can also be made to allow both domains to mutually authorise users from the other. By default, joining several domains under a tree or a forest will form a two-way trust relationship.

It is important to note that having a trust relationship between domains doesn't automatically grant access to all resources on other domains. Once a trust relationship is established, you have the chance to authorise users across different domains, but it's up to you what is actually authorised or not.


---

## Important Concept
- Trust ≠ Automatic Access  
- Even with trust :
  - You must manually allow permissions

---

## Key Idea
- Trees : organize domains  
- Forests : combine organizations  
- Trusts : allow communication between them
