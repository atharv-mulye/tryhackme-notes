# CAPA: The Basics

## What is CAPA ?

CAPA (Common Analysis Platform for Artifacts) is an open-source static malware analysis tool developed by FireEye Mandiant.

It analyzes executable files and automatically identifies their capabilities using a large set of predefined rules.

Instead of reverse engineering the entire binary manually, CAPA quickly tells you what the program is capable of doing.

---

## Static vs Dynamic Analysis

### Static Analysis
- Examines a file **without executing it**.
- Safer because the malware never runs.
- Used by CAPA.

### Dynamic Analysis
- Executes the file in an isolated environment (sandbox).
- Observes the malware's actual behavior during execution.

---

## Files Supported by CAPA

- Portable Executables (PE): Windows executable files (.exe, .dll) that contain programs or libraries.
- ELF binaries: Linux/Unix executable files used to run programs and shared libraries.
- .NET modules: Applications or libraries compiled for the Microsoft .NET runtime (CLR), such as .exe and .dll files.
- Shellcode: Small machine-code payloads designed to execute specific actions, often used in exploits.
- Sandbox reports: Logs generated by sandbox environments that record a program's behavior during execution.

---

## What Can CAPA Detect ?

CAPA identifies capabilities such as:

- Network communication
- File creation/modification
- Registry operations
- Process injection
- Process creation
- Persistence mechanisms
- Encryption
- Command execution
- Anti-analysis techniques
- Many other malicious behaviors

---

## Why Use CAPA ?

- Fast static malware analysis
- Does not execute suspicious files
- Automates years of reverse engineering knowledge
- Helps analysts quickly understand malware functionality
- Useful for malware analysis, threat hunting, and incident response

> The beauty of CAPA is that it encapsulates years of reverse engineering knowledge into an automated tool, making it accessible even to those who may not be experts in reverse engineering. This can be incredibly useful for analysts and security professionals, allowing them to quickly understand potentially malicious software's functionality without manually reverse engineering the code.
> CAPA answers the question: "What is this executable capable of doing?" without running it.

## Common Options

| Option | Purpose | Example |
|--------|---------|---------|
| `-h` | Display help and available options | `capa -h` |
| `-v` | Show verbose results | `capa.exe .\cryptbot.bin -v` |
| `-vv` | Show very detailed (very verbose) results | `capa.exe .\cryptbot.bin -vv` |

> Higher verbosity provides more analysis details but increases processing time.

## Reading a Saved Result

Instead of analyzing the binary again, we can view a previously saved report:

```powershell
Get-Content .\cryptbot.txt
```

This displays the same CAPA analysis output without rerunning the scan.

---

## CAPA Output Sections

- File Information — Hashes (MD5, SHA1, SHA256), OS, architecture, file format, analysis type.
- MITRE ATT&CK Mapping — Maps detected capabilities to ATT&CK tactics and techniques.
- MAEC Category — Classifies the malware's overall behavior.
- MBC (Malware Behavior Catalog) — Lists malware behaviors (e.g., HTTP communication, process creation, file operations).
- Capabilities — Human-readable list of what the executable can do (networking, persistence, anti-VM, PowerShell, file operations, etc.).

> CAPA does not determine whether a file is malicious, it reports the capabilities it discovers.

### 2. MITRE ATT&CK

MITRE ATT&CK is a knowledge base that organizes attacker behaviors into standard categories.
CAPA maps the detected capabilities to these behaviors.

> The MITRE ATT&CK (Adversarial Tactics, Techniques, and Common Knowledge) framework is a comprehensive global knowledge repository that meticulously documents the tactics and techniques employed by threat actors at every stage of a cyber-attack. It functions as a strategic playbook, providing detailed insights into attackers' methods, from gaining initial access to maintaining a presence, escalating privileges, evading defenses, moving laterally within a network, and much more.

### 3. MAEC (Malware Attribute Enumeration and Characterization)

MAEC is a standard used to classify malware based on its overall behavior.

Common values:

| MAEC Value | Meaning |
|------------|---------|
| Launcher | Starts or launches malicious actions (e.g., runs payloads, creates persistence, connects to C2). |
| Downloader | Downloads additional files or payloads from the Internet and executes them. |

> Malware Attribute Enumeration and Characterization is a specialized language designed to encode and communicate complex details concerning malware. It contains an extensive range of attributes, including behaviours, artefacts, and interconnections among various instances of malware. This language functions as a standardized system for tracking and analyzing the complicated complexities of malware.

Example:

```terminal
┌─────────────────────────────┬────────────────────────────────────────────────────────────────────┐
│ MAEC Category               │ MAEC Value                                                         │
├─────────────────────────────┼────────────────────────────────────────────────────────────────────┤
│ malware-category            │ launcher                                                           │
└─────────────────────────────┴────────────────────────────────────────────────────────────────────┘
```

This means the binary mainly acts as a launcher rather than performing all malicious actions itself.

| MAEC Value | Description |
|------------|-------------|
| Launcher | Exhibits behaviors that trigger specific actions similar to malware behavior. |
| Downloader | Exhibits behaviors where it downloads and executes other files, commonly seen in more complex malware. |

When CAPA tags a file with a “launcher” MAEC value, it indicates that the file demonstrates behaviour similar to but not limited to:
- Dropping additional payloads
- Activating persistence mechanisms
- Connecting to command-and-control (C2) servers
- Executing specific functions

Additionally, when CAPA tags a file with a “Downloader” MAEC value, it indicates that the file demonstrates behaviour similar but not limited to:
- Fetching additional payloads or resources from the internet
- pulling in updates
- executing secondary stages
- retrieving configuration files

## What is MBC?

MBC (Malware Behavior Catalog) is a standardized framework that describes what a malware sample is capable of doing.

Unlike MITRE ATT&CK (which focuses on attacker techniques), MBC focuses on malware behaviors.

CAPA maps detected capabilities to MBC categories to make malware behavior easier to understand.

---

## MBC Format

| Format | Sample | Explanation |
|--------|--------|-------------|
| OBJECTIVE::Behavior::Method [Identifier] | `ANTI-STATIC ANALYSIS::Executable Code Obfuscation::Argument Obfuscation [B0032.020]` | `ANTI-STATIC ANALYSIS` = Objective<br>`Executable Code Obfuscation` = Behavior<br>`Argument Obfuscation` = Method<br>`B0032.020` = Identifier |
| OBJECTIVE::Behavior [Identifier] | `COMMUNICATION::HTTP Communication [C0002]` | `COMMUNICATION` = Objective<br>`HTTP Communication` = Behavior<br>`C0002` = Identifier |

> The first format contains an additional **Method** (similar to a sub-technique).

---

## Objectives

Objectives describe the overall goal of the malware.

| Objective | Purpose |
|-----------|---------|
| Anti-Behavioral Analysis | Malware attempts to avoid detection by hindering behavioural analysis using tools like sandboxes or debuggers / Evades sandboxes/debuggers |
| Anti-Static Analysis | Malware attempts to obstruct or add complexity to static analysis, making it more challenging for security professionals to identify and understand its malicious behaviours and intentions / Makes static analysis difficult through obfuscation. |
| Collection | Malware focuses on identifying and gathering information from the targeted machine or network / Collects information from the victim. |
| Command and Control | Malware typically establishes communication with compromised systems through various methods such as command and control servers, peer-to-peer networks, or other means. This communication allows the malware to control the compromised systems, enabling the attackers to execute commands, exfiltrate data, or carry out other malicious activities / Communicates with attacker-controlled servers. |
| Credential Access | The primary aim of malware is to steal account credentials, such as usernames and passwords / Steals usernames, passwords, or credentials. |
| Defense Evasion | The malware aims to bypass and circumvent the various detection and security mechanisms present within the system to avoid being detected or mitigated / Avoids detection by security tools. |
| Discovery | Malware Seeks to collect detailed information about the configuration and setup of the system or network environment, including hardware, software, and network infrastructure / Gathers system or network information. |
| Execution | Malware is designed to execute unauthorized commands or code on a targeted computer system without the user’s consent. This can include a wide range of harmful activities, such as stealing personal information, damaging files, or gaining unauthorized access to the system / Executes malicious commands or code. |
| Exfiltration | Malware is designed to infiltrate computer systems or networks to steal and extract sensitive data. This can include personal information, financial details, and any other valuable data stored on the targeted system or network / Steals and sends data outside the network. |
| Impact | Malware aims to manipulate, disrupt, or damage computer systems and data. It can enter computers through infected emails, compromised websites, and other deceptive means, leading to financial loss, privacy breaches, and system instability / Damages or disrupts systems. |
| Lateral Movement | Malware seeks to spread through the network, either actively through machine access or passively, such as via malicious emails / Spreads to other systems. |
| Persistence | Malware is intentionally developed with the capability to remain undetected and operational on a computer system for an extended period / Maintains long-term access. |
| Privilege Escalation | Malware seeks to infiltrate a computer system or network to gain elevated permissions or control. Once inside the target environment, malware can seek to escalate its privileges, access sensitive information, or take control of system resources for malicious purposes / Gains higher privileges. |

## Micro-Objectives

Micro-objectives group common low-level actions that malware performs.

| Micro-Objective | Description |
|----------------|-------------|
| PROCESS | exhibiting behaviours related to processes such as but not limited to Creating Process, Setting Thread Context, Terminating Process, and Checking Mutex / Process-related actions (create, terminate, inject). |
| MEMORY | exhibiting behaviours such as, but not limited to, Allocating Memory, Changing Memory Protection, and Freeing Memory / Memory operations (allocate, protect, free). |
| COMMUNICATION | exhibiting behaviours such as (not limited to (DNS, FTP, HTTP, ICMP, SMTP) network traffic / Network communication (HTTP, DNS, FTP, SMTP, etc.). |
| DATA | exhibiting behaviours such as but not limited to Checking strings, compressing, decoding and encoding dat / Data operations (check, encode, decode, compress). |

| Behavior | Method | ID | Meaning |
|----------|--------|----|---------|

## What is a Namespace ?

A namespace groups CAPA detection rules based on their purpose.

It helps organize related capabilities, making the analysis output easier to understand.

## Namespace Format

| Format | Sample | Explanation |
|--------|--------|-------------|
| Capability (Rule Name) :: TLN / Namespace | `reference anti-VM strings :: anti-analysis/anti-vm/vm-detection` | `reference anti-VM strings` = Capability (Rule Name)<br>`anti-analysis` = Top-Level Namespace (TLN)<br>`anti-vm/vm-detection` = Namespace |

## Common Top-Level Namespaces (TLN)

| TLN | Purpose |
|-----|---------|
| anti-analysis | contains a set of rules specifically designed to detect behaviours exhibited by malware to evade analysis. These behaviours include obfuscation, packing, and anti-debugging techniques / Detects VM detection, obfuscation, anti-debugging, etc. |
| collection | contains a set of data-related rules that malware may enumerate and collect for exfiltration or other purposes. Think of it as the “data-gathering” aspect of malware behaviour / Detects data collection behaviors. |
| communication | contains a set of rules that pertain to different communication behaviours demonstrated by malware. This encompasses how malware interacts with networks, including data transmission and reception, command and control communications, and other network-related behaviours / Detects network communication. |
| compiler | contains a set of rules and configurations for recognizing specific build environments or compilers employed in generating executables. These namespaces essentially serve as the unique “signature” that identifies the compilation process of a program / Identifies compiler/build environment. |
| data-manipulation | contains a set of rules that govern the behaviours involved in altering data within executable files. This aspect can be considered the “data transformation” component of malware behaviour, encompassing actions such as String Encryption and Data Encoding / Detects encoding, encryption, and data transformation. |
| executable | contains a set of rules pertaining to the attributes in executable files. These attributes include PE sections or debug info associated with the executable / Detects PE sections and executable attributes. |
| host-interaction | contains a set of rules related to behaviors involving interactions with the host system. This encompasses how malware interacts with its environment. Specifically, the rules in this namespace may capture behaviors related to reading, writing, or modifying files on disk, including creating, deleting, or modifying files and directories. / Detects interactions with files, directories, and processes. |
| impact | contains a set of rules related to the potential consequences or effects of a program’s behavior. Think of it as the aspect that focuses on the possible harm that this malware can cause. It may include behaviors related to establishing remote access, data exfiltration, destruction, or modification. / Detects behaviors that may damage or affect the victim. |
| internal | Rules contained within the system are not intended for direct use by analysts or for reporting. Instead, these rules are meant for internal purposes within the CAPA tool, serving as the behind-the-scenes aspect of rule development and execution. | 
| lib | building blocks to create other rules | 
| linking | contains rules to identify behaviors involving linking or dynamically loading external code or libraries during program execution. This is its primary function and is crucial for the program’s security. Understanding linking behavior is essential for several reasons. Malware often depends on external libraries or components (such as OpenSSL, Zlib, or other third-party libraries) to carry out specific tasks. Detecting these dependencies helps analysts understand the malware’s capabilities. External libraries also introduce an additional attack surface. If a vulnerability exists in a linked library, it can be exploited by the malware or defenders during analysis / Detects dynamic loading of libraries or external code. |
| load-code | contains a set of rules and regulations related to the behaviors associated with dynamically loading or executing code during program execution. This concept can be equated to the “runtime code injection” aspect of malware behavior, which involves unauthorized code introduction during a program’s execution / Detects runtime code loading or execution. |
| malware-family | contains a set of rules related to behaviors that are linked to particular malware families or groups. It serves as a way to identify the distinct characteristics or “signatures” associated with known malware families, allowing for more accurate detection and classification of potential threats / Detects known malware family signatures. |
| nursery | this is a staging ground that contains rules for those who are not quite polished | 
| persistence | contains rules related to behaviors associated with maintaining access or persistence within a compromised system. This namespace is essentially focused on understanding how malware can establish and maintain a presence within a compromised environment, allowing it to persist and carry out malicious activities over an extended period / Detects techniques used to maintain access. |
| runtime | contains a set of rules that seek to identify the language or platform on which the program runs / Detects runtime language or platform. |
| targeting	| contains a set of rules related to behaviors exhibited by programs that interact with ATMs. |

## Dissecting CAPA Results Part 4: Capability

## What is a Capability?

A **Capability** is a behavior or action that CAPA detects in a binary.

It tells us **what the program can do**, not necessarily what it is currently doing.

CAPA detects these capabilities using **YAML (.yml) rules**.

### How CAPA Finds a Capability

When CAPA scans a binary, it:

1. Checks the binary against thousands of detection rules.
2. If a rule matches, CAPA reports that behavior as a **Capability**.
3. It also shows the **Namespace** where that rule belongs.

---

## Example 1

```text
Capability:
reference anti-VM strings

Namespace:
anti-analysis/anti-vm/vm-detection

Rule:
reference-anti-vm-strings.yml
```

### Interpretation

- CAPA found the rule `reference-anti-vm-strings.yml`.
- This means the binary contains strings related to VMware or VirtualBox.
- Malware often checks if it is running inside a Virtual Machine (VM) to avoid analysis.

**Conclusion:**

> The binary can detect virtual machine environments.

---

## Example 2

```text
Capability:
schedule task via schtasks

Namespace:
persistence/scheduled-tasks

Rule:
schedule-task-via-schtasks.yml
```

### Interpretation

- CAPA detected code that creates Windows Scheduled Tasks.
- Malware commonly uses scheduled tasks to start automatically after reboot.

**Conclusion:**

> The binary can maintain persistence using Windows Scheduled Tasks.

---

## Capability and Rule Names

The capability name is usually the same as the rule filename.

Example:

```text
Capability
reference Base64 string

↓

Rule
reference-base64-string.yml
```

The only difference is:

- Spaces (` `) become dashes (`-`)
- `.yml` is added.

---

## Example Output

```text
Capability:
reference Base64 string

Namespace:
data-manipulation/encoding/base64
```

### Interpretation

| Label | Meaning |
|--------|---------|
| Capability | The binary references Base64 strings. |
| Top-Level Namespace | `data-manipulation` → Related to data transformation. |
| Namespace | `encoding/base64` → Related to Base64 encoding/decoding. |
| Rule Matched | `reference-base64-string.yml` |

**Conclusion:**

> The binary is capable of using Base64 encoding.

---

## Exception

Most capabilities are stored inside their matching namespace.

However, some unfinished or experimental rules are stored under the **`nursery`** namespace until they are fully developed.

---

## Key Points

- A **Capability** tells what a binary **can do**.
- CAPA detects capabilities using **YAML (.yml) rules**.
- Every capability belongs to a **Namespace**.
- The capability name is usually the same as the matched **rule name**.
- Reading capabilities helps quickly understand a binary without manually reverse engineering it.

## CAPA Web Explorer & Very Verbose Mode

## Why use `-vv`?

The normal CAPA output tells us **what capabilities were detected**.

The `-vv` (**Very Verbose**) option tells us:

- **Why** a capability was detected.
- **Which rule matched.**
- **Which strings, APIs, or conditions triggered the rule.**

---

## Common CAPA Options

| Option | Purpose |
|--------|---------|
| `-v` | Shows more detailed output. |
| `-vv` | Shows the complete rule matching process (Very Verbose). |
| `-j` | Saves the output in JSON format. |

Example:

```bash
capa -vv sample.exe
```

Generate JSON for Web Explorer:

```bash
capa -j -vv sample.exe > output.json
```

---

# CAPA Web Explorer

Reading thousands of lines of `-vv` output in a terminal is difficult.

Instead, CAPA provides **Web Explorer**, which displays the results in an easy-to-read interface.

### Steps

1. Run CAPA with `-j -vv`
2. Generate a JSON file.
3. Open **CAPA Web Explorer**.
4. Upload the JSON file.
5. Explore matched capabilities and rules.

---

# What does Web Explorer show?

For every detected capability, it shows:

- Capability name
- Namespace
- Rule (.yml)
- Exact conditions that matched
- Strings, APIs, or instructions responsible for the detection

This helps explain **why CAPA reported a capability**.

---

# Example 1

Capability:

```text
reference anti-VM strings targeting VMware
```

Rule:

```text
reference-anti-vm-strings-targeting-vmware.yml
```

Matched feature:

```yaml
string: /VMWare/i
```

### Interpretation

CAPA found the string **"VMWare"** inside the binary.

This indicates the program may check whether it is running inside a VMware virtual machine.

---

# Example 2

Capability:

```text
schedule task via schtasks
```

Rule:

```text
schedule-task-via-schtasks.yml
```

Matched features:

```yaml
string: /schtasks/i
string: /\/create/i
```

### Interpretation

CAPA found the strings:

- `schtasks`
- `/create`

This suggests the binary may create a Windows Scheduled Task to maintain persistence.

---

# Rule Matching

A CAPA rule contains conditions that must match before a capability is reported.

Example:

```yaml
features:
  - string: /VMWare/i
```

If the binary contains this string, CAPA marks the rule as matched.

---

# Global Search

CAPA Web Explorer also provides a **Global Search** feature.

It lets you quickly search for:

- Capabilities
- APIs
- Strings
- Namespaces
- Rules

This makes analyzing large reports much easier than reading thousands of lines manually.

---

## Key Points

- `-vv` explains **why** CAPA detected a capability.
- `-j` exports results as JSON.
- CAPA Web Explorer provides an easier way to analyze results.
- Every capability is matched because a rule's conditions were satisfied.
- CAPA can detect strings, APIs, and other patterns defined inside its YAML rules.
