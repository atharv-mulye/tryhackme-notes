# Passive Reconnaissance

## Introduction

**Passive reconnaissance** is the process of gathering information about a target from **publicly available sources without directly interacting with the target's infrastructure**.

It is commonly used during:

* Penetration testing
* Bug bounty hunting
* Threat intelligence
* Security assessments

### Passive vs Active Reconnaissance

| Type                       | Description                                                           | Detection Risk |
| -------------------------- | --------------------------------------------------------------------- | -------------- |
| **Passive Reconnaissance** | Collect information from public sources without contacting the target | Low            |
| **Active Reconnaissance**  | Directly interact with the target's systems to discover information   | Higher         |

### Common Passive Reconnaissance Sources

<pre>
Public Information
       ↓
DNS Records
WHOIS Data
Certificate Transparency Logs
Search Engines
Device Census Platforms
       ↓
Target Intelligence
</pre>

Common sources include:

* **DNS** - domains, subdomains, mail servers, name servers
* **WHOIS** - domain registration and ownership information
* **Certificate Transparency (CT) Logs** - certificates and potentially undiscovered subdomains
* **Search Engines** - indexed websites, documents, usernames, and exposed information
* **Device Census Platforms** - publicly observable internet-facing services and systems

### Why Passive Reconnaissance Matters

Passive reconnaissance allows an attacker or security tester to build a picture of the target **before attempting direct interaction**.

It can reveal:

* Domains and subdomains
* IP addresses and network ranges
* Technology and infrastructure details
* Email addresses and usernames
* Publicly exposed services
* Organizational relationships
* Potential attack surface

The major advantage is that much of this information can be collected **without generating traffic to the target**, making passive reconnaissance difficult to detect.

### Key Takeaways

* Passive reconnaissance gathers intelligence **without directly contacting the target**.
* It has significantly lower detection risk than active reconnaissance.
* Publicly available information can reveal a surprisingly large attack surface.
* DNS, WHOIS, CT logs, search engines, and internet-wide scanning platforms are valuable sources.
* Passive recon should generally be performed **before active reconnaissance** to improve efficiency and reduce unnecessary interaction with the target.

## Passive vs Active Reconnaissance

Before computer networks existed, Sun Tzu wrote in The Art of War: "If you know the enemy and know yourself, your victory will not stand in doubt."

**Reconnaissance (recon)** is the preliminary process of gathering information about a target before attempting further actions.

Recon is commonly divided into :

<pre>
Reconnaissance
      │
      ├── Passive Reconnaissance
      │
      └── Active Reconnaissance
</pre>

The key difference is whether the tester **directly interacts with the target**.

---

## Passive Reconnaissance

Passive reconnaissance gathers information from **publicly available sources without directly interacting with the target**.

No packets are intentionally sent to the target's infrastructure, making it significantly harder for the target to detect.

> Passive reconnaissance relies exclusively on publicly available information. No packets are sent to the target and no direct interaction occurs. It is analogous to observing the target territory from a safe distance using binoculars, without ever stepping onto their land.

### Common Passive Recon Activities

| Activity                      | Information Obtained                                          |
| ----------------------------- | ------------------------------------------------------------- |
| Querying public DNS records from open resolvers (A, MX, TXT, etc.) | Domains, IPs, mail servers, TXT records                       |
| Searching certificate transparency logs (e.g., crt.sh) for subdomains and issued certificates | Subdomains and issued certificates                            |
| Reviewing job postings on LinkedIn or company career pages for tech stack hints   | Technologies, infrastructure, software used                   |
| Reading public news, press releases, or leaked documents on paste sites   | Organizational and technical information                      |
| Checking exposed devices via search engines like Shodan or Censys | Publicly exposed devices and services                         |
| Scanning public GitHub repositories for hardcoded credentials or configuration files | Source code, configuration files, potentially exposed secrets |

### Example

<pre>
Target Organization
       ↓
Public Sources
       ↓
DNS / CT Logs / Search Engines / GitHub / Shodan
       ↓
Collected Intelligence
       ↓
Potential Attack Surface
</pre>

The tester observes information that is already publicly accessible rather than probing the target directly.

---

## Active Reconnaissance

Active reconnaissance involves **direct interaction with the target or someone associated with the target**.

Because the target can observe or log these interactions, active recon carries a higher detection risk.

> Active reconnaissance requires direct engagement with the target. Your probes can be logged, detected, or blocked. It is analogous to walking up to the doors and windows to test locks, cameras, and alarms.

### Common Active Recon Activities

| Activity                | Example                                   |
| ----------------------- | ----------------------------------------- |
| Host discovery          | ICMP ping, ARP requests                   |
| Port scanning           | Nmap, Masscan                             |
| Service enumeration     | Banner and service probing                |
| Web enumeration         | Directory brute-forcing, endpoint fuzzing |
| API interaction         | Testing or enumerating API endpoints      |
| Social engineering      | Phishing, vishing, pretexting             |
| Physical reconnaissance | Tailgating or approaching employees       |

### Example

<pre>
Target
  ↓
Direct Interaction
  ↓
Packets / Requests / Human Contact
  ↓
Target Logs or Detects Activity
</pre>

---

## Passive vs Active Reconnaissance

| Feature                         | Passive Recon                                   | Active Recon                                         |
| ------------------------------- | ----------------------------------------------- | ---------------------------------------------------- |
| Target interaction              | None                                            | Direct                                               |
| Detection risk                  | Low                                             | Higher                                               |
| Traffic generated toward target | No intentional direct traffic                   | Yes                                                  |
| Typical sources                 | DNS, CT logs, GitHub, search engines, Shodan    | Nmap, ping, web requests, fuzzing                    |
| Main advantage                  | Stealth                                         | More detailed and accurate information               |
| Main risk                       | Incomplete information                          | Detection and possible blocking                      |
| Authorization concerns          | Generally lower, but data-use rules still apply | Requires explicit authorization for security testing |

---

## Important Distinction

**Direct interaction with a person affiliated with the target is also active reconnaissance.**

For example, asking an employee about their organization's technology stack involves direct engagement with the target organization, even though no network packets are sent.

<pre>
No Network Traffic ≠ Automatically Passive

Human Interaction with Target
            ↓
      Active Recon
</pre>

---

## Why Start with Passive Recon ?

A common reconnaissance approach is:

<pre>
Passive Recon
      ↓
Build Initial Target Profile
      ↓
Identify Potential Attack Surface
      ↓
Active Recon
      ↓
Validate and Expand Findings
</pre>

Passive reconnaissance helps reduce unnecessary interaction with the target while providing useful context for later testing.

---

## Defender Perspective

Defenders should also understand their organization's **passive footprint** - the information an attacker can discover without touching the internal network.

Organizations can monitor sources such as:

* Shodan and Censys
* Certificate Transparency logs
* Public repositories
* Search engines
* OSINT monitoring platforms

Reducing unnecessary public exposure can make reconnaissance more difficult for attackers.

### Key Takeaways

* **Passive recon** gathers information without directly interacting with the target.
* **Active recon** involves direct interaction and is more detectable.
* Passive recon commonly uses DNS, CT logs, search engines, GitHub, Shodan, and Censys.
* Active recon includes host discovery, port scanning, enumeration, fuzzing, and social engineering.
* Directly engaging a target employee can also constitute active reconnaissance.
* In authorized security testing, passive recon is often performed first to understand the attack surface before active testing.
* Defenders should monitor their own public footprint and minimize unnecessary exposure.

## WHOIS

**WHOIS** is a query/response protocol historically used to retrieve domain registration information. Traditional WHOIS servers operate over **TCP port 43**.

WHOIS data is maintained by domain registrars and may reveal useful information about a domain.

> **Note:** Traditional WHOIS has largely been replaced by **RDAP** for modern gTLD registration data.

### Information Available Through WHOIS

| Information         | Purpose / Recon Value                                              |
| ------------------- | ------------------------------------------------------------------ |
| **Registrar**       | Identifies the company managing the domain registration            |
| **Registrant**      | May reveal owner or organization, but is usually privacy-protected |
| **Creation Date**   | Shows when the domain was registered                               |
| **Updated Date**    | Shows when registration information last changed                   |
| **Expiration Date** | Shows the domain renewal deadline                                  |
| **Name Servers**    | Identifies authoritative DNS infrastructure                        |
| **Status Codes**    | Shows domain state and transfer restrictions                       |
| **Abuse Contacts**  | Contact information for reporting domain abuse                     |

Due to privacy regulations such as **GDPR** and the widespread use of privacy services, personal registrant information is often redacted.

For reconnaissance, useful information can still include:

* Domain age
* Registrar
* Registration and modification dates
* Name servers
* Domain status
* Historical registration changes

> Full personal details are now rare due to privacy laws (GDPR, CCPA) and widespread use of privacy proxies. In practice, attackers focus on dates (for estimating age or timing social engineering around renewal periods), the registrar (for phishing patterns), name servers (potential weak points), and historical changes. Services like whoxy.com provide historical WHOIS snapshots. Historical WHOIS data can reveal previous owners, registrar changes, or name server migrations that may indicate past compromises or infrastructure shifts.

```bash
whois DOMAIN_NAME
```

## Analyzing WHOIS Output

A WHOIS query can reveal several useful pieces of information.

### 1. Registrar

The output identifies the registrar responsible for the domain.

```text
Registrar: NAMECHEAP INC
Registrar IANA ID: 1068
```

**Recon value:**
The registrar tells us which company manages the domain registration. This can help identify the registration infrastructure and provide context for further research.

### 2. Domain Registration Dates

The output provides important timestamps:

```text
Creation Date: 2018-07-05
Updated Date: 2025-05-11
Expiration Date: 2034-07-05
```

**Recon value:**

* **Creation Date** → Indicates when the domain was originally registered.
* **Updated Date** → Indicates when registration information was last modified.
* **Expiration Date** → Shows the current registry expiration date.

These dates can help establish the domain's history and identify significant registration changes.

### 3. Domain Status

The domain returned:

```text
clientTransferProhibited
```

This indicates that the domain is protected against unauthorized domain transfers.

**Recon value:**
It provides information about the domain's security/registration state and can indicate that transfer protection is enabled.

### 4. Name Servers

The WHOIS response revealed:

```text
kip.ns.cloudflare.com
uma.ns.cloudflare.com
```

This shows that the domain uses **Cloudflare name servers**.

**Recon value:**

<pre>
Target Domain
     ↓
Name Servers
     ↓
Cloudflare DNS Infrastructure
</pre>

Name servers provide information about the target's DNS infrastructure and can be useful when mapping the organization's external infrastructure.

> The presence of Cloudflare name servers does **not** mean Cloudflare is necessarily the origin server. Cloudflare may be acting as the DNS provider and/or reverse proxy.

### 5. Registrant Information

The registrant information was redacted:

```text
Registrant Name: Redacted for Privacy Purposes
Registrant Organization: WITHHELD FOR PRIVACY LLC
```

**Recon value:**
This demonstrates why modern WHOIS often provides limited personal information. Privacy services prevent the actual registrant's name, address, phone number, and email from being publicly exposed.

The displayed contact details belong to the privacy service rather than necessarily to the actual domain owner.

### 6. DNSSEC Status

The output contains:

```text
DNSSEC: unsigned
```

This indicates that the domain's DNS delegation is **not DNSSEC-signed**.

**Recon value:**
It provides information about the domain's DNS security configuration and can be recorded as part of the overall reconnaissance profile.

### 7. Registrar Abuse Contact

WHOIS may also provide registrar abuse contacts:

```text
Abuse Contact:
abuse@namecheap.com
```

This is primarily useful for reporting abuse rather than directly attacking the target.

## WHOIS vs RDAP

| Feature         | WHOIS                | RDAP                         |
| --------------- | -------------------- | ---------------------------- |
| Transport       | TCP 43               | HTTPS                        |
| Output          | Plain text           | JSON                         |
| Parsing         | More difficult       | Easy to automate             |
| Standardization | Inconsistent         | Structured                   |
| Modern standard | Legacy               | Current                      |
| Privacy support | Limited/legacy model | Better differentiated access |

### Practical Workflow

<pre>
Domain
  ↓
WHOIS / RDAP
  ↓
Registrar
Registration Dates
Domain Status
Name Servers
DNSSEC
Privacy Information
  ↓
Build Domain Profile
  ↓
Combine with Other Passive Recon
</pre>

### Key Takeaways

* WHOIS can reveal **registrar, registration dates, domain status, name servers, DNSSEC status, and limited registrant information**.
* Modern WHOIS records frequently hide personal information through privacy services.
* **RDAP** provides similar registration data in a structured JSON format over HTTPS.
* The most valuable approach is to **analyze and correlate** WHOIS/RDAP information rather than looking for a single finding.
* Name servers can reveal the DNS provider, while registration dates provide useful historical context.
* WHOIS/RDAP is only one part of passive reconnaissance and should be combined with DNS, certificate transparency, search engines, and other OSINT sources.

## DNS Reconnaissance

### What Is DNS Reconnaissance ?

DNS (Domain Name System) translates human-readable domain names into information that computers use to communicate, such as IP addresses.

**DNS reconnaissance** involves querying DNS records to learn about a domain's internet-facing infrastructure. These records can reveal IP addresses, mail servers, nameservers, and other technical details.

DNS queries to public recursive resolvers are generally considered passive reconnaissance because they do not directly probe the target's services. However, DNS queries may still be logged, and the target's authoritative DNS infrastructure may observe queries depending on the resolution path.

### Common DNS Record Types

| Record  | Purpose                                                                                                       |
| ------- | ------------------------------------------------------------------------------------------------------------- |
| `A`     | Maps a domain to an IPv4 address.                                                                             |
| `AAAA`  | Maps a domain to an IPv6 address.                                                                             |
| `CNAME` | Specifies an alias pointing to another domain name.                                                           |
| `MX`    | Identifies mail servers for a domain.                                                                         |
| `NS`    | Identifies authoritative nameservers for a DNS zone.                                                          |
| `TXT`   | Stores text information, often used for domain verification and email security policies.                      |
| `SOA`   | Contains administrative information about a DNS zone, including its primary nameserver and timing parameters. |

Different record types provide different pieces of information about a domain's infrastructure.

### Using `nslookup`

`nslookup` stands for **Name Server Lookup**. It is a command-line tool used to query DNS records and inspect the responses.

#### Query A records

```text
root@ip- ------:~# nslookup -type=A tryhackme.com
Server:		127.0.0.1
Address:	127.0.0.1#53

Non-authoritative answer:
Name:	tryhackme.com
Address: 10.48.83.95
```

This requests the IPv4 addresses associated with `tryhackme.com`.
The local DNS resolver (127.0.0.1) returned 10.48.83.95, a private IPv4 address. The answer is marked non-authoritative because it came from a resolver rather than directly from the authoritative nameserver.

#### Query MX records

```text
root@ip- ----:~# nslookup -type=MX tryhackme.com
Server:		127.0.0.1
Address:	127.0.0.1#53

Non-authoritative answer:
*** Can't find tryhackme.com: No answer

Authoritative answers can be found from:
tryhackme.com
	origin = ns-1536.awsdns-00.co.uk
	mail addr = awsdns-hostmaster.amazon.com
	serial = 1
	refresh = 7200
	retry = 900
	expire = 1209600
	minimum = 86400

```
This requests the domain's mail exchanger records, which identify the mail servers configured to receive email for the domain.
No MX record was returned (No answer). The SOA information identifies the DNS zone's authoritative server and administrative details; it does not mean the domain definitely cannot receive email.

#### Specify a DNS resolver

```text
root@ip- ----:~# nslookup -type=A tryhackme.com 1.1.1.1
Server:		1.1.1.1
Address:	1.1.1.1#53

Non-authoritative answer:
Name:	tryhackme.com
Address: 64.239.109.65
Name:	tryhackme.com
Address: 64.239.123.65
```
Here, `1.1.1.1` is the DNS resolver being queried. Specifying a resolver lets you compare results from different DNS services.
Cloudflare's public DNS resolver (1.1.1.1) returned two public IPv4 addresses: 64.239.109.65 and 64.239.123.65. This differs from the local resolver's answer.
**Reconnaissance value:** `nslookup` provides a quick way to discover DNS information without directly scanning the target's ports or services.

### Using `dig`

`dig` stands for **Domain Information Groper**. It is a DNS query tool that provides detailed response information and is useful for troubleshooting, reconnaissance, and scripting.

#### Query A records

```text
root@ip- ----:~# dig tryhackme.com A

; <<>> DiG 9.18.39-0ubuntu0.24.04.7-Ubuntu <<>> tryhackme.com A
;; global options: +cmd
;; Got answer:
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 11114
;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1

;; OPT PSEUDOSECTION:
; EDNS: version: 0, flags:; udp: 1232
;; QUESTION SECTION:
;tryhackme.com.			IN	A

;; ANSWER SECTION:
tryhackme.com.		267	IN	A	10.48.83.95

;; Query time: 1 msec
;; SERVER: 127.0.0.1#53(127.0.0.1) (UDP)
;; WHEN: Fri Oct 09 10:16:38 UTC 2026
;; MSG SIZE  rcvd: 58
```
The local resolver returned one A record, 10.48.83.95, with a TTL of 267 seconds. NOERROR means the query succeeded, and SERVER: 127.0.0.1#53 identifies the resolver queried.

#### Query MX records

```text
root@ip- ----:~# dig tryhackme.com MX

; <<>> DiG 9.18.39-0ubuntu0.24.04.7-Ubuntu <<>> tryhackme.com MX
;; global options: +cmd
;; Got answer:
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 41650
;; flags: qr rd ra; QUERY: 1, ANSWER: 0, AUTHORITY: 1, ADDITIONAL: 1

;; OPT PSEUDOSECTION:
; EDNS: version: 0, flags:; udp: 1232
;; QUESTION SECTION:
;tryhackme.com.			IN	MX

;; AUTHORITY SECTION:
tryhackme.com.		900	IN	SOA	ns-1536.awsdns-00.co.uk. awsdns-hostmaster.amazon.com. 1 7200 900 1209600 86400

;; Query time: 2 msec
;; SERVER: 127.0.0.1#53(127.0.0.1) (UDP)
;; WHEN: Fri Oct 09 10:16:51 UTC 2026
;; MSG SIZE  rcvd: 126
```
The query succeeded, but ANSWER: 0 means no MX records were returned. The SOA record in the authority section provides DNS zone information, including the authoritative nameserver ns-1536.awsdns-00.co.uk.

#### Query a specific resolver

```text
root@ip- ----:~# dig @1.1.1.1 tryhackme.com A

; <<>> DiG 9.18.39-0ubuntu0.24.04.7-Ubuntu <<>> @1.1.1.1 tryhackme.com A
; (1 server found)
;; global options: +cmd
;; Got answer:
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 21516
;; flags: qr rd ra; QUERY: 1, ANSWER: 2, AUTHORITY: 0, ADDITIONAL: 1

;; OPT PSEUDOSECTION:
; EDNS: version: 0, flags:; udp: 1232
;; QUESTION SECTION:
;tryhackme.com.			IN	A

;; ANSWER SECTION:
tryhackme.com.		294	IN	A	64.239.123.129
tryhackme.com.		294	IN	A	64.239.109.129

;; Query time: 9 msec
;; SERVER: 1.1.1.1#53(1.1.1.1) (UDP)
;; WHEN: Fri Oct 09 10:17:08 UTC 2026
;; MSG SIZE  rcvd: 74
```
The `@1.1.1.1` syntax specifies which DNS resolver should receive the query.
Cloudflare's resolver returned two public IPv4 addresses, 64.239.123.129 and 64.239.109.129, with a TTL of 294 seconds. Compared with the local resolver, this shows different DNS answers; the output alone does not establish why.

#### Display only the returned addresses

```text
dig @1.1.1.1 tryhackme.com A +short
```

The `+short` option reduces the output to the answer values, making repeated queries easier to compare.

### Understanding `dig` Output

Important fields in a typical `dig` response include:

| Field             | Meaning                                                                                                    |
| ----------------- | ---------------------------------------------------------------------------------------------------------- |
| `status: NOERROR` | The DNS query completed successfully. It does not guarantee that every expected record exists.             |
| `ANSWER SECTION`  | Contains the DNS records returned in the response.                                                         |
| `TTL`             | Indicates how long a record may remain cached before it expires. The displayed value is the remaining TTL. |
| `IN`              | Indicates the Internet DNS class.                                                                          |
| `A`               | Identifies an IPv4 address record.                                                                         |
| `MX`              | Identifies a mail exchanger record. MX records also contain a priority value.                              |
| `SERVER`          | Shows the DNS server that answered the query.                                                              |
| `Query time`      | Shows how long the query took, as reported by the tool.                                                    |

For example, an answer such as:

```text
tryhackme.com.  247  IN  A  64.239.109.1
```

indicates that the domain has an A record returning `64.239.109.1`, with a remaining TTL of 247 seconds in that response.

### Why Can Repeated DNS Queries Return Different IP Addresses ?

During reconnaissance of `tryhackme.com`, repeated DNS queries returned different pairs of IPv4 addresses.

Some observed addresses were:

```text
64.239.109.1
64.239.123.1
64.239.109.65
64.239.123.65
64.239.109.129
64.239.123.129
```

The results changed even when the same domain and, in some tests, the same resolver were used.

#### Comparing two resolvers

```bash
dig @1.1.1.1 tryhackme.com A
dig @8.8.8.8 tryhackme.com A
```

In the observed tests:

* `1.1.1.1` returned `64.239.109.1` and `64.239.123.1`.
* `8.8.8.8` returned `64.239.123.65` and `64.239.109.65`.

Both responses reported `NOERROR`, meaning the queries completed successfully. The different answers do not, by themselves, indicate a DNS error.

#### Repeating queries against one resolver

```bash
for i in {1..5}; do
  dig @1.1.1.1 tryhackme.com A +short
  sleep 2
done
```

This Bash loop performs five DNS queries, waiting two seconds between each query. In the observed output, the returned addresses varied across queries.

#### Why might this happen ?

Possible explanations include:

* **Multiple A records:** A domain may have several IPv4 addresses.
* **DNS-based traffic distribution:** DNS may return different addresses to distribute traffic across infrastructure.
* **Geographic or network-based responses:** Some DNS configurations provide different answers depending on the resolver or query context.
* **Caching and timing:** Recursive resolvers may have different cached data or query the authoritative servers at different times.
* **DNS record changes:** The domain's DNS configuration may change over time.

These are possible explanations, not confirmed causes for the observed results. The outputs alone do not prove that round-robin DNS, a CDN, or a particular load-balancing mechanism is being used.

#### What do the changing IPs mean ?

The observations indicate that DNS responses for the domain were not identical across the tested queries. They do not prove that each IP belongs to a different physical server, that the addresses are permanently assigned, or that the underlying infrastructure changed between requests.

The TTL is the remaining cache lifetime of a record, not a measure of how long the server has existed or how long the IP will remain assigned to the domain.

### Investigating Authoritative Nameservers

The WHOIS/RDAP results identified these nameservers for `tryhackme.com`:

* `kip.ns.cloudflare.com`
* `uma.ns.cloudflare.com`

You can query them directly to compare their responses:

```bash
dig @kip.ns.cloudflare.com tryhackme.com A
dig @uma.ns.cloudflare.com tryhackme.com A
```

Compare the returned addresses and TTL values with the answers from recursive resolvers such as `1.1.1.1` and `8.8.8.8`.

This can help investigate whether the authoritative responses also vary. It may not establish the exact cause, because authoritative DNS responses can depend on configuration and query context.

**Important distinction:** `1.1.1.1` is the recursive resolver in the earlier command, not necessarily the target's web server. Likewise, the use of Cloudflare nameservers does not prove that every returned A-record address belongs to Cloudflare.

### Passive DNS Reconnaissance Workflow

A basic workflow for investigating a domain is:

1. Query its A and AAAA records to identify IPv4 and IPv6 addresses.
2. Query its MX records to identify configured mail servers.
3. Query its NS records to identify authoritative nameservers.
4. Query TXT records to inspect publicly available domain-verification and email-policy information.
5. Use `dig` to inspect response details such as TTL, status, and answer records.
6. Compare responses across resolvers or repeated queries when an observation needs further investigation.
7. Record the findings with the query, resolver, date/time, and returned values.

Only perform further testing against systems you are authorized to assess.

### Defensive Relevance

DNS records can expose information about an organization's infrastructure. Defenders should review public DNS records, remove obsolete records, avoid publishing unnecessary internal details, and configure email-security records appropriately.

DNS over HTTPS (DoH) and DNS over TLS (DoT) encrypt the connection between a client and its DNS resolver. They do not make DNS queries inherently anonymous or prevent all parties involved in resolution from observing relevant queries.

### Key Takeaways

* DNS reconnaissance reveals publicly available information about domain infrastructure.
* `nslookup` is useful for quick DNS queries, while `dig` provides more detailed output and useful scripting options.
* Different DNS record types reveal different kinds of infrastructure information.
* A domain can return multiple IP addresses, and observed answers can vary across queries or resolvers.
* Changing answers may indicate DNS answer selection, caching differences, or other configuration behavior; the exact cause requires further investigation.
* Record what you observed without assuming that each IP represents a distinct physical server or that a particular load-balancing technology is in use.

## Subdomain Discovery - DNSDumpster and Certificate Transparency

### Why Discover Subdomains ?

Basic DNS commands such as `dig` and `nslookup` resolve domain names that you already know. They do not automatically discover every subdomain belonging to a domain.

For example:

* `tryhackme.com` - main domain
* `blog.tryhackme.com` - blog subdomain
* `app.tryhackme.com` - application subdomain
* `dev.example.com` - development subdomain

Subdomains can reveal additional applications, APIs, administrative interfaces, or forgotten services. These expand the organization's potential attack surface.

### DNSDumpster

[DNSDumpster](https://dnsdumpster.com/) is a web-based reconnaissance tool that collects publicly available DNS and infrastructure information to help discover subdomains and related hosts.

**How to use it:**

1. Open DNSDumpster.
2. Search for `tryhackme.com`.
3. Review the discovered subdomains, IP addresses, DNS records, and infrastructure map.

DNSDumpster also graphs the data, showing how subdomains, IPs, and mail servers relate to each other:

<img width="1482" height="676" alt="image" src="https://github.com/user-attachments/assets/2c767911-1f15-439c-90c7-6fe9b126a2e3" />

**What the results tell you:**

* **Subdomains and hosts:** Additional domain names associated with the target.
* **IP addresses:** Addresses associated with discovered hosts.
* **MX records:** Information about mail infrastructure.
* **TXT and CNAME records:** Additional DNS configuration and domain relationships.
* **Infrastructure map:** A visual representation of relationships between hosts, IPs, and mail servers.

**Why it matters:** DNSDumpster can reveal hostnames you might not discover by querying only the main domain.

> *Note:* DNSDumpster aggregates information from public sources. Its coverage and methods may vary, so do not assume every result is current or that the tool uses only passive sources in every circumstance.

### Certificate Transparency (CT) Logs

Certificate Transparency is a public logging system for TLS certificates issued by participating Certificate Authorities.

Certificates can contain a **Subject Alternative Name (SAN)** field listing the domain names covered by the certificate. Searching public CT logs can therefore reveal subdomains that may not appear in a basic DNS lookup.

#### Using crt.sh

Open [crt.sh](https://crt.sh/) and search for:

```text
%.tryhackme.com
```

The `%` wildcard is used by crt.sh to match names associated with subdomains of `tryhackme.com`.

**What the results mean:**

* **Certificate entries:** Certificates recorded in CT logs.
* **Common Name (CN) and SANs:** Domain names included in certificate information.
* **Subdomains:** Names such as `blog.tryhackme.com` may be revealed even if you did not know them beforehand.
* **Validity dates:** Help indicate when a certificate became valid and when it expires.

**Why it matters:** CT logs provide an additional source for discovering subdomains without directly scanning the target's infrastructure.

**Limitations:** CT logs reveal names included in logged certificates, not every existing subdomain. Results may include expired certificates, duplicates, or hostnames that no longer resolve. Searching CT logs is passive with respect to the target, although the search service itself receives your query.

### Other Passive Subdomain Discovery Tools

* **SecurityTrails:** Provides domain, DNS, and historical infrastructure information, subject to its access limits.
* **Subfinder:** A command-line tool that aggregates subdomains from configured sources. Its passive mode can be used for OSINT-based discovery.

Tools differ in their data sources, coverage, and collection methods, so results should be cross-checked.

### Defender Perspective

Organizations can monitor CT logs and their known subdomain inventory to identify:

* Unexpected certificates issued for their domains.
* Forgotten or unauthorized subdomains.
* Stale DNS records pointing to resources that no longer exist.
* Potential subdomain takeover risks caused by dangling DNS records.

A discovered hostname alone does not prove a vulnerability. The hostname, DNS records, and associated service must be validated before drawing conclusions.

### Key Takeaways

* `dig` and `nslookup` query known DNS names; they do not automatically enumerate all subdomains.
* DNSDumpster helps discover subdomains and visualize related infrastructure.
* CT logs and crt.sh reveal domain names recorded in TLS certificate information.
* Passive subdomain discovery helps build a broader picture of the target's public attack surface.
* Results can be outdated or incomplete, so validate findings and perform active testing only with authorization.

## Shodan - Search Engine for Internet-Connected Devices

### What Is Shodan ?

Shodan is a search engine for internet-connected devices and services. Unlike Google, which primarily indexes web pages, Shodan collects and indexes information such as service banners, open ports, and responses from internet-facing systems.

It can provide information about servers, routers, IoT devices, databases, and other publicly accessible services.

**Why it matters:** Shodan helps security professionals identify an organization's potential internet-facing attack surface without directly scanning its systems themselves.

### Using Shodan

1. Visit [shodan.io](https://www.shodan.io/).
2. Search for a domain such as `tryhackme.com` or an IP address discovered during DNS reconnaissance.
3. Review the matching hosts and available service information.
4. Open a host result to examine its details.

Shodan's indexed data may not be complete or current, and some features require an account.

### Understanding Shodan Results

| Field                | Meaning                                                                               |
| -------------------- | ------------------------------------------------------------------------------------- |
| IP address           | The public IP address associated with the indexed host.                               |
| ASN                  | Autonomous System Number identifying the network that announces the IP address range. |
| Organization         | The organization or network provider associated with the address.                     |
| Location             | An approximate geographic location inferred from available data.                      |
| Open ports           | Ports Shodan observed as accessible when it collected the data.                       |
| Services and banners | Information returned by a service, potentially including its software or version.     |
| Tags                 | Labels assigned to hosts based on observed characteristics or classifications.        |

**Important:** An IP address associated with a domain may belong to a CDN, reverse proxy, or shared hosting provider. Its details do not necessarily identify the domain's origin server. A Shodan result is also a historical observation, not proof that a port remains open now.

### Shodan Search Filters

Shodan supports filters that help narrow results.

```text
hostname:tryhackme.com
```

**Explanation:** Searches for indexed hosts associated with the specified hostname.

```text
org:"TryHackMe"
```

**Explanation:** Filters results associated with the specified organization name, where that organization information is available.

```text
port:443 country:US
```

**Explanation:** Finds matching indexed hosts with port `443` in the United States.

```text
http.component:"wordpress"
```

**Explanation:** Searches for HTTP services identified as using the WordPress component.

These are search filters, not commands that directly scan a target. Their results depend on Shodan's indexed data and detection accuracy.

For more filters, see the [Shodan Search Query Fundamentals](https://help.shodan.io/the-basics/search-query-fundamentals) guide.

### Censys - An Alternative

Censys is another internet intelligence platform that provides information about internet-facing hosts, services, and TLS certificates.

Using both Shodan and Censys can help cross-reference findings because their datasets, collection methods, and indexing times may differ.

### Defensive Relevance

Organizations can use Shodan to identify:

* Unexpectedly exposed services.
* Forgotten or test systems accessible from the internet.
* Services that reveal unnecessary software-version information.
* Potentially vulnerable services requiring further verification.

A version match or vulnerability tag is an indication to investigate, not confirmation that the host is exploitable.

### Key Takeaways

* Shodan indexes internet-facing devices and services rather than ordinary web pages.
* Results may reveal IP addresses, ASNs, ports, banners, and technology information.
* Search filters narrow the results to relevant hosts.
* Shodan data may be outdated or incomplete, and an IP may represent shared infrastructure rather than an origin server.
* Censys provides a complementary source for internet-host and certificate information.
* Use these findings for authorized security assessment and exposure monitoring.
