# Protocols and Servers II

## Introduction

Network protocols enable communication between clients and servers. However, protocols that transmit data without encryption can expose usernames, passwords, messages, and other sensitive information to anyone able to capture the network traffic.
For example, when a user logs into email over public Wi-Fi using an unencrypted protocol, an attacker monitoring the traffic may be able to capture the transmitted credentials and email contents.
Common protocols include Telnet, HTTP, FTP, SMTP, POP3, and IMAP. Modern deployments use secure alternatives such as SSH, HTTPS, SFTP, FTPS, and TLS-protected email protocols to protect data in transit.

Understanding how these protocols work helps security professionals identify legacy systems, insecure configurations, and weaknesses in network communication.

## Common Attack Categories

Network services are commonly targeted through the following attack types :

1. **Sniffing Attack :** Capturing network traffic to discover sensitive information transmitted without encryption.
2. **Man-in-the-Middle (MITM) Attack :** Intercepting communication between two parties to potentially read or modify the data exchanged.
3. **Password Attack :** Attempting to obtain valid credentials through techniques such as brute force, password spraying, or credential stuffing.

These attacks exploit weaknesses in communication security or authentication mechanisms.

## The CIA Triad

The CIA triad represents three fundamental goals of information security.

| Principle | Meaning | Example |
|---|---|---|
| Confidentiality | Only authorized parties can access information. | Protecting email credentials with encryption. |
| Integrity | Data remains accurate and is not modified without authorization. | Preventing unauthorized changes to a banking transaction. |
| Availability | Systems and services remain accessible when needed. | Keeping an online service operational during an attack. |

Different organizations prioritize these principles according to their needs. Intelligence agencies may prioritize confidentiality, financial systems emphasize integrity, and online services depend heavily on availability.

## CIA vs DAD

Attacks can threaten the CIA triad through three broad outcomes, summarized as DAD: **Disclosure, Alteration, and Destruction**.

| Security Goal | Opposing Outcome | Explanation |
|---|---|---|
| Confidentiality | Disclosure | Sensitive information is exposed to unauthorized parties. |
| Integrity | Alteration | Data is modified without authorization. |
| Availability | Destruction or disruption | Data or services become unavailable or unusable. |

Examples :

- **Sniffing :** Can cause disclosure when unencrypted credentials or messages are captured.
- **MITM :** Can cause disclosure or alteration when an attacker successfully intercepts communication.
- **Password attacks :** Can lead to unauthorized access and subsequent data exposure or modification.
- **Denial of Service (DoS) :** Targets availability by making a service difficult or impossible to access.

## The Modern Attack Landscape

### Sniffing Attacks

Sniffing involves capturing network packets to inspect transmitted data. TLS encryption makes captured traffic much harder to read, but plaintext services and incorrectly configured systems remain vulnerable to information exposure.

> Sniffing attacks are harder on properly configured networks due to widespread TLS adoption, but they remain effective against misconfigured services, internal networks without encryption, and legacy systems.

### Man-in-the-Middle Attacks

MITM attacks attempt to intercept communication between two parties. Attackers may try to read or modify data while making the connection appear legitimate.

Defenses include properly validated TLS certificates, HTTPS, HTTP Strict Transport Security (HSTS), and certificate pinning in suitable applications.

> MITM attacks are mitigated by technologies like HSTS (HTTP Strict Transport Security), certificate pinning, and Certificate Transparency logs, but they can still succeed when these protections are absent or improperly implemented.

### Password Attacks

Common credential attack techniques include:

- **Brute Force :** Trying many possible passwords against an account.
- **Password Spraying :** Trying a small number of common passwords against multiple accounts.
- **Credential Stuffing :** Testing leaked username-and-password combinations against other services.

Defenses include strong, unique passwords, multi-factor authentication (MFA), rate limiting, and appropriate account lockout or throttling controls.

> Password attacks have evolved beyond simple brute force. Attackers now use credential stuffing (trying leaked username/password pairs from breaches), password spraying (trying common passwords across many accounts), and leverage massive breach databases.

## Understanding Vulnerabilities

A vulnerability is a weakness in a system that may be exploited to cause harm. Its impact depends on the weakness and how it is exploited.

- **Denial of Service (DoS) :** May compromise system availability.
- **Remote Code Execution (RCE) :** May allow an attacker to execute commands or code on a target system, potentially compromising confidentiality, integrity, and availability.

A vulnerability creates risk, but exploitation is not guaranteed. Risk also depends on factors such as exploitability, exposure, and potential impact.

## Key Takeaways

- Unencrypted protocols can expose credentials and sensitive information.
- Sniffing primarily threatens confidentiality, while MITM attacks can threaten confidentiality and integrity.
- Password attacks exploit weak, reused, or poorly protected credentials.
- The CIA triad defines security goals, while DAD describes harmful outcomes.
- TLS, strong authentication, MFA, and secure protocol configurations help reduce these risks.
- Understanding attack techniques helps security professionals identify weaknesses and recommend effective defenses.

## Sniffing Attacks

## What Is a Sniffing Attack ?

A **sniffing attack** involves capturing and analysing network packets to inspect data exchanged between systems. If communication uses an unencrypted protocol, captured traffic may expose sensitive information such as login credentials, emails, and session data.

Sniffing can be performed using packet capture tools such as **Tcpdump** and **Wireshark**.

## Where Sniffing Attacks Are Relevant

Sniffing remains a security risk in situations where network traffic is unencrypted or encryption is improperly configured.

- **Internal corporate networks:** Communication between internal systems may lack encryption.
- **Legacy systems:** Older services may use cleartext protocols.
- **Misconfigured services:** Encryption may be available but not enforced.
- **IoT devices:** Some devices transmit information without encryption.
- **Wireless networks:** Attackers with suitable network access may capture traffic.
- **Successful MITM attacks:** An attacker may gain visibility into traffic through traffic redirection or an encryption downgrade, where the protocol permits it.

During authorised penetration tests, packet analysis helps identify insecure protocols, exposed credentials, and communication patterns.

## Packet Capture Tools

| Tool | Description |
|---|---|
| **Tcpdump** | Lightweight command-line packet capture and filtering tool. |
| **Wireshark** | Graphical tool for inspecting packets, dissecting protocols, and filtering traffic. |
| **Tshark** | Command-line packet analyser that uses Wireshark's dissection engine. |
| **tcpflow** | Reassembles TCP connections into data streams. |
| **ngrep** | Searches network traffic for specified patterns. |
| **NetworkMiner** | Analyses captured traffic to extract information such as files, hosts, and sessions. |

Packet capture generally requires appropriate privileges and access to the relevant traffic. On a switched network, a device does not automatically see all traffic exchanged between other devices.

## Capturing Cleartext POP3 Credentials

POP3 traditionally uses **TCP port 110** without encryption. If a user authenticates over an unencrypted connection, the username and password may be visible in captured packets.

### Tcpdump example

```bash
sudo tcpdump port 110 -A
```

**Command breakdown:**

- `sudo` — runs the command with elevated privileges.
- `tcpdump` — captures and displays network packets.
- `port 110` — filters traffic involving TCP or UDP port 110, depending on the capture and filter context; POP3 normally uses TCP.
- `-A` — displays packet payload data as printable ASCII where possible.

Example payloads from an unencrypted POP3 session might contain:

```text
USER frank
PASS example_password
```

These commands are part of the POP3 authentication exchange. If transmitted without encryption, they can reveal the username and password to someone able to inspect the traffic.

### Other useful Tcpdump commands

```bash
# Capture traffic involving a specific host
sudo tcpdump host 10.20.30.148

# Display readable HTTP payloads
sudo tcpdump -A port 80

# Display readable FTP payloads
sudo tcpdump -A port 21

# Save packets for later analysis
sudo tcpdump -w capture.pcap

# Read a saved capture
tcpdump -r capture.pcap -A
```

Use packet capture only on systems and networks where you have explicit authorisation. Captured files may contain credentials and other sensitive data, so protect them accordingly.

### Wireshark analysis

Wireshark can display the same traffic in a graphical interface.

A display filter such as :

```text
pop
```

helps isolate packets identified as POP traffic. Inspecting the relevant packets or following a TCP stream can make the authentication exchange easier to understand.

**Important:** Tcpdump's capture filters and Wireshark's display filters use different syntax. A capture filter determines which packets are recorded; a display filter determines which captured packets are shown.

## Mitigation

The primary defence against sniffing is to **encrypt data in transit**.

- **Use TLS:** Prefer HTTPS, implicit TLS, or correctly configured STARTTLS for supported services.
- **Replace insecure protocols:** Use SSH instead of Telnet and SFTP instead of unencrypted FTP.
- **Enforce encryption:** Disable insecure fallback options and require secure connections wherever possible.
- **Segment networks:** Separate sensitive systems into restricted network zones.
- **Secure network access:** Use 802.1X authentication where appropriate to prevent unauthorised devices from joining a network.
- **Use encrypted tunnels:** Protect traffic across networks that cannot be fully trusted.
- **Monitor suspicious activity:** Detect ARP spoofing, unexpected traffic redirection, and other potential indicators of interception.
- **Protect packet captures:** Restrict access to capture files and securely dispose of them when no longer required.

Network segmentation and monitoring reduce exposure, but they do not replace encryption.

Additional mitigations include : 

- Network segmentation limits which systems can see each other's traffic by dividing the network into isolated zones.
- Encrypted VLANs and tunnels protect sensitive traffic even on internal networks.
- 802.1X port-based authentication requires devices to authenticate before gaining network access, preventing unauthorised devices from connecting and sniffing traffic.
- Zero trust architecture is a security model that treats all network traffic as potentially hostile, encrypting all communications regardless of whether they originate inside or outside the network perimeter.
- Monitoring for ARP spoofing and other traffic redirection techniques helps detect sniffing attempts in progress.

Modern best practice assumes the network is hostile, even internal networks. This means encrypting all traffic, not just traffic that crosses the internet.

## Key Takeaways

- Sniffing captures and analyses network packets.
- Cleartext protocols can expose credentials and sensitive communications.
- Tcpdump, Wireshark, and Tshark are commonly used for packet analysis.
- POP3 on TCP port 110 can expose authentication data when used without encryption.
- Access to the relevant traffic is necessary; ordinary devices on a switched network cannot necessarily capture every other device's traffic.
- Encryption in transit is the primary defence, supported by network segmentation, access controls, and monitoring.

## Man-in-the-Middle (MITM) Attacks

## What Is a MITM Attack?

A **Man-in-the-Middle (MITM) attack** occurs when an attacker secretly positions themselves between two communicating parties, intercepting and potentially modifying their messages.

For example, a user sends a request to transfer $20 to a recipient. An attacker intercepts the request, changes the amount to $2000, and forwards the modified message. If the recipient's system does not verify the message's authenticity and integrity, it may process the altered request.

<img width="800" height="450" alt="image" src="https://github.com/user-attachments/assets/93743f3b-797f-4807-83de-9edc3771459a" />

A successful MITM attack can compromise :

- **Confidentiality:** Reading private communications or credentials.
- **Integrity:** Modifying messages or transactions.
- **Authenticity:** Impersonating a legitimate party.

## How MITM Attacks Work

An attacker generally needs a way to intercept or redirect communication between the victim and the intended destination.

| Technique | How it works |
|---|---|
| **ARP spoofing** | Sends forged ARP messages on a local network to associate the attacker's MAC address with another device's IP address, potentially redirecting traffic through the attacker. |
| **DNS spoofing** | Supplies false DNS responses to redirect a victim to an attacker-controlled destination. |
| **Rogue access point** | Uses a fake or malicious Wi-Fi access point to attract users and potentially inspect their traffic. |
| **BGP hijacking** | Announces incorrect or unauthorised routing information to divert internet traffic through an unintended network. |

These techniques operate at different layers of network communication. For example, ARP spoofing targets local network address resolution, while BGP hijacking affects internet routing.

> For an attacker to position themselves between two communicating parties, they typically need to redirect traffic through their system. Common techniques include:

> ARP Spoofing is effective on local networks. The attacker sends forged ARP (Address Resolution Protocol) messages to associate their MAC address with the IP address of the default gateway or target system. As a result, traffic intended for those systems is sent to the attacker instead.

> DNS Spoofing involves providing false DNS responses to redirect victims to attacker-controlled servers. This can happen through compromised DNS servers, DNS cache poisoning, or by responding to DNS queries faster than the legitimate server.

> Rogue Access Points are fake wireless access points set up by attackers. When victims connect to these networks (often named to look like legitimate networks such as Airport_WiFi_Free), all their traffic flows through the attacker's system.

> BGP Hijacking operates at the internet routing level, where attackers announce false BGP routes to redirect traffic through their infrastructure. This is a more sophisticated attack, typically targeting specific organisations or regions.

## Common MITM Tools

| Tool | Purpose |
|---|---|
| **Bettercap** | Modular network analysis and security testing, including traffic interception and spoofing capabilities. |
| **Ettercap** | Network traffic interception and MITM testing, particularly on local networks. |
| **mitmproxy** | Interactive HTTP/HTTPS proxy for inspecting and modifying web traffic in authorised testing environments. |
| **Responder** | Detects and responds to Windows name-resolution requests such as LLMNR and NBT-NS, potentially capturing authentication material in misconfigured networks. |

These tools are used in authorised security assessments to identify weaknesses in network configurations, authentication, and traffic protection.

> Many tools can aid in carrying out MITM attacks. Understanding these helps you recognise what attackers can do and why mitigations matter:

> Bettercap is the modern successor to Ettercap and is actively maintained. It supports ARP spoofing, DNS spoofing, HTTP/HTTPS proxying, and has a modular architecture for various attack scenarios.

> Ettercap is a classic tool for MITM attacks on LANs. While still functional, Bettercap is generally preferred for modern assessments.

> mitmproxy is an interactive HTTPS proxy that allows inspection and modification of traffic. It is particularly useful for analysing and manipulating HTTP/HTTPS communications.

> Responder is designed for Windows environments and exploits name resolution protocols such as LLMNR (Link-Local Multicast Name Resolution) and NBT-NS (NetBIOS Name Service). These are fallback protocols that Windows systems use when standard DNS resolution fails. Responder listens for these broadcast queries and responds with its own IP address, tricking victims into sending authentication credentials to the attacker. This is a common technique during internal penetration tests of Active Directory environments.

### LLMNR and NBT-NS

- **LLMNR (Link-Local Multicast Name Resolution):** Allows devices to resolve names on a local network when conventional DNS resolution is unsuccessful.
- **NBT-NS (NetBIOS Name Service):** Supports name resolution in legacy Windows networking environments.

If these protocols are enabled in an environment where they are not needed, a malicious system may respond to name-resolution requests and trick clients into contacting it. Depending on the configuration, this can expose authentication material.

## MITM Attacks Against Encrypted Traffic

Encryption makes interception much less useful to an attacker, but implementation and configuration weaknesses can still create opportunities.

### SSL stripping

SSL stripping attempts to downgrade a victim's connection from HTTPS to HTTP, leaving the victim's side of the communication unencrypted while the attacker maintains a secure connection to the legitimate server.

> SSL Stripping downgrades HTTPS connections to HTTP. When a victim tries to connect to a website, the attacker intercepts the request, establishes an HTTPS connection with the legitimate server, but serves the content to the victim over unencrypted HTTP. The victim may not notice the missing padlock icon, especially if they did not explicitly type https://.

**Limitation:** HSTS and HTTPS-first browser behaviour make this technique harder to perform successfully. HSTS-protected connections cannot simply fall back to HTTP in a compliant browser once the policy is enforced.

### Fake or invalid certificates

An attacker may present a certificate that does not properly establish the server's identity. If a user ignores a certificate warning or an application fails to validate certificates correctly, the attacker may be able to intercept encrypted communications.

> Fake Certificates involve the attacker presenting their own certificate and establishing separate encrypted connections with both parties. This works if the victim accepts an invalid certificate warning or if the attacker has compromised a Certificate Authority (CA).

### Compromised certificate authorities

TLS relies on a system of trusted Certificate Authorities (CAs). If a trusted CA is compromised or improperly issues a certificate, an attacker may be able to impersonate a domain in circumstances where clients accept that certificate.

> Compromised or Rogue CAs represent a more serious threat. If an attacker controls a trusted CA (or obtains a fraudulent certificate from one), they can generate valid-looking certificates for any domain.

## Modern Defences Against MITM

| Defence | How it helps |
|---|---|
| **HTTPS and TLS** | Encrypt data in transit and authenticate servers when certificate validation is performed correctly. |
| **HSTS** | Instructs browsers to use HTTPS for a domain and prevents insecure HTTP fallback after the policy is applied. |
| **HSTS preload** | Allows supported browsers to know in advance that a domain must use HTTPS. |
| **Certificate validation** | Checks that the certificate is trusted, valid for the requested hostname, and within its validity period. |
| **Certificate Transparency (CT)** | Provides publicly auditable logs of certificate issuance, helping detect suspicious or misissued certificates. |
| **Certificate or public-key pinning** | Restricts an application to an expected certificate or public key, although deployment and rotation require careful management. |
| **DANE** | Uses DNSSEC-protected DNS records to associate domain names with certificate or public-key information. |
| **Secure network configuration** | Reduces exposure through network segmentation, secure Wi-Fi, and protections against traffic redirection. |

**Important distinctions:**

- TLS provides encryption and integrity, along with server authentication when correctly configured and validated.
- Certificate Transparency improves visibility into certificate issuance; it does not itself prevent every fraudulent certificate from being used.
- Certificate pinning can strengthen trust decisions but is not universally deployed and must be maintained carefully.
- DANE depends on DNSSEC and compatible client and service support.

> Modern security mechanisms make MITM attacks significantly harder than they were a decade ago:

> HTTPS Everywhere: Most websites now use HTTPS by default. Major browsers mark HTTP sites as "Not Secure", and some have begun blocking mixed content entirely.

> HSTS (HTTP Strict Transport Security) tells browsers to only connect via HTTPS for a specified period. Once a browser has seen an HSTS header for a domain, it will refuse to connect over HTTP, preventing SSL stripping attacks. Many major sites are also on the HSTS preload list, meaning browsers ship with knowledge that these sites should only be accessed via HTTPS.

> Certificate Transparency (CT) requires CAs to log all issued certificates to public, auditable logs. This makes it much harder for attackers to obtain fraudulent certificates without detection. Browsers can check these logs and reject certificates that are not properly logged.

> Certificate Pinning allows applications to specify exactly which certificates or public keys are valid for their connections. This is common in mobile apps and prevents attacks even if a CA is compromised. However, it makes certificate rotation more complex.

> DANE (DNS-based Authentication of Named Entities) uses DNSSEC to publish certificate information in DNS records, providing an alternative trust path that does not rely solely on the CA system.

> Despite these protections, MITM attacks remain possible when users ignore certificate warnings, applications do not properly validate certificates, the target uses cleartext protocols, the attacker can compromise a trusted CA, internal networks lack encryption, or legacy systems do not support modern security features.

> MITM can also affect other cleartext protocols such as FTP, SMTP, and POP3. The fundamental mitigation requires the use of cryptography. The solution lies in proper authentication along with encryption or signing of exchanged messages. With the help of Public Key Infrastructure (PKI) and trusted root certificates, Transport Layer Security (TLS) protects against MITM attacks when properly implemented.

## Why MITM Attacks Still Succeed

MITM attacks may remain possible when:

- Applications use unencrypted protocols such as Telnet, HTTP, or unprotected email services.
- Users ignore certificate warnings.
- Applications do not correctly validate certificates or hostnames.
- Internal systems communicate without encryption.
- Network traffic can be redirected through ARP, DNS, or routing manipulation.
- A trusted CA or endpoint has been compromised.

Using HTTPS alone does not protect every connection if applications downgrade protocols, mishandle certificates, or send sensitive data through other unencrypted channels.

## Mitigation Best Practices

1. **Encrypt communications:** Use correctly configured TLS for web, email, and other supported services.
2. **Authenticate endpoints:** Validate certificates, hostnames, and trust chains; never disable validation to bypass errors.
3. **Enforce HTTPS:** Configure HSTS and remove insecure HTTP fallbacks where appropriate.
4. **Secure local networks:** Use strong Wi-Fi security, network segmentation, and access controls.
5. **Reduce legacy protocol exposure:** Replace insecure services and disable unnecessary LLMNR or NBT-NS where operationally feasible.
6. **Monitor network behaviour:** Investigate unexpected ARP changes, DNS responses, and routing anomalies.
7. **Protect sensitive transactions:** Verify transaction details and use application-level integrity and authentication controls where appropriate.

## Key Takeaways

- A MITM attack allows an attacker to intercept and potentially alter communication between two parties.
- ARP spoofing, DNS spoofing, rogue access points, and BGP hijacking are possible ways to redirect traffic.
- Bettercap, Ettercap, mitmproxy, and Responder support different forms of network security testing.
- TLS, correct certificate validation, and HSTS substantially reduce MITM risk.
- Encryption must be combined with authentication, integrity protection, secure configuration, and network monitoring for effective defence.

## Transport Layer Security (TLS)

## What Is TLS?

**Transport Layer Security (TLS)** is a cryptographic protocol that protects data exchanged between communicating systems. It helps prevent attackers from reading or modifying data in transit and authenticates the server when certificate validation is correctly performed.

TLS provides three important security properties:

- **Confidentiality:** Encrypts data so unauthorised parties cannot read it.
- **Integrity:** Detects unauthorised modification of transmitted data.
- **Authentication:** Helps verify the identity of the communicating server.

TLS helps protect against password sniffing and Man-in-the-Middle (MITM) attacks when implemented and configured correctly.

## SSL vs TLS

**SSL (Secure Sockets Layer)** was an earlier protocol developed to secure internet communications. TLS replaced SSL and introduced stronger security mechanisms.

| Protocol version | Status |
|---|---|
| SSL 2.0 and SSL 3.0 | Obsolete/deprecated and insecure; must not be used. |
| TLS 1.0 and TLS 1.1 | Deprecated; avoid using them. |
| TLS 1.2 (2008) | Secure when configured with modern cryptographic algorithms and settings. |
| TLS 1.3 (2018) | Modern standard with a simpler handshake and improved security. |

> SSL 2.0 and 3.0 are deprecated and considered insecure. They should never be used.

> TLS 1.0 and 1.1 were deprecated in 2021 due to known vulnerabilities. Major browsers no longer support them.

> TLS 1.2 (2008) remains widely used and is considered secure when properly configured with modern cipher suites.

> TLS 1.3 (2018) is the current standard. It removes outdated cryptographic algorithms, reduces handshake latency, and provides forward secrecy by default.

The term *SSL certificate* is still widely used, but modern websites generally use TLS certificates and TLS connections.

> You will still see the term "SSL" used colloquially (such as "SSL certificate"), but in practice, all modern systems use TLS. When someone says "SSL," they almost always mean TLS.

## Where TLS Fits in the Network Model

The common protocols covered so far send data in cleartext, making it possible for anyone with access to the network to capture, save, and analyse the exchanged messages. The image below shows the ISO/OSI network layers. Encryption can be added via the presentation layer. As a result, data will be presented in an encrypted format (ciphertext) instead of its original form.

<img width="800" height="400" alt="image" src="https://github.com/user-attachments/assets/b732f446-e16b-4e91-8aab-621784130b55" />

Protocols such as HTTP, FTP, SMTP, POP3, and IMAP define how applications communicate. TLS can protect the data exchanged by these protocols.

Conceptually, TLS sits between the application protocol and the transport layer when used over TCP. It does not map perfectly to one OSI layer.

For example, HTTPS combines HTTP with TLS:

- Without TLS, HTTP data can be readable to someone who can capture the traffic.
- With TLS, HTTP messages are encrypted before being transmitted over the network.

TLS protects data in transit; it does not automatically protect data stored on a device or prevent attacks against a compromised endpoint.

>It is worth noting that the OSI model is a conceptual simplification. In practice, TLS operates between the transport and application layers rather than mapping neatly to a single OSI layer. However, the diagram is useful for understanding that encryption sits below the application protocol, wrapping its data before transmission.

## Common Protocols and Their Secure Versions

### Upgrading Protocols with TLS

An existing cleartext protocol can be upgraded to use encryption via TLS. The following table lists the protocols covered so far and their default ports before and after the encryption upgrade via TLS.

| Application protocol | Default port without TLS | Secure version / configuration | Common secure port |
|---|---:|---|---:|
| HTTP | 80 | HTTPS | 443 |
| FTP | 21 | FTPS | 990 for implicit FTPS; explicit FTPS commonly starts on 21 |
| SMTP | 25 | SMTP with TLS | 465 for implicit TLS; 25 may support STARTTLS |
| SMTP submission | — | Submission with STARTTLS | 587 |
| POP3 | 110 | POP3S | 995 |
| IMAP | 143 | IMAPS | 993 |
| DNS | 53 | DNS over TLS (DoT) | 853 |
| DNS | 53 | DNS over HTTPS (DoH) | 443 |

Ports are defaults, and actual configurations may vary.

**Important distinctions:**

- **SFTP** transfers files over SSH; it is not FTP wrapped in TLS.
- **FTPS** is FTP protected with TLS.
- **DoT** encrypts DNS queries using TLS.
- **DoH** sends DNS queries over HTTPS.

Encrypted DNS reduces the ability of network observers to inspect DNS queries, although other traffic metadata may still reveal information about a user's activity.

## Implicit TLS vs STARTTLS

There are two common ways to establish TLS protection.

### Implicit TLS

TLS negotiation begins immediately when the connection is established.

Examples:

- HTTPS on TCP port 443
- IMAPS on TCP port 993
- POP3S on TCP port 995
- SMTP submission with implicit TLS on TCP port 465

### STARTTLS

The client first establishes a connection using the application protocol, then requests an upgrade to TLS.

For example, SMTP submission commonly uses port 587 with STARTTLS.

The connection must successfully upgrade to TLS before sensitive information is exchanged. If an application allows an attacker to remove the STARTTLS offer and silently continue without encryption, a downgrade attack may be possible.

**Best practice:** Configure clients and servers to require encryption where appropriate, and reject insecure fallback rather than silently sending credentials in cleartext.

## How HTTPS Works

HTTPS protects HTTP communication using TLS. A simplified connection sequence is:

1. **Establish a TCP connection** with the web server.
2. **Perform the TLS handshake** to negotiate security parameters, authenticate the server, and establish shared session keys.
3. **Exchange HTTP data** through the encrypted TLS connection.

This prevents passive observers from directly reading HTTP requests, responses, cookies, and credentials carried inside the TLS connection.

## The TLS Handshake

The TLS handshake establishes the parameters needed for secure communication.

<img width="925" height="395" alt="image" src="https://github.com/user-attachments/assets/41107ce7-db1a-4971-bcf5-9efadca74480" />

### Simplified TLS 1.2 handshake

1. **ClientHello:** The client sends supported TLS versions, cipher suites, and other negotiation information.
2. **ServerHello:** The server selects compatible connection parameters and provides its certificate and other handshake information as required.
3. **Key exchange:** The client and server establish shared key material using the negotiated mechanism.
4. **Handshake verification:** Both parties verify the handshake and begin protected communication.

The exact message sequence depends on the cipher suite and authentication method.

### TLS 1.3 improvements

- **Faster handshake:** A typical full handshake can complete in one round trip (1-RTT), compared with two round trips for a typical TLS 1.2 handshake.
- **Forward secrecy:** Supported key exchanges provide forward secrecy by default, so later compromise of the server's long-term private key does not normally reveal previously recorded sessions.
- **Simpler cryptography:** Obsolete algorithms and many legacy options have been removed.
- **More handshake encryption:** More handshake information is protected after key establishment.
- **0-RTT resumption:** Returning clients may send early data, but it can be replayed in some circumstances. Applications must account for this risk and avoid using early data for operations that must never be repeated.

Once the handshake succeeds, application data is encrypted and integrity-protected using negotiated symmetric session keys.

## Certificates and Trust

A TLS certificate binds a domain name or other identity to a public key. Certificates are generally issued and digitally signed by a Certificate Authority (CA) trusted by the client's operating system or application.

When visiting an HTTPS website, the browser checks several things, including:

1. **Identity:** Does the certificate cover the requested hostname?
2. **Trust chain:** Does the certificate chain lead to a trusted CA?
3. **Validity period:** Is the certificate currently valid?
4. **Other validation requirements:** Is the certificate properly formed and acceptable under the client's security rules?

If validation fails, the browser may display a security warning or block the connection.

A certificate does not encrypt data by itself. TLS uses the certificate and associated cryptographic mechanisms as part of establishing an authenticated, encrypted connection.

## The Modern Certificate Ecosystem

### Let's Encrypt

Let's Encrypt is a Certificate Authority that provides free, automated TLS certificates, making HTTPS accessible to websites without the cost of traditional paid certificates.

### Certificate Transparency (CT)

Certificate Transparency logs publicly record certificate issuance. These logs help domain owners and security researchers identify unexpected or suspicious certificates.

CT improves visibility but does not, by itself, guarantee that every misissued certificate will be rejected.

### Short-lived certificates

Shorter certificate lifetimes reduce the time a certificate remains usable if compromised and encourage automated renewal. Certificates must be renewed reliably to avoid service interruptions.

### ACME and Certbot

- **ACME (Automated Certificate Management Environment):** A protocol for automating certificate issuance and renewal.
- **Certbot:** A tool that can obtain and renew certificates from compatible CAs, including Let's Encrypt.

Automation reduces manual work and helps prevent certificates from expiring unexpectedly.

## Testing TLS Configurations

Security professionals can assess TLS configurations using the following tools.

| Tool | Purpose |
|---|---|
| **testssl.sh** | Checks supported TLS versions, cipher suites, certificates, and common configuration weaknesses. |
| **SSLyze** | Analyses TLS configurations and supports automated security testing. |
| **SSL Labs Server Test** | Provides a detailed assessment of publicly accessible HTTPS servers. |

```bash

```

Common issues to check include:

- Deprecated TLS versions.
- Weak or obsolete cipher suites.
- Invalid, expired, or hostname-mismatched certificates.
- Missing or incorrect certificate chains.
- Poorly configured key exchange.
- Insecure fallback to unencrypted communication.

Only test systems for which you have permission.

## Key Takeaways

- TLS provides confidentiality, integrity, and server authentication when correctly implemented.
- SSL is obsolete; modern systems should use TLS 1.2 or TLS 1.3.
- HTTPS is HTTP protected by TLS.
- Implicit TLS begins encryption immediately, while STARTTLS upgrades an existing application connection.
- Certificates help clients verify server identity, and trusted CAs form the foundation of certificate validation.
- TLS 1.3 improves handshake performance and removes many legacy cryptographic options.
- Tools such as testssl.sh, SSLyze, SSL Labs, and Nmap help identify TLS configuration weaknesses.'
