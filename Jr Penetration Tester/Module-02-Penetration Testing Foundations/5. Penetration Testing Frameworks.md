# Penetration Testing Frameworks

## Introduction

A **penetration testing framework** is a structured methodology that guides a penetration tester through the different stages of a security assessment.

Instead of performing random security checks, a framework provides a systematic process covering activities such as:

<pre>
Planning & Scoping
        ↓
Reconnaissance
        ↓
Enumeration
        ↓
Vulnerability Analysis
        ↓
Exploitation
        ↓
Post-Exploitation
        ↓
Reporting
        ↓
Remediation Validation
</pre>

The exact phases depend on the framework being used.

### Why Use a Framework ?

Without a structured methodology, a penetration test can become inconsistent and incomplete. A tester may:

* Miss important attack surfaces
* Perform tests in an unorganised manner
* Fail to document findings properly
* Test systems that are outside the agreed scope
* Produce results that are difficult for the client to act upon

A framework helps ensure that the assessment follows an established and repeatable process.

---

## Benefits of Penetration Testing Frameworks

### 1. Thoroughness

A structured methodology helps testers systematically cover the relevant attack surface and reduces the chance of overlooking important security issues.

### 2. Consistency

Using the same methodology allows different testers or teams to follow a comparable process and produce more consistent results.

### 3. Compliance

Some organisations need security assessments to align with specific standards, regulations, or industry requirements.

Frameworks can provide a recognised methodology for conducting and documenting these assessments.

### 4. Better Communication

A recognised methodology makes it easier for:

* Penetration testers
* Security teams
* Clients
* Auditors
* Management

to understand how the assessment was performed and how the findings were identified.

---

## 1. OSSTMM

**Open Source Security Testing Methodology Manual (OSSTMM)** provides a scientific and metrics-driven approach to security testing.

It focuses on measuring security through a structured testing methodology.

## 2. OWASP WSTG

**OWASP Web Security Testing Guide (WSTG)** is focused specifically on **web application security testing**.

It provides guidance for testing areas such as:

* Authentication
* Authorisation
* Session management
* Input validation
* Configuration
* Business logic
* Client-side security

This is particularly relevant when performing **Web Application VAPT**.

## 3. NIST SP 800-115

**NIST Special Publication 800-115** provides technical guidance for conducting information security testing and assessments.

It covers activities such as:

* Planning
* Discovery
* Attack and penetration
* Reporting

NIST publications are widely used as references for structured security assessment processes.

## 4. PTES

**Penetration Testing Execution Standard (PTES)** provides a practical, phase-driven approach to penetration testing.

Its methodology broadly follows the lifecycle of a real penetration testing engagement, from **pre-engagement interactions through reporting**.

## 5. ISSAF

**Information Systems Security Assessment Framework (ISSAF)** is a detailed security assessment methodology.

It provides structured guidance for assessing different areas of an organisation's security environment.

It is historically influential and includes a detailed assessment process.

## MITRE ATT&CK

**MITRE ATT&CK** is different from a traditional end-to-end penetration testing framework.

It is a knowledge base that documents **adversary tactics and techniques** based on real-world observations.

It can complement penetration testing by helping testers understand and map attacker behaviour.

<pre>
Penetration Testing Framework
            +
      MITRE ATT&CK
            ↓
Better Understanding of
Adversary Techniques
</pre>

<pre>

        ↓

## OSSTMM

## Overview

**OSSTMM (Open Source Security Testing Methodology Manual)** is a security testing methodology developed by the **Institute for Security and Open Methodologies (ISECOM)**.

Its main philosophy is:

> **Measure security instead of relying only on subjective opinions.**

OSSTMM applies a more **scientific, quantitative, repeatable, and verifiable** approach to security testing.

Instead of simply reporting that a system is "secure" or "insecure", OSSTMM focuses on measuring the target's **attack surface, exposure, and effectiveness of security controls**.

---

## Five Security Channels

OSSTMM divides security testing into **five channels**. This ensures that testing is not limited to network infrastructure alone.

| Channel     | Focus                   | Examples                                           |
| ----------- | ----------------------- | -------------------------------------------------- |
| **HUMSEC**  | Human Security          | Social engineering, human-factor weaknesses        |
| **PHYSSEC** | Physical Security       | Physical access, badge systems, tailgating         |
| **SPECSEC** | Wireless Communications | Wi-Fi, Bluetooth, RFID, electromagnetic signals    |
| **COMSEC**  | Telecommunications      | VoIP, phone systems, fax, modems                   |
| **DATASEC** | Data Networks           | Network services, firewalls, application protocols |

### 1. HUMSEC - Human Security

Focuses on vulnerabilities involving people.

Examples:

* Social engineering
* Credential disclosure
* Weak security awareness
* Manipulation of employees

### 2. PHYSSEC - Physical Security

Evaluates physical controls protecting systems and facilities.

Examples:

* Badge readers
* Physical access controls
* Server-room security
* Tailgating

### 3. SPECSEC - Wireless Communications

Covers wireless and electromagnetic communication technologies.

Examples:

* Wi-Fi
* Bluetooth
* RFID
* Other wireless signals

### 4. COMSEC - Telecommunications

Focuses on telecommunications infrastructure.

Examples:

* Phone systems
* VoIP
* Fax systems
* Modems

### 5. DATASEC - Data Networks

Focuses on traditional network and application-layer security.

Examples:

* Network services
* Firewalls
* Network protocols
* Application-layer protocols

### Why Five Channels ?

An organisation may have strong network security but still be vulnerable through another channel.

For example :

<pre>
Strong Network Security
        ↓
But...
        ↓
Employee → Social Engineering
        OR
Physical Access → Tailgating
        ↓
Security Controls Bypassed
</pre>

The five-channel model encourages testers to consider the **complete attack surface**.

---

## Risk Assessment Values (RAVs)

A key part of OSSTMM's quantitative approach is the **Risk Assessment Value (RAV)**.

RAV is used to measure the relationship between :

* **Attack surface / exposure**
* **Security controls**

Conceptually :

<pre>
Attack Surface / Exposure
           ↕
     Security Controls
           ↓
          RAV
</pre>

A **positive RAV** indicates residual exposure or risk remains.

A RAV **close to zero** indicates that the security controls are more closely matched to the measured exposure.

The purpose of using numerical measurements is to make security assessments more:

* Repeatable
* Verifiable
* Auditable
* Comparable

---

## OSSTMM Testing Phases

The OSSTMM testing cycle can be divided into **four phases**:

<pre>
Induction
   ↓
Interaction
   ↓
Inquiry
   ↓
Intervention
</pre>

<pre>
The OSSTMM testing cycle has four phases. Let's walk through them using a scenario: your team is assessing the external network of FinVault Corp, a financial services company, scoped to 10.0.113.0/24 and their customer portal at portal.finvault-corp.thm.

Phase 1: Induction covers enumeration and verification. You map what exists and confirm it is real. At FinVault, you query DNS, review certificate transparency logs, and discover subdomains like vpn.finvault-corp.thm and mail.finvault-corp.thm. You then verify each asset is live and responsive. The output is a confirmed inventory of the target environment.

Phase 2: Interaction covers qualification and quantification. You actively probe the verified assets and assess their relevance. At FinVault, you connect to each service, fingerprint its technology, and quantify the exposure: 12 externally reachable services across 8 hosts, 4 of which accept unauthenticated connections. These findings feed directly into the attack surface calculation.

Phase 3: Inquiry covers privilege escalation and verification escalation. You test whether the measured exposure can be converted into unauthorized access. At FinVault, you discover an IDOR vulnerability in the customer portal that allows one authenticated user to read another customer's account statements. Verification escalation confirms the scope: read access to 12,000 accounts, no write access.

Phase 4: Intervention covers quarantine, audit, and enticement. You address findings and examine the broader control environment. At FinVault, the vulnerable endpoint is restricted. At the same time, a patch is developed (quarantine), the wider access control model is examined for similar flaws (audit), and a canary token is deployed to test internal detection capabilities (enticement).
</pre>

---

## Phase 1 : Induction

**Induction** focuses on **enumeration and verification**.

The tester identifies what exists within the defined scope and verifies that the discovered assets are real and responsive.

Typical activities may include:

* DNS enumeration
* Certificate transparency review
* Subdomain discovery
* Asset discovery
* Service verification

### Output

A **confirmed inventory of the target environment**.

<pre>
Discover Assets
      ↓
Verify Assets
      ↓
Confirmed Target Inventory
</pre>

---

## Phase 2 : Interaction

**Interaction** focuses on **qualification and quantification** of the verified assets.

The tester actively interacts with the discovered systems to understand their technologies, services, and exposure.

Activities may include:

* Connecting to services
* Technology fingerprinting
* Service enumeration
* Measuring exposed services
* Assessing accessibility

The results contribute to understanding the target's **attack surface**.

<pre>
Verified Assets
      ↓
Active Probing
      ↓
Service / Technology Identification
      ↓
Quantify Exposure
</pre>

---

## Phase 3 : Inquiry

**Inquiry** focuses on determining whether the measured exposure can be converted into **unauthorised access or increased privileges**.

Testing may involve :

* Exploitation
* Privilege escalation
* Access-control testing
* Verification of discovered vulnerabilities
* Determining the actual impact of a vulnerability

For example, an IDOR vulnerability might allow one authenticated user to access another user's information.

The tester then verifies the **actual scope of access** rather than simply reporting that an IDOR exists.

<pre>
Identified Exposure
        ↓
Attempt Exploitation
        ↓
Verify Access
        ↓
Determine Actual Impact
</pre>

---

## Phase 4 : Intervention

**Intervention** focuses on **quarantine, audit, and enticement**.

### Quarantine

Address or isolate a discovered security issue and evaluate the effectiveness of the response.

### Audit

Examine the wider environment to determine whether similar weaknesses exist elsewhere.

### Enticement

Use controlled mechanisms to test whether security monitoring and detection capabilities respond to attacker activity.

For example, a **canary token** can be used to determine whether unauthorised access triggers an alert.

<pre>
Identify Weakness
      ↓
Quarantine / Address
      ↓
Audit Wider Environment
      ↓
Test Detection
</pre>

---

## OSSTMM Reporting

OSSTMM uses the **Security Test Audit Report (STAR)** format for reporting.

The standardised reporting approach helps provide:

* Consistent documentation
* Auditable results
* Repeatable assessments
* Easier comparison between assessments or teams

---

## Strengths and Limitations

| Aspect         | OSSTMM                                                |
| -------------- | ----------------------------------------------------- |
| Approach       | Scientific and measurement-driven                     |
| Focus          | Broad security testing                                |
| Key concept    | Quantification and RAVs                               |
| Coverage       | Human, physical, wireless, telecom, and data networks |
| Reporting      | STAR                                                  |
| Main advantage | Repeatable and auditable measurements                 |
| Challenge      | Steep learning curve                                  |
| Challenge      | Can require significant time and expertise            |

## Key Takeaways

* **OSSTMM** stands for **Open Source Security Testing Methodology Manual**.
* It was developed by **ISECOM**.
* Its core philosophy is **metrics over subjective opinions**.
* OSSTMM considers five security channels: **HUMSEC, PHYSSEC, SPECSEC, COMSEC, and DATASEC**.
* **RAVs (Risk Assessment Values)** provide a quantitative way to assess exposure and security controls.
* The four major testing phases are:

  1. **Induction** - enumeration and verification
  2. **Interaction** - qualification and quantification
  3. **Inquiry** - privilege/access testing and verification
  4. **Intervention** - quarantine, audit, and enticement
* OSSTMM uses the **STAR** format for security test reporting.
* Its measurement-driven approach makes assessments more **repeatable, auditable, and comparable**.

## OWASP WSTG

## Overview

**OWASP WSTG (Web Security Testing Guide)** is a comprehensive framework for testing the security of **web applications and web services**.

It is maintained by the **Open Web Application Security Project (OWASP)**.

While the **OWASP Top 10** provides a high-level list of common and critical web application security risks, the **WSTG provides detailed testing procedures** for identifying those vulnerabilities.

### WSTG vs OWASP Top 10

<pre>
OWASP Top 10
     ↓
What are the major web security risks?

OWASP WSTG
     ↓ 
How do we systematically test for them ?
</pre>

The WSTG contains **90+ test cases** organised into different categories covering the major attack surfaces of modern web applications.

---

## WSTG Testing Categories

The WSTG covers areas including:

1. Information Gathering
2. Configuration and Deployment Management
3. Identity Management
4. Authentication
5. Authorization
6. Session Management
7. Input Validation
8. Error Handling
9. Cryptography
10. Business Logic
11. Client-Side Testing
12. API Testing

This broad coverage helps testers avoid focusing on only obvious areas such as login forms or search functionality.

---

## Test Case IDs

WSTG provides identifiers for individual test cases.

For example:

<pre>
WSTG-INPV-01
</pre>

The identifier tells the tester which category and specific test case is being referenced.

Test cases provide practical guidance about:

* What should be tested
* How to perform the test
* What behaviour to look for
* How to identify security weaknesses

This makes findings easier to document and reproduce.

---

## Risk-Based Testing

The WSTG follows a **risk-based approach**.

Testing should not simply become a checklist where every item receives equal attention. Testers should consider:

* **Exploitability** - How easily can the weakness be exploited?
* **Impact** - What could happen if it is exploited?
* **Application context** - How important is the affected functionality?
* **Attack surface** - Which components are exposed?

For example, a vulnerability affecting a payment API may require more attention than a low-impact issue affecting a non-sensitive feature.

<pre>
Vulnerability
      ↓
Exploitability + Impact
      ↓
Risk Understanding
      ↓
Prioritise Testing / Remediation
</pre>

---

## WSTG Across the SDLC

One important characteristic of the WSTG is that security testing is not limited to the final penetration test.

It can be applied throughout the **Software Development Life Cycle (SDLC)**.

<pre>
Planning
   ↓
Definition & Design
   ↓
Development
   ↓
Deployment
   ↓
Maintenance & Operations
</pre>

<pre>
Let's see how this works for our online retailer, ShopSecure Inc., which is building a new customer portal.

Phase 1: Before development begins. Security requirements and regulatory obligations are established upfront. For ShopSecure, this means defining that the portal must comply with PCI DSS (since it processes payments) and establishing measurable criteria, such as the maximum acceptable time for patching vulnerabilities.

Phase 2: During definition and design. The application architecture is reviewed for security flaws before any code is written. ShopSecure's team creates threat models for the payment flow, identifying that the checkout API will be a high-value target and designing rate-limiting and input validation controls from the start.

Phase 3: During development. Code is vetted through walkthroughs and reviews. ShopSecure's developers review the authentication module against WSTG test cases for credential handling (WSTG-ATHN), identifying a flaw in which password reset tokens do not expire.

Phase 4: During deployment. Security controls are verified in the production environment. ShopSecure's team runs a penetration test against the staged application, verifying that default credentials have been changed, that TLS is properly configured, and that no debug endpoints are exposed.

Phase 5: During maintenance and operations. Security is maintained post-launch through periodic health checks, especially after updates. When ShopSecure pushes a new product recommendation feature three months later, the relevant WSTG test cases are re-executed to ensure the update has not introduced new vulnerabilities.        
</pre>

---

## Phase 1 : Planning

Security requirements should be established **before development begins**.

Activities may include:

* Identifying security requirements
* Understanding regulatory requirements
* Defining security objectives
* Establishing measurable security criteria

For example, an application processing payment information may need to consider **PCI DSS** requirements.

---

## Phase 2 : Definition and Design

Security is considered while designing the application's architecture.

Important activities include:

* Architecture review
* Threat modelling
* Identifying high-value components
* Designing security controls

For example, a payment API may be identified as a high-value target.

Security controls such as:

* Rate limiting
* Input validation
* Strong authentication
* Access controls

can then be designed into the application from the beginning.

---

## Phase 3 : Development

Security testing continues while the application is being developed.

Activities can include:

* Code review
* Security walkthroughs
* Reviewing authentication mechanisms
* Testing input validation
* Checking security requirements against implementation

For example, testing an application's password-reset functionality may reveal that reset tokens do not expire properly.

---

## Phase 4 : Deployment

Security controls are verified when the application is deployed.

Testing may include:

* Penetration testing
* Configuration testing
* TLS configuration checks
* Default credential checks
* Debug endpoint discovery
* Deployment configuration review

The goal is to ensure that security controls work correctly in the actual deployed environment.

---

## Phase 5 : Maintenance and Operations

Security testing continues **after the application goes live**.

Applications change over time, so new features and updates can introduce new vulnerabilities.

Testing should therefore be repeated after significant changes.

<pre>
Application Update
       ↓
Identify Affected Components
       ↓
Re-run Relevant Security Tests
       ↓
Verify No New Vulnerabilities
</pre>

For example, if a new product recommendation feature is added, the relevant security tests should be performed again.

---

## Strengths of OWASP WSTG

### 1. Comprehensive Coverage

The WSTG covers a wide range of web application security areas rather than focusing on only a few common vulnerabilities.

### 2. Practical Testing Guidance

It provides specific test cases and procedures, making it useful for hands-on penetration testing.

### 3. Community Driven

The guide is maintained and improved by the global security community.

### 4. Modern Web Application Support

Its testing approach can be applied to modern architectures such as:

* APIs
* Single-page applications (SPAs)
* Microservices
* Traditional web applications

---

## Limitations

### 1. Large Scope

Testing every available WSTG test case can require significant time and resources.

### 2. Specialised Knowledge

Some areas require deeper expertise, particularly:

* Cryptography
* Business logic
* Complex application architectures
* Advanced client-side testing

### 3. Checklist Mentality

A tester should not blindly execute every test case without understanding the application's architecture and risk.

<pre>
WSTG Checklist
      +
Application Understanding
      +
Security Expertise
      ↓
Effective Web Application Testing
</pre>

The WSTG should therefore be treated as a **structured foundation**, not a replacement for professional judgement and manual analysis.

---

## WSTG in a Web VAPT

For a web application penetration test, the WSTG can provide the testing structure :

<pre>
Information Gathering
        ↓
Configuration Testing
        ↓
Identity & Authentication
        ↓
Authorization
        ↓
Session Management
        ↓
Input Validation
        ↓
Business Logic
        ↓
Client-Side Testing
        ↓
API Testing
        ↓
Reporting
</pre>

This makes the WSTG particularly useful when performing **Web Application VAPT** because it helps ensure that major security areas are systematically evaluated.

## Key Takeaways

* **OWASP WSTG** stands for **OWASP Web Security Testing Guide**.
* It provides detailed guidance for **web application security testing**.
* Unlike the OWASP Top 10, which is a high-level risk awareness document, the WSTG provides **specific testing procedures**.
* It contains **90+ test cases** across areas such as authentication, authorization, session management, input validation, business logic, client-side security, and APIs.
* WSTG test cases use identifiers such as `WSTG-INPV-01`.
* The methodology follows a **risk-based approach** rather than treating every issue equally.
* Security testing can be integrated throughout the **SDLC**, from planning through maintenance.
* Its major strengths are **comprehensive coverage, practical test cases, and community-driven updates**.
* A complete implementation can be resource-intensive, and testers should avoid treating the WSTG as a purely mechanical checklist.
* For web application pentesting, **WSTG is one of the most useful structured references for organising security testing**.

## NIST SP 800-115

## Overview

**NIST SP 800-115 (Technical Guide to Information Security Testing and Assessment)** is a security testing and assessment framework published by the **National Institute of Standards and Technology (NIST)**.

It was developed for the U.S. federal environment but its principles are also widely applicable to enterprises and other organisations.

Unlike frameworks focused specifically on penetration testing, NIST SP 800-115 covers a **broader range of security assessment techniques**.

These include:

* Documentation and policy reviews
* Configuration reviews
* Log analysis
* Vulnerability scanning
* Vulnerability validation
* Penetration testing

The main idea is to determine whether security controls are working as intended and whether weaknesses can actually be exploited.

---

## Core Objectives

NIST SP 800-115 focuses on three major objectives:

### 1. Identify Vulnerabilities

Find weaknesses in:

* Systems
* Networks
* Applications
* Configurations
* Security controls

### 2. Validate Security Controls

Determine whether security controls actually work as expected.

For example:

<pre>
Security Control
      ↓
Security Test
      ↓
Expected Behaviour?
      ↓
Yes → Control Working
No  → Potential Weakness
</pre>

### 3. Assess Exploitability

Determine whether an identified vulnerability can actually be exploited under realistic attack conditions.

Finding a vulnerability is different from proving that it can be exploited.

---

## NIST SP 800-115 Phases

The methodology can be understood through three major phases:

<pre>
Planning
   ↓
Execution
   ↓
Post-Testing
</pre>

---

## Phase 1 : Planning

Before any testing begins, the assessment must be properly defined.

Important planning activities include:

* Define objectives
* Define scope
* Identify systems and networks
* Establish rules of engagement
* Define testing windows
* Establish communication procedures
* Define emergency stop conditions
* Identify responsible stakeholders

### Example

Suppose an organisation has:

<pre>
Internet-Facing Portal
Internal Network
Classified Network
</pre>

The assessment might specify:

<pre>
In Scope:
✓ Internet-facing portal
✓ Supporting backend systems

Out of Scope:
✗ Classified network
</pre>

Clearly defining scope helps prevent accidental testing of systems that were not authorised for the engagement.

### Output

The planning phase produces a **formal test plan** that defines how the assessment will be conducted.

---

## Phase 2: Execution

This is where the actual security testing takes place.

NIST SP 800-115 groups testing activities into four major technique categories:

<pre>
Review Techniques
       ↓
Target Identification & Analysis
       ↓
Target Vulnerability Validation
       ↓
Penetration Testing
</pre>

### 1. Review Techniques

Review techniques involve examining existing information and configurations.

Examples:

* Security policies
* System documentation
* Network diagrams
* Firewall rules
* Access control lists
* System configurations
* Logs

The goal is to identify security weaknesses without necessarily interacting aggressively with the target.

### 2. Target Identification and Analysis

This involves discovering and analysing the target environment.

Activities may include:

* Host discovery
* Port scanning
* Service enumeration
* Technology fingerprinting
* Network mapping

For example:

<pre>
Target Network
      ↓
Discover Hosts
      ↓
Identify Open Ports
      ↓
Identify Services
      ↓
Fingerprint Technologies
</pre>

The result is a better understanding of the target's attack surface.

### 3. Target Vulnerability Validation

Vulnerability scanning can produce **false positives**.

Therefore, identified vulnerabilities should be validated where appropriate.

For example:

<pre>
Scanner
   ↓
Potential SQL Injection
   ↓
Manual Validation
   ↓
Confirmed / False Positive
</pre>

Validation determines whether the reported weakness actually exists and helps establish its real impact.

### 4. Penetration Testing

Penetration testing goes further by simulating realistic attacks against identified weaknesses.

The goal is to determine:

* Whether vulnerabilities can be exploited
* What level of access can be obtained
* What systems or data could be affected
* How multiple vulnerabilities can be chained together

For example:

<pre>
Vulnerability
      ↓
Exploitation
      ↓
Privilege Escalation
      ↓
Additional Access
      ↓
Demonstrate Impact
</pre>

NIST SP 800-115 does **not** require every assessment to reach full penetration testing.

The appropriate techniques depend on the assessment's objectives, scope, and rules of engagement.

---

## Phase 3: Post-Testing

After testing is complete, the results are analysed and documented.

Activities include:

* Analyse findings
* Validate evidence
* Prioritise risks
* Map findings to affected controls
* Develop remediation recommendations
* Prepare the final report

### Actionable Findings

A good finding should provide more than simply naming a vulnerability.

For example:

<pre>
Weak:
"SQL Injection exists."

Better:
"The `search` parameter is vulnerable to SQL injection.
An attacker can manipulate the parameter to access
database information. Input validation and parameterised
queries should be implemented."
</pre>

A useful finding should explain:

* **What** is vulnerable
* **Where** it is vulnerable
* **How** it can be exploited
* **What** could be affected
* **How** to remediate it

---

## NIST Testing Progression

The execution techniques can be viewed as a progression from lower-impact assessment activities toward active exploitation.

<pre>
Review
  ↓
Target Identification
  ↓
Vulnerability Validation
  ↓
Penetration Testing
</pre>

Not every engagement needs to perform every stage.

The required level of testing should depend on the **assessment objectives and authorised scope**.

---

## Strengths and Limitations

| Aspect         | NIST SP 800-115                                |
| -------------- | ---------------------------------------------- |
| Type           | Security testing and assessment guidance       |
| Scope          | Broad security assessment                      |
| Main focus     | Identify vulnerabilities and validate controls |
| Testing        | Review → Discovery → Validation → Pentesting   |
| Major strength | Flexible and widely recognised                 |
| Major strength | Supports structured and repeatable assessments |
| Limitation     | Guidance rather than a regulation              |
| Limitation     | Requires skilled security professionals        |

### Strengths

* **Flexible:** Can be applied to different environments and technologies.
* **Broad:** Covers more than just penetration testing.
* **Structured:** Provides a systematic assessment process.
* **Widely recognised:** NIST publications are commonly referenced by government and enterprise security teams.
* **Tool-independent:** Focuses on testing techniques rather than requiring a specific toolset.

### Limitations

* It is **guidance**, not a regulation by itself.
* It does not automatically impose testing frequencies or penalties.
* Effective implementation requires testers with a broad range of skills.
* Organisations may still need other standards or regulatory requirements depending on their environment.

---

## NIST SP 800-115 vs OWASP WSTG

These frameworks serve different purposes:

|                  | NIST SP 800-115                           | OWASP WSTG                       |
| ---------------- | ----------------------------------------- | -------------------------------- |
| Primary focus    | General security testing                  | Web application security         |
| Scope            | Broad                                     | Web applications                 |
| Testing approach | Review, discovery, validation, pentesting | Detailed web security test cases |
| Useful for       | Enterprise/security assessments           | Web VAPT                         |
| Application      | Networks, systems, applications, etc.     | Web applications and APIs        |

They can also be used together.

<pre>
NIST SP 800-115
General Assessment Methodology
          +
OWASP WSTG
Web Application Testing
          ↓
More Complete Web Security Assessment
</pre>

## Key Takeaways

* **NIST SP 800-115** stands for **Technical Guide to Information Security Testing and Assessment**.
* It is broader than a traditional penetration testing framework.
* Its three major phases are **Planning, Execution, and Post-Testing**.
* Execution includes:

  1. **Review techniques**
  2. **Target identification and analysis**
  3. **Target vulnerability validation**
  4. **Penetration testing**
* Vulnerability validation helps distinguish **real vulnerabilities from false positives**.
* Penetration testing determines whether identified weaknesses can produce meaningful impact.
* The framework emphasises **actionable findings and remediation guidance**.
* NIST SP 800-115 is **guidance rather than a regulation**.
* It is useful for broad security assessments, while **OWASP WSTG** is specifically focused on web application security testing.

## PTES

## Overview

**PTES (Penetration Testing Execution Standard)** is a practical methodology designed to describe how a real-world penetration testing engagement should be conducted **from beginning to end**.

PTES focuses primarily on the **flow of the engagement**, rather than only defining vulnerabilities or measurement techniques.

It is especially useful for understanding what happens throughout a typical penetration test:

<pre>
Client Engagement
       ↓
Planning & Scoping
       ↓
Reconnaissance
       ↓
Threat Modeling
       ↓
Vulnerability Analysis
       ↓
Exploitation
       ↓
Post-Exploitation
       ↓
Reporting
</pre>

PTES consists of **seven phases**.

---

## Seven PTES Phases

<pre>
1. Pre-Engagement Interactions
              ↓
2. Intelligence Gathering
              ↓
3. Threat Modeling
              ↓
4. Vulnerability Analysis
              ↓
5. Exploitation
              ↓
6. Post-Exploitation
              ↓
7. Reporting
</pre>

---

## Phase 1 : Pre-Engagement Interactions

This phase occurs **before any security testing begins**.

The tester and client establish exactly how the engagement will be conducted.

Important activities include:

* Define scope
* Identify authorised targets
* Define testing windows
* Establish rules of engagement
* Identify emergency contacts
* Define communication procedures
* Obtain written authorisation

### Scope

The scope specifies exactly what the tester is authorised to test.

For example:

<pre>
In Scope:
✓ Corporate network
✓ Patient portal
✓ Company wireless networks

Out of Scope:
✗ Third-party systems
✗ Unauthorised networks
✗ Production systems outside the agreement
</pre>

Clear scope is essential because testing systems without authorisation can create **legal, operational, and professional problems**.

### Key Idea

> **Never begin a penetration test without clearly defined scope and authorisation.**

---

## Phase 2 : Intelligence Gathering

The tester collects information about the target environment.

Both **passive and active reconnaissance** may be used depending on the agreed scope.

### Passive Reconnaissance

The tester gathers information without directly interacting with the target infrastructure.

Examples:

* Public employee information
* Email addresses
* Certificate transparency records
* Public documentation
* Job postings
* Technology information

### Active Reconnaissance

The tester directly interacts with authorised target systems.

Examples:

* DNS enumeration
* Network scanning
* Service enumeration
* Host discovery

<pre>
Passive Recon
      +
Active Recon
      ↓
Target Intelligence
</pre>

The gathered information helps guide the later phases.

---

## Phase 3 : Threat Modeling

**Threat modeling** identifies:

* Valuable assets
* Potential attackers
* Likely attack paths
* Security weaknesses that could lead to those assets

Instead of testing everything randomly, the tester uses the gathered intelligence to determine **which attack paths are most relevant**.

Example:

<pre>
Employee Workstation
        ↓
Credential Compromise
        ↓
Internal Network
        ↓
Database
        ↓
Sensitive Records
</pre>

Another possible path could be:

<pre>
Web Application
      ↓
Web Vulnerability
      ↓
Application Server
      ↓
Backend Database
</pre>

Threat modeling helps testers prioritise their efforts based on **realistic attack paths and valuable assets**.

---

## Phase 4 : Vulnerability Analysis

The tester identifies vulnerabilities that could enable the attack paths identified during threat modeling.

Activities may include:

* Vulnerability scanning
* Service enumeration
* Configuration analysis
* Manual testing
* Version identification
* Vulnerability research
* Manual validation

Automated scanners can identify potential vulnerabilities, but findings should be manually verified when appropriate.

<pre>
Automated Scan
      ↓
Potential Vulnerability
      ↓
Manual Verification
      ↓
Confirmed Vulnerability
</pre>

This helps reduce **false positives**.

---

## Phase 5 : Exploitation

In this phase, the tester attempts to exploit **confirmed vulnerabilities** within the authorised scope.

The purpose is not simply to obtain as many shells as possible.

Instead, exploitation should demonstrate **meaningful security impact**.

<pre>
Confirmed Vulnerability
        ↓
Controlled Exploitation
        ↓
Gain Access
        ↓
Demonstrate Impact
</pre>

For example, exploiting a web vulnerability may allow the tester to gain access to an application server and demonstrate access to sensitive backend data.

### Key Principle

> **Exploit to demonstrate impact, not simply to "pop boxes."**

Testing should remain controlled and aligned with the rules of engagement.

---

## Phase 6 : Post-Exploitation

After gaining access, the tester determines **what the compromised system allows an attacker to do**.

Activities may include:

* Privilege assessment
* Credential discovery
* Internal network discovery
* Lateral movement
* Accessing sensitive resources
* Pivoting to other systems
* Demonstrating business impact

Example:

<pre>
Initial Compromise
       ↓
Privilege / Credential Discovery
       ↓
Internal Network Access
       ↓
Lateral Movement
       ↓
Sensitive System
       ↓
Demonstrate Impact
</pre>

### Technical Finding → Business Impact

Post-exploitation helps translate technical access into meaningful consequences.

For example:

<pre>
Technical:
"Obtained shell on application server."

        ↓

Impact :
"Used the compromised server to access
sensitive customer records."
</pre>

The second statement provides much more useful information to the organisation because it explains **what the compromise actually enables**.

---

## Phase 7 : Reporting

The final phase is **reporting**.

The report should communicate the findings clearly to both technical and non-technical audiences.

### Executive Summary

Designed for:

* Management
* Executives
* Business stakeholders

It focuses on:

* Overall security findings
* Business impact
* Major risks
* High-level remediation priorities

### Technical Report

Designed for:

* Security teams
* System administrators
* Developers
* IT teams

It should contain details such as:

* Affected systems
* Vulnerability description
* Exploitation steps
* Evidence
* Screenshots
* Technical impact
* Remediation recommendations

<pre>
Technical Testing
       ↓
Findings & Evidence
       ↓
Risk / Impact Analysis
       ↓
Executive Report + Technical Report
       ↓
Remediation
</pre>

---

## PTES Strengths

### 1. Practical End-to-End Workflow

PTES closely follows the actual lifecycle of a penetration testing engagement.

### 2. Strong Pre-Engagement Guidance

It places significant importance on:

* Scope
* Authorisation
* Rules of engagement
* Communication
* Testing constraints

This is especially important for preventing accidental out-of-scope activity.

### 3. Useful for Beginners

The seven phases provide a clear mental model for understanding how a penetration test progresses.

### 4. Business-Focused Exploitation

PTES encourages testers to demonstrate **real impact**, rather than stopping after obtaining initial access.

---

## Limitations

### 1. Older Technical Guidance

Some of the detailed technical guidance and tool references are older and may not reflect current tools or techniques.

The overall methodology remains useful, but current documentation should be consulted for modern tooling.

### 2. Less Quantitative

Unlike OSSTMM, PTES does not focus heavily on quantitative security measurements.

Results therefore depend more on the tester's analysis and judgement.

---

## PTES vs Other Frameworks

| Framework           | Main Focus                                        |
| ------------------- | ------------------------------------------------- |
| **OSSTMM**          | Quantitative, measurement-driven security testing |
| **OWASP WSTG**      | Detailed web application security testing         |
| **NIST SP 800-115** | Broad security testing and assessment             |
| **PTES**            | Practical end-to-end penetration testing workflow |

These frameworks can complement each other.

For example :

<pre>
PTES
  ↓
Engagement Workflow
  +
OWASP WSTG
  ↓
Web Application Testing
  +
MITRE ATT&CK
  ↓
Adversary Techniques
</pre>

## Key Takeaways

* **PTES** stands for **Penetration Testing Execution Standard**.
* It focuses on the **end-to-end workflow of a penetration testing engagement**.
* PTES has **seven phases**:

  1. Pre-Engagement Interactions
  2. Intelligence Gathering
  3. Threat Modeling
  4. Vulnerability Analysis
  5. Exploitation
  6. Post-Exploitation
  7. Reporting
* **Scope and written authorisation** should be established before testing begins.
* Threat modeling helps testers focus on realistic attack paths rather than random testing.
* Vulnerabilities should be **validated before exploitation** where appropriate.
* Exploitation should demonstrate **meaningful security impact**.
* Post-exploitation translates technical access into **real-world business impact**.
* Reporting should serve both **technical and executive audiences**.
* PTES is particularly useful for understanding the **practical lifecycle of a real penetration testing engagement**.

## Penetration Testing Frameworks - ISSAF

## Overview

**ISSAF (Information Systems Security Assessment Framework)** is an open-source penetration testing framework developed by the **Open Information Systems Security Group (OISSG)**.

The latest known version, **ISSAF v0.2.1**, dates from around 2006 and is **no longer actively maintained**. Because its technical guidance is outdated, ISSAF should not be treated as a modern tool or exploit reference.

Its main value today is its **assessment methodology and adversarial progression**.

ISSAF covers multiple security areas:

* Network infrastructure
* Host systems
* Web applications
* Databases
* Social engineering

It uses a **risk-based approach**, focusing attention on vulnerabilities that are both exploitable and capable of causing significant impact.

---

## ISSAF Assessment Structure

ISSAF divides an assessment into three major phases:

<pre>
Planning & Preparation
          ↓
       Assessment
          ↓
Reporting & Cleanup
</pre>

The **Assessment phase** contains the framework's well-known **nine-step model**.

---

## Phase 1 : Planning and Preparation

This phase establishes the boundaries and conditions of the engagement.

Typical activities include:

* Defining the scope
* Identifying target systems
* Establishing rules of engagement
* Setting communication and escalation procedures
* Identifying emergency contacts
* Defining testing restrictions
* Selecting appropriate testing tools
* Identifying production systems that require extra care

### Example

A client may authorize testing of:

* Corporate network
* Git server
* Web application

while restricting disruptive testing against production systems during business hours.

---

## Phase 2 : Assessment

This is the core of ISSAF.

The nine steps represent an attack progression where each stage builds upon information or access obtained during the previous stage.

<pre>
1. Information Gathering
          ↓
2. Network Mapping
          ↓
3. Vulnerability Identification
          ↓
4. Penetration
          ↓
5. Access & Privilege Escalation
          ↓
6. Further Enumeration
          ↓
7. Lateral Movement
          ↓
8. Maintaining Access
          ↓
9. Covering Tracks
</pre>

### 1. Information Gathering

Collect information about the target from available sources.

Examples:

* DNS records
* WHOIS information
* Public employee information
* Technology references
* Public documentation
* Job postings

#### Goal

Build an initial understanding of the organization's infrastructure, technologies, and potential attack surface.

### 2. Network Mapping

Identify reachable systems and understand the network topology.

Typical targets may include:

* Web servers
* VPN gateways
* Mail servers
* Git servers
* CI/CD servers
* Developer workstations

#### Goal

Determine **what systems exist and how they are connected**.

### 3. Vulnerability Identification

Analyze discovered systems for security weaknesses.

This may involve:

* Vulnerability scanning
* Service analysis
* Configuration review
* Version identification
* Manual validation

#### Example

A CI/CD server may expose an administrative interface without authentication, creating a potential initial-access vector.

### 4. Penetration

Attempt controlled exploitation of confirmed vulnerabilities.

The purpose is to determine whether a discovered weakness can actually provide access or produce meaningful impact.

<pre>
Identified Vulnerability
          ↓
   Controlled Exploitation
          ↓
      Initial Access
</pre>

### 5. Gaining Access and Privilege Escalation

After obtaining initial access, attempt to increase privileges within the authorized scope.

This can involve:

* Credential discovery
* Misconfigured permissions
* Weak service accounts
* Local privilege escalation
* Access to privileged resources

<pre>
Initial Access
      ↓
Credential / Permission Discovery
      ↓
Privilege Escalation
      ↓
Higher-Level Access
</pre>

### 6. Enumerating Further

With additional privileges, reassess the environment to discover resources that were previously inaccessible.

Examples:

* Internal repositories
* API keys
* Database credentials
* Configuration files
* Sensitive source code
* Internal services

The important concept is that **new access can reveal a larger attack surface**.

### 7. Compromise Remote Users / Sites

This step represents **lateral movement** through the environment.

An attacker may use compromised credentials or trusted relationships to access additional systems.

<pre>
Compromised System
        ↓
   Credentials
        ↓
   Other Systems
        ↓
Additional Access
</pre>

Possible targets include:

* Developer workstations
* Internal servers
* Mail servers
* Other network segments

The objective is to determine how far an attacker could move after the initial compromise.

### 8. Maintaining Access

Assess whether an attacker could maintain access after the original entry point is removed or the system is restarted.

This relates to **persistence**.

During a controlled assessment, persistence mechanisms may be documented or safely demonstrated without actually leaving unauthorized access behind.

Examples of persistence concepts include:

* Backdoors
* Scheduled execution
* Compromised accounts
* CI/CD pipeline manipulation

The goal is to understand whether an attacker could retain a foothold.

### 9. Covering Tracks

The final step examines how an attacker could avoid detection by removing or obscuring evidence of their activity.

A penetration tester may assess:

* Which logs record testing activity
* Whether authentication events are logged
* Whether administrative actions are recorded
* Whether security alerts are generated
* Gaps in centralized logging

The focus is on identifying **detection and logging weaknesses**, not permanently destroying evidence.

---

## Phase 3 : Reporting and Cleanup

After testing, findings are documented and prioritized according to their **technical and business impact**.

A typical report contains:

* Executive summary
* Technical findings
* Evidence
* Attack paths
* Business impact
* Severity
* Remediation recommendations

### Cleanup

Before closing the engagement:

* Remove temporary test artifacts
* Revoke temporary accounts
* Remove test files
* Restore modified configurations
* Confirm that no testing residue remains

<pre>
Testing
   ↓
Evidence Collection
   ↓
Reporting
   ↓
Cleanup
   ↓
Client Confirmation
</pre>

---

## ISSAF's Attack Progression

One of the most useful ways to understand ISSAF is to group its nine steps by attack stage:

| Steps | Main Activity                      |
| ----- | ---------------------------------- |
| 1–3   | Reconnaissance and analysis        |
| 4–7   | Exploitation and deeper compromise |
| 8     | Persistence                        |
| 9     | Stealth / detection avoidance      |

This creates a simplified attacker progression:

<pre>
Reconnaissance
      ↓
Attack Surface Discovery
      ↓
Initial Compromise
      ↓
Privilege Escalation
      ↓
Further Enumeration
      ↓
Lateral Movement
      ↓
Persistence
      ↓
Stealth
</pre>

This is why ISSAF remains useful for understanding **adversarial thinking**, even though its technical content is outdated.

---

## Strengths

* Clear end-to-end assessment structure
* Strong attacker-oriented perspective
* Covers multiple security domains
* Provides a useful model for understanding attack progression
* Uses risk-based prioritization
* Helpful for learning how individual vulnerabilities can form a larger attack chain

## Limitations

* No longer actively maintained
* Latest version is from around 2006
* Tool-specific instructions are outdated
* References old software and techniques
* No active official development community

Therefore, ISSAF should **not** be used as the primary source for modern tool usage or current exploitation techniques.

---

## ISSAF vs Modern Frameworks

| Framework           | Main Focus                                                |
| ------------------- | --------------------------------------------------------- |
| **ISSAF**           | Adversarial assessment methodology and attack progression |
| **PTES**            | Practical end-to-end penetration testing                  |
| **OWASP WSTG**      | Detailed web application security testing                 |
| **NIST SP 800-115** | Security testing and assessment methodology               |
| **OSSTMM**          | Quantifiable and repeatable security testing              |

ISSAF can therefore be combined conceptually with newer frameworks rather than followed as a standalone modern testing guide.

---

## Key Takeaways

* **ISSAF** stands for Information Systems Security Assessment Framework.
* It was developed by **OISSG** and is no longer actively maintained.
* Its assessment process has **three major phases**:

  1. Planning and Preparation
  2. Assessment
  3. Reporting and Cleanup
* The Assessment phase contains **nine steps**, progressing from reconnaissance to covering tracks.
* Its greatest value today is understanding **attack progression and adversarial logic**.
* Its outdated tool-specific guidance should not be relied upon for modern engagements.
* For current technical procedures, use maintained resources such as **PTES, OWASP WSTG, NIST guidance, and official tool documentation**.

## MITRE ATT&CK

## Overview

**MITRE ATT&CK** stands for **Adversarial Tactics, Techniques, and Common Knowledge**.

Developed and maintained by **MITRE**, ATT&CK is **not a traditional penetration testing framework**. Instead, it is a knowledge base that documents how real-world adversaries operate.

While frameworks such as **PTES, OSSTMM, and NIST SP 800-115** help answer:

> **How should we conduct a security assessment?**

ATT&CK helps answer:

> **What techniques do real adversaries use?**

This makes ATT&CK useful for:

* Threat intelligence
* Red teaming
* Detection engineering
* Incident response
* Adversary simulation
* Enriching penetration testing reports

---

## ATT&CK Matrix

ATT&CK organizes adversary behavior into a **matrix**.

The two main concepts are:

| Concept            | Meaning                                                             |
| ------------------ | ------------------------------------------------------------------- |
| **Tactics**        | The adversary's objective - **why** they perform an action          |
| **Techniques**     | The method used to achieve that objective - **how** they perform it |
| **Sub-techniques** | More specific variations of a technique                             |

Simplified:

<pre>
Tactic
  ↓
Why is the attacker doing this?
  ↓
Technique
  ↓
How are they doing it?
  ↓
Sub-technique
  ↓
What specific method are they using?
</pre>

### Example

<pre>
Initial Access
      ↓
Phishing (T1566)
      ↓
Spearphishing Attachment (T1566.001)
</pre>

Here:

* **Initial Access** = attacker's objective
* **Phishing** = technique
* **Spearphishing Attachment** = specific sub-technique

---

## Enterprise ATT&CK Tactics

The Enterprise matrix organizes adversary behavior across **14 tactics**:

1. Reconnaissance
2. Resource Development
3. Initial Access
4. Execution
5. Persistence
6. Privilege Escalation
7. Defense Evasion
8. Credential Access
9. Discovery
10. Lateral Movement
11. Collection
12. Command and Control
13. Exfiltration
14. Impact

These represent different objectives an adversary may pursue during an intrusion.

> Note: The Enterprise matrix has evolved over time, so the exact tactic/technique structure can change as ATT&CK is updated.

---

## Techniques and Sub-Techniques

Each technique has a unique identifier.

Examples:

| Technique                         | ID      | Purpose                                          |
| --------------------------------- | ------- | ------------------------------------------------ |
| Phishing                          | `T1566` | Obtain initial access through phishing           |
| Exploit Public-Facing Application | `T1190` | Exploit an externally exposed application        |
| Valid Accounts                    | `T1078` | Abuse legitimate credentials                     |
| OS Credential Dumping             | `T1003` | Obtain credentials from operating-system sources |

Techniques can have more specific sub-techniques.

For example:

<pre>
T1566 - Phishing
    ├── T1566.001 - Spearphishing Attachment
    ├── T1566.002 - Spearphishing Link
    └── T1566.003 - Spearphishing via Service
</pre>

---

## What a Technique Entry Contains

ATT&CK technique entries provide more than just a technique name.

They can include:

* Technique description
* Sub-techniques
* Known threat groups using the technique
* Software associated with the technique
* Detection guidance
* Mitigation recommendations
* References to real-world observations

This connection to **observed adversary behavior** is what makes ATT&CK particularly useful for security operations.

---

## ATT&CK as a Complement to Penetration Testing Frameworks

ATT&CK does **not** replace a penetration testing methodology.

A useful distinction is:

<pre>
PTES / NIST / OSSTMM
        ↓
How do we conduct the assessment?
        ↓
ATT&CK
        ↓
How do we describe the adversary behavior we observed?
</pre>

### Example

A PTES engagement might tell you to:

<pre>
Reconnaissance
      ↓
Threat Modeling
      ↓
Vulnerability Analysis
      ↓
Exploitation
      ↓
Post-Exploitation
      ↓
Reporting
</pre>

During the engagement, you may discover that an attacker could use:

* Phishing
* Valid Accounts
* Credential Dumping
* Lateral Movement
* Data Collection

These behaviors can then be mapped to corresponding ATT&CK techniques.

---

## Mapping Penetration Test Findings to ATT&CK

Mapping findings to ATT&CK gives the client additional context beyond the vulnerability itself.

| Penetration Test Finding                             | Tactic            | ATT&CK Technique                                |
| ---------------------------------------------------- | ----------------- | ----------------------------------------------- |
| Phishing attachment delivered to an employee         | Initial Access    | Spearphishing Attachment (`T1566.001`)          |
| Exploited an exposed web application                 | Initial Access    | Exploit Public-Facing Application (`T1190`)     |
| Extracted cached credentials                         | Credential Access | OS Credential Dumping (`T1003`)                 |
| Used stolen credentials to access another system     | Lateral Movement  | Use Alternate Authentication Material (`T1550`) |
| Accessed sensitive records from a compromised server | Collection        | Data from Information Repositories (`T1213`)    |

The ATT&CK mapping does **not replace the vulnerability finding**.

Instead, it adds another layer of context:

<pre>
Vulnerability
      ↓
Successful Exploitation
      ↓
Observed Adversary Behavior
      ↓
ATT&CK Technique
      ↓
Detection / Mitigation Guidance
</pre>

---

## Why ATT&CK Mapping Is Useful

Without ATT&CK mapping, a report might simply say:

> "The tester obtained access using stolen credentials."

With ATT&CK mapping, the security team can identify the corresponding adversary behavior and investigate:

* Can this behavior be detected?
* Are relevant logs being collected?
* Are alerts configured?
* Are appropriate security controls in place?
* Can similar activity be identified elsewhere?

This shifts the focus from fixing **one individual vulnerability** toward understanding the broader attack behavior.

---

## Example Attack Chain

A penetration test may reveal the following sequence:

<pre>
Phishing Email
      ↓
Initial Access
      ↓
Credential Theft
      ↓
Privilege Escalation
      ↓
Lateral Movement
      ↓
Sensitive Data Access
      ↓
Data Exfiltration
</pre>

Each stage can potentially be mapped to an ATT&CK technique.

This allows the complete attack path to be represented using a **standardized adversary-behavior vocabulary**.

---

## ATT&CK vs Penetration Testing Frameworks

| Framework / Knowledge Base | Primary Purpose                                   |
| -------------------------- | ------------------------------------------------- |
| **PTES**                   | Structure a penetration test from start to finish |
| **OSSTMM**                 | Structured and measurable security testing        |
| **NIST SP 800-115**        | Security testing and assessment guidance          |
| **OWASP WSTG**             | Detailed web application security testing         |
| **ISSAF**                  | Adversarial security assessment methodology       |
| **MITRE ATT&CK**           | Describe and categorize adversary behavior        |

The important distinction is:

<pre>
Penetration Testing Frameworks
            ↓
      Testing Methodology
            ↓
      "How do we test?"

MITRE ATT&CK
            ↓
   Adversary Knowledge Base
            ↓
"What behavior did we observe?"
</pre>

---

## Strengths

* Based on documented real-world adversary behavior
* Provides standardized technique identifiers
* Creates a common language between security teams
* Useful for red-team and adversary simulation activities
* Helps connect penetration-test findings with detection engineering
* Provides detection and mitigation context
* Useful across multiple security disciplines

## Limitations

* Large and continuously evolving knowledge base
* Requires time to learn and navigate effectively
* ATT&CK does not provide a complete penetration testing methodology
* Mapping a finding to a technique requires understanding the actual attacker behavior
* Technique coverage and applicability depend on the environment being assessed

---

## Key Takeaways

* **MITRE ATT&CK** stands for **Adversarial Tactics, Techniques, and Common Knowledge**.
* It is a **knowledge base of adversary behavior**, not a traditional penetration testing framework.
* **Tactics** describe **why** an adversary performs an action.
* **Techniques** describe **how** they achieve an objective.
* **Sub-techniques** provide more specific implementations.
* ATT&CK technique IDs provide a standardized vocabulary for describing attacker behavior.
* Penetration testers can map their findings to ATT&CK to provide additional context for clients.
* ATT&CK complements frameworks such as **PTES, OSSTMM, NIST, and OWASP WSTG** rather than replacing them.
* Its major value in penetration testing is connecting **technical findings to real-world adversary behavior and defensive detection**.

## Other Notable Frameworks

## Overview

Not every security engagement uses a general-purpose penetration testing methodology.

Some frameworks are designed for a **specific technology, industry, regulatory requirement, or security objective**. Knowing these frameworks helps a penetration tester recognize when a specialized methodology or control framework is relevant.

The five notable frameworks covered here are:

1. **WASC Threat Classification**
2. **CSA Cloud Controls Matrix (CCM)**
3. **OWASP Mobile Application Security Testing Guide (MASTG)**
4. **PCI DSS Penetration Testing Guidelines**
5. **CBEST**

The goal is not to master each framework immediately, but to understand **what it is and when it becomes relevant**.

---

## 1. WASC Threat Classification

**WASC Threat Classification** was developed by the **Web Application Security Consortium (WASC)**.

It is a **taxonomy for categorizing web application threats and attacks**.

Examples of categories include:

* Insufficient authentication
* Information leakage
* Abuse of functionality
* Input validation problems
* Authentication and authorization weaknesses

### Purpose

WASC helped provide standardized terminology for describing web application threats.

However, it is now largely **legacy material**, with modern web security work more commonly relying on resources such as:

* OWASP Top 10
* OWASP WSTG

### When You May Encounter It

* Older security documentation
* Legacy reports
* Historical web security references
* Older compliance material

> WASC Threat Classification(opens in new tab) was developed by the Web Application Security Consortium (WASC) as a taxonomy for categorizing web application vulnerabilities and attack types. It organizes threats into categories such as insufficient authentication, information leakage, and abuse of functionality. While it was influential in the mid-2000s and helped standardize how the industry discussed web threats, it has since been largely superseded by the OWASP Top Ten and WSTG as the dominant web security references. You may still encounter it referenced in older documentation or compliance frameworks.

## 2. CSA Cloud Controls Matrix

The **Cloud Controls Matrix (CCM)** is developed by the **Cloud Security Alliance (CSA)**.

It is a security controls framework designed specifically for **cloud environments**.

Unlike PTES or WSTG, CCM is **not a penetration testing methodology**.

It focuses on:

* Security controls
* Cloud governance
* Compliance
* Cloud provider security
* Security posture assessment

The framework covers areas such as:

* Data security
* Identity and access management
* Infrastructure security
* Application security
* Governance

It also provides mappings to other standards and frameworks.

### When You May Use It

CCM becomes relevant when assessing an organization's **cloud security posture** rather than simply performing a traditional penetration test.

<pre>
Cloud Environment
       ↓
Security Controls
       ↓
Control Assessment
       ↓
Compliance / Security Posture
</pre>

> CSA Cloud Controls Matrix(CCM)(opens in new tab) is published by the Cloud Security Alliance (CSA) and provides a cyber security controls framework specifically designed for cloud computing environments. It maps controls across 17 domains, including data security, identity and access management, and infrastructure security, and aligns them with major standards like ISO 27001, NIST, and PCI DSS. CCM is not a penetration testing methodology; it is a governance and compliance tool that helps organizations assess whether their cloud providers and configurations meet security requirements. You would encounter it when a client needs a cloud security posture assessment rather than a traditional pentest.

## 3. OWASP Mobile Application Security Testing Guide (MASTG)

The **OWASP Mobile Application Security Testing Guide (MASTG)** is the mobile application counterpart to the OWASP WSTG.

It provides testing guidance for:

* Android applications
* iOS applications

Areas covered include:

* Data storage
* Cryptography
* Network communication
* Platform interaction
* Authentication
* Authorization
* Code quality
* Mobile-specific security mechanisms

### MASTG and MASVS

### Example Use Case

For a mobile banking application, a tester may use MASTG to investigate:

* Weak cryptographic implementation
* Insecure network communication
* Improper platform interaction
* Authentication weaknesses

> OWASP Mobile Application Security Testing Guide (MASTG)(opens in new tab) is the mobile counterpart to the WSTG we covered in Task 3. Maintained by OWASP, the MASTG(opens in new tab) provides detailed test cases for Android and iOS application security, covering areas like data storage, cryptographic implementation, network communication, platform interaction, and code quality. If your engagement involves testing a mobile banking app, a healthcare patient portal app, or any client-facing mobile application, the MASTG is the go-to reference. It is used alongside the OWASP Mobile Application Security Verification Standard (MASVS), which defines the security requirements that the MASTG tests against.

## 4. PCI DSS Penetration Testing Guidelines

**PCI DSS (Payment Card Industry Data Security Standard)** establishes security requirements for environments that handle payment card data.

Penetration testing requirements are included within the PCI DSS framework.

This is different from frameworks such as PTES because PCI DSS requirements are tied to a **specific regulatory/compliance environment**.

Testing may need to address areas such as:

* External attack surface
* Internal network
* Cardholder-data environment
* Network segmentation
* Significant infrastructure changes

Organizations subject to PCI DSS requirements must follow the applicable testing requirements and frequencies defined by the current standard.

### When It Matters

PCI DSS becomes especially relevant for organizations such as:

* Payment processors
* Retailers handling cardholder data
* Financial/payment service providers
* Other organizations within the applicable card-payment environment

### Important Concept

A general penetration test may demonstrate that a vulnerability exists.

A PCI DSS assessment additionally needs to determine whether the testing satisfies the **specific compliance requirements** applicable to the organization's cardholder-data environment.

> PCI DSS Penetration Testing Guidelines(opens in new tab) are defined within the Payment Card Industry Data Security Standard, specifically in Requirement 11.4 (PCI DSS v4.0). Unlike the general-purpose frameworks covered earlier, these guidelines are regulatory mandates: any organization that processes, stores, or transmits cardholder data must conduct penetration tests that meet PCI DSS criteria. The guidelines specify that tests must cover both the external perimeter and the internal network, must be conducted at least annually and after significant infrastructure changes, and must validate network segmentation controls. When your client is a retailer, payment processor, or any entity in the payment card ecosystem, PCI DSS requirements will shape both the scope and the reporting format of your engagement.

## 5. CBEST

**CBEST** is a **threat-intelligence-led penetration testing framework** developed by the **Bank of England** for the UK financial sector.

It is designed for organizations such as:

* Banks
* Insurers
* Financial market infrastructure providers

The distinguishing feature of CBEST is the integration of **threat intelligence with penetration testing**.

Instead of testing only a generic set of vulnerabilities, the engagement first identifies relevant threat actors and realistic attack scenarios.

<pre>
Threat Intelligence
        ↓
Relevant Threat Actors
        ↓
Realistic Attack Scenarios
        ↓
Targeted Penetration Testing
        ↓
Business Impact
</pre>

### Key Characteristic

CBEST attempts to make testing more representative of the threats that are relevant to the specific financial institution.

> CBEST Framework(opens in new tab) was developed by the Bank of England in collaboration with the UK financial sector. It is a threat-intelligence-led penetration testing framework designed specifically for UK financial institutions, including banks, insurers, and financial market infrastructure providers. CBEST engagements begin with a bespoke threat intelligence phase that identifies the most relevant threat actors and attack scenarios for the specific institution, and the subsequent penetration test simulates those realistic threat scenarios. CBEST is notable for its close integration of threat intelligence with hands-on testing and for its regulatory backing within the UK financial sector.

## Choosing the Right Framework

## Overview

Knowing different penetration testing frameworks is only the first step. A penetration tester must also determine **which framework or combination of frameworks fits a particular engagement**.

Framework selection depends on several factors:

* Target environment
* Engagement scope
* Regulatory requirements
* Testing objectives
* Required measurement and repeatability
* Team expertise and available resources

A useful way to think about it is:

<pre>
Engagement Requirements
          ↓
Scope + Target
          ↓
Regulations
          ↓
Testing Objectives
          ↓
Team Capabilities
          ↓
Primary Framework
          ↓
Supplementary Frameworks
</pre>

In real engagements, selecting **one framework does not necessarily exclude others**. A primary methodology can structure the assessment while specialized frameworks provide additional testing or compliance requirements.

Each framework solves a different problem :

* **OSSTMM** introduced a scientific and metrics-driven approach to security testing, including **Risk Assessment Values (RAVs)**.
* **OWASP WSTG** provided a structured roadmap for **web application security testing**.
