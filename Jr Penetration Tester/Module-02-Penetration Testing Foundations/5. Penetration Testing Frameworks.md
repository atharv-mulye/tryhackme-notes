# Penetration Testing Frameworks

## Introduction

A **penetration testing framework** is a structured methodology that guides a penetration tester through the different stages of a security assessment.

Instead of performing random security checks, a framework provides a systematic process covering activities such as:

<pre>
Planning & Scoping
        ↓
Reconnaissance
        ↓
Enumeration
        ↓
Vulnerability Analysis
        ↓
Exploitation
        ↓
Post-Exploitation
        ↓
Reporting
        ↓
Remediation Validation
</pre>

The exact phases depend on the framework being used.

### Why Use a Framework ?

Without a structured methodology, a penetration test can become inconsistent and incomplete. A tester may:

* Miss important attack surfaces
* Perform tests in an unorganised manner
* Fail to document findings properly
* Test systems that are outside the agreed scope
* Produce results that are difficult for the client to act upon

A framework helps ensure that the assessment follows an established and repeatable process.

---

## Benefits of Penetration Testing Frameworks

### 1. Thoroughness

A structured methodology helps testers systematically cover the relevant attack surface and reduces the chance of overlooking important security issues.

### 2. Consistency

Using the same methodology allows different testers or teams to follow a comparable process and produce more consistent results.

### 3. Compliance

Some organisations need security assessments to align with specific standards, regulations, or industry requirements.

Frameworks can provide a recognised methodology for conducting and documenting these assessments.

### 4. Better Communication

A recognised methodology makes it easier for:

* Penetration testers
* Security teams
* Clients
* Auditors
* Management

to understand how the assessment was performed and how the findings were identified.

## Major Penetration Testing Frameworks

Different frameworks are designed for different purposes. There is no single methodology that is appropriate for every type of security assessment.

| Framework                                  | Primary Focus                                              |
| ------------------------------------------ | ---------------------------------------------------------- |
| **OSSTMM**                                 | Scientific and metrics-driven security testing             |
| **OWASP WSTG**                             | Web application security testing                           |
| **NIST SP 800-115**                        | Technical security testing and assessment                  |
| **PTES**                                   | Practical, phase-based penetration testing                 |
| **ISSAF**                                  | Detailed security assessment methodology                   |
| **MITRE ATT&CK**                           | Adversary tactics and techniques                           |
| **WASC Threat Classification**             | Web application threat classification                      |
| **CSA Cloud Controls Matrix**              | Cloud security controls                                    |
| **OWASP MASTG**                            | Mobile application security testing                        |
| **PCI DSS Penetration Testing Guidelines** | Payment-card environment testing                           |
| **CBEST**                                  | Threat-intelligence-led assessments for financial services |

---

## 1. OSSTMM

**Open Source Security Testing Methodology Manual (OSSTMM)** provides a scientific and metrics-driven approach to security testing.

It focuses on measuring security through a structured testing methodology.

## 2. OWASP WSTG

**OWASP Web Security Testing Guide (WSTG)** is focused specifically on **web application security testing**.

It provides guidance for testing areas such as:

* Authentication
* Authorisation
* Session management
* Input validation
* Configuration
* Business logic
* Client-side security

This is particularly relevant when performing **Web Application VAPT**.

## 3. NIST SP 800-115

**NIST Special Publication 800-115** provides technical guidance for conducting information security testing and assessments.

It covers activities such as:

* Planning
* Discovery
* Attack and penetration
* Reporting

NIST publications are widely used as references for structured security assessment processes.

## 4. PTES

**Penetration Testing Execution Standard (PTES)** provides a practical, phase-driven approach to penetration testing.

Its methodology broadly follows the lifecycle of a real penetration testing engagement, from **pre-engagement interactions through reporting**.

## 5. ISSAF

**Information Systems Security Assessment Framework (ISSAF)** is a detailed security assessment methodology.

It provides structured guidance for assessing different areas of an organisation's security environment.

It is historically influential and includes a detailed assessment process.

## MITRE ATT&CK

**MITRE ATT&CK** is different from a traditional end-to-end penetration testing framework.

It is a knowledge base that documents **adversary tactics and techniques** based on real-world observations.

It can complement penetration testing by helping testers understand and map attacker behaviour.

<pre>
Penetration Testing Framework
            +
      MITRE ATT&CK
            ↓
Better Understanding of
Adversary Techniques
</pre>

---

## Other Security Frameworks and Guides

Several specialised frameworks and guides exist for particular environments or purposes:

### WASC Threat Classification

Focuses on categorising threats against **web applications**.

### CSA Cloud Controls Matrix

Provides a framework for evaluating **cloud security controls**.

### OWASP MASTG

The **Mobile Application Security Testing Guide (MASTG)** focuses on testing **mobile applications**.

### PCI DSS Penetration Testing Guidelines

Provides guidance for penetration testing within environments subject to **PCI DSS** requirements.

### CBEST

**CBEST** is a threat-intelligence-led security assessment framework designed for the **financial services sector**.

---

## Choosing a Framework

The appropriate methodology depends on the **scope and objective of the assessment**.

<pre>
What are you testing ?
        ↓
Web Application → OWASP WSTG
        ↓
Mobile App     → OWASP MASTG
        ↓
General Security Assessment → NIST / PTES / OSSTMM
        ↓
Adversary Behaviour → MITRE ATT&CK
        ↓
Cloud Environment → CSA CCM
        ↓
Payment Environment → PCI DSS Guidance
</pre>

A penetration tester may also combine multiple methodologies when appropriate.

For example, a web application assessment could use:

<pre>
OWASP WSTG
     +
PTES
     +
MITRE ATT&CK
</pre>

Each provides a different perspective rather than replacing the others.

## Key Takeaways

* A **penetration testing framework** provides a structured methodology for conducting security assessments.
* Frameworks help improve **thoroughness, consistency, compliance, and communication**.
* Different frameworks are designed for different **testing objectives and environments**.
* **OWASP WSTG** is focused on web application security testing.
* **NIST SP 800-115** provides technical guidance for security testing and assessment.
* **PTES** provides a practical, phase-driven penetration testing methodology.
* **OSSTMM** uses a scientific and metrics-driven approach.
* **ISSAF** provides a detailed security assessment methodology.
* **MITRE ATT&CK** complements penetration testing by documenting adversary tactics and techniques.
* Specialised guides such as **MASTG, CSA CCM, PCI DSS, WASC, and CBEST** address specific technologies or industries.
* The framework should be selected based on the **scope, target environment, and objective of the assessment**.

## OSSTMM

## Overview

**OSSTMM (Open Source Security Testing Methodology Manual)** is a security testing methodology developed by the **Institute for Security and Open Methodologies (ISECOM)**.

Its main philosophy is:

> **Measure security instead of relying only on subjective opinions.**

OSSTMM applies a more **scientific, quantitative, repeatable, and verifiable** approach to security testing.

Instead of simply reporting that a system is "secure" or "insecure", OSSTMM focuses on measuring the target's **attack surface, exposure, and effectiveness of security controls**.

---

## Five Security Channels

OSSTMM divides security testing into **five channels**. This ensures that testing is not limited to network infrastructure alone.

| Channel     | Focus                   | Examples                                           |
| ----------- | ----------------------- | -------------------------------------------------- |
| **HUMSEC**  | Human Security          | Social engineering, human-factor weaknesses        |
| **PHYSSEC** | Physical Security       | Physical access, badge systems, tailgating         |
| **SPECSEC** | Wireless Communications | Wi-Fi, Bluetooth, RFID, electromagnetic signals    |
| **COMSEC**  | Telecommunications      | VoIP, phone systems, fax, modems                   |
| **DATASEC** | Data Networks           | Network services, firewalls, application protocols |

### 1. HUMSEC — Human Security

Focuses on vulnerabilities involving people.

Examples:

* Social engineering
* Credential disclosure
* Weak security awareness
* Manipulation of employees

### 2. PHYSSEC — Physical Security

Evaluates physical controls protecting systems and facilities.

Examples:

* Badge readers
* Physical access controls
* Server-room security
* Tailgating

### 3. SPECSEC — Wireless Communications

Covers wireless and electromagnetic communication technologies.

Examples:

* Wi-Fi
* Bluetooth
* RFID
* Other wireless signals

### 4. COMSEC — Telecommunications

Focuses on telecommunications infrastructure.

Examples:

* Phone systems
* VoIP
* Fax systems
* Modems

### 5. DATASEC — Data Networks

Focuses on traditional network and application-layer security.

Examples:

* Network services
* Firewalls
* Network protocols
* Application-layer protocols

### Why Five Channels?

An organisation may have strong network security but still be vulnerable through another channel.

For example:

<pre>
Strong Network Security
        ↓
But...
        ↓
Employee → Social Engineering
        OR
Physical Access → Tailgating
        ↓
Security Controls Bypassed
</pre>

The five-channel model encourages testers to consider the **complete attack surface**.

---

## Risk Assessment Values (RAVs)

A key part of OSSTMM's quantitative approach is the **Risk Assessment Value (RAV)**.

RAV is used to measure the relationship between:

* **Attack surface / exposure**
* **Security controls**

Conceptually:

<pre>
Attack Surface / Exposure
           ↕
     Security Controls
           ↓
          RAV
</pre>

A **positive RAV** indicates residual exposure or risk remains.

A RAV **close to zero** indicates that the security controls are more closely matched to the measured exposure.

The purpose of using numerical measurements is to make security assessments more:

* Repeatable
* Verifiable
* Auditable
* Comparable

## OSSTMM Testing Phases

The OSSTMM testing cycle can be divided into **four phases**:

<pre>
Induction
   ↓
Interaction
   ↓
Inquiry
   ↓
Intervention
</pre>

---

## Phase 1: Induction

**Induction** focuses on **enumeration and verification**.

The tester identifies what exists within the defined scope and verifies that the discovered assets are real and responsive.

Typical activities may include:

* DNS enumeration
* Certificate transparency review
* Subdomain discovery
* Asset discovery
* Service verification

### Output

A **confirmed inventory of the target environment**.

<pre>
Discover Assets
      ↓
Verify Assets
      ↓
Confirmed Target Inventory
</pre>

---

## Phase 2: Interaction

**Interaction** focuses on **qualification and quantification** of the verified assets.

The tester actively interacts with the discovered systems to understand their technologies, services, and exposure.

Activities may include:

* Connecting to services
* Technology fingerprinting
* Service enumeration
* Measuring exposed services
* Assessing accessibility

The results contribute to understanding the target's **attack surface**.

<pre>
Verified Assets
      ↓
Active Probing
      ↓
Service / Technology Identification
      ↓
Quantify Exposure
</pre>

---

## Phase 3: Inquiry

**Inquiry** focuses on determining whether the measured exposure can be converted into **unauthorised access or increased privileges**.

Testing may involve:

* Exploitation
* Privilege escalation
* Access-control testing
* Verification of discovered vulnerabilities
* Determining the actual impact of a vulnerability

For example, an IDOR vulnerability might allow one authenticated user to access another user's information.

The tester then verifies the **actual scope of access** rather than simply reporting that an IDOR exists.

<pre>
Identified Exposure
        ↓
Attempt Exploitation
        ↓
Verify Access
        ↓
Determine Actual Impact
</pre>

---

## Phase 4 : Intervention

**Intervention** focuses on **quarantine, audit, and enticement**.

### Quarantine

Address or isolate a discovered security issue and evaluate the effectiveness of the response.

### Audit

Examine the wider environment to determine whether similar weaknesses exist elsewhere.

### Enticement

Use controlled mechanisms to test whether security monitoring and detection capabilities respond to attacker activity.

For example, a **canary token** can be used to determine whether unauthorised access triggers an alert.

<pre>
Identify Weakness
      ↓
Quarantine / Address
      ↓
Audit Wider Environment
      ↓
Test Detection
</pre>

---

## OSSTMM Reporting

OSSTMM uses the **Security Test Audit Report (STAR)** format for reporting.

The standardised reporting approach helps provide:

* Consistent documentation
* Auditable results
* Repeatable assessments
* Easier comparison between assessments or teams

---

## Strengths and Limitations

| Aspect         | OSSTMM                                                |
| -------------- | ----------------------------------------------------- |
| Approach       | Scientific and measurement-driven                     |
| Focus          | Broad security testing                                |
| Key concept    | Quantification and RAVs                               |
| Coverage       | Human, physical, wireless, telecom, and data networks |
| Reporting      | STAR                                                  |
| Main advantage | Repeatable and auditable measurements                 |
| Challenge      | Steep learning curve                                  |
| Challenge      | Can require significant time and expertise            |

## Key Takeaways

* **OSSTMM** stands for **Open Source Security Testing Methodology Manual**.
* It was developed by **ISECOM**.
* Its core philosophy is **metrics over subjective opinions**.
* OSSTMM considers five security channels: **HUMSEC, PHYSSEC, SPECSEC, COMSEC, and DATASEC**.
* **RAVs (Risk Assessment Values)** provide a quantitative way to assess exposure and security controls.
* The four major testing phases are:

  1. **Induction** — enumeration and verification
  2. **Interaction** — qualification and quantification
  3. **Inquiry** — privilege/access testing and verification
  4. **Intervention** — quarantine, audit, and enticement
* OSSTMM uses the **STAR** format for security test reporting.
* Its measurement-driven approach makes assessments more **repeatable, auditable, and comparable**.
